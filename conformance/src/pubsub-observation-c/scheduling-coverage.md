# C scheduling disposition coverage

The optional `schedulingDisposition` is bound to the exact source run/head/packet/descriptor and runtime binary/input digests, the approved proposal/correction/review, and owner decision line hashes. It applies only to named unfiltered control windows, R12/N12/N13 finite valid-Seek windows, and R9 cross-key interleaving. It does not change the recorder or add calls, attempts, waits, or parent-closure authority.

`semanticVerdict`, `physicalVerdict`, and `counts` remain the exact comparison outputs. `dispositionVerdict` and `dispositionCounts` are separate owner-bound semantic obligation results. Each proof retains the source/runtime binding, actual deliveries, required/received/ACKed identities, original source request IDs, and retained uncertainty. Consumers must explicitly choose the owner-bound result rather than rewriting historical records.

|Obligation|Dedicated verification|
|---|---|
|Exact owner, source, and runtime binding; no filtered/R8/N8/R13 expansion|Approximate approval/source/runtime mutations and excluded stage tests|
|Complete published control coverage and own-token ACKs|All six three-marker permutations, all four partition cuts, and every proper subset; matching first batch stays NC|
|Publication/ID/payload/topic/token and duplicate correspondence|maxMessages, payload drift, foreign ID, token collision, repeated acknowledged marker under a fresh token|
|Same-key sequence and one outstanding batch per key|R9 allowed cross-key permutations, same-key inversion, outstanding-key overlap|
|Finite valid-Seek eligibility and original exclusion|Snapshot pre-ACK forbidden marker, required marker present/missing, empty censored window|
|Current ACK effect, observed errors, exact lease deadline|Stale/failed/unknown ACK, empty/nonempty ACK error, exact expiration and nanosecond boundary|
|Strict envelope fields, deliveryAttempt, timestamp and verified clock|Unexpected field, altered deliveryAttempt/publishTime, missing clock receipts|
|Original dispatch count and actual-token continuation|Two original Pull/ACK slots with a different local partition, no unapproved continuation|
|Historical/exact evidence and source immutability|Unchanged batches retain exact MATCH; changed partitions retain exact difference and separate obligation verdict; input remains byte-equivalent|

The isolated mutation harness exercises approval, runtime, payload, forbidden membership, duplicates, maxMessages, same-key order, outstanding batches, ACK deadlines, complete marker ACKs, and retained delivery shape. A passing baseline and unchanged control distinguish a killed behavioral mutant from an invalid harness. Full actual replay completion and independent parent closure remain separate obligations.

An empty finite Seek proof remains NOT_COMPARABLE because it does not manufacture a marker/ACK witness. This additive uncertainty does not create a new requirement that every production recording/window be nonempty, authorize extra observations, or decide parent closure. Original G0 obligations and evidence across the two recordings must be assessed independently.
