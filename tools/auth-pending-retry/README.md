# Phone MFA refusal and retry

This local correction delays credential consumption until request matching succeeds. It is not a new production observation or approval.

The HTTP handler now checks an SMS code without consuming it, validates its MFA purpose and exact pending credential, and consumes the code after successful core finalization. The core finalizer checks that both the pending credential and requested phone factor exist before removing the pending credential and its owner index. Existing request serialization, SMS expiry validation and transient expiry sweeping remain unchanged.

## Local coverage

- Two independent pending credentials for the same account are created by real password sign-ins. An SMS session from A combined with pending B is refused without losing the SMS code, changing the pending count or emitting a notice. A can then use that same code and obtain an ID token that retrieves the original account. Both profiles are tested without blocking hooks.
- Successful retry consumes the SMS code immediately, checked directly in the store before request-level sweeping can mask a missing consumption. Reusing the completed combination is refused.
- A core finalization request naming an absent factor preserves its pending credential; a retry naming the existing factor succeeds and removes that pending credential.
- A valid plain phone sign-in code is refused by the MFA finalizer, and a valid MFA sign-in code is refused by the plain phone sign-in, each with `INVALID_SESSION_INFO`. Neither refusal removes a code, changes the pending count or emits a notice. Both codes then succeed for their own purpose and are consumed exactly once. This regression was added after the fix and passed against it; it fails when the finalizer consumes the code before checking its purpose.

- Expiry boundaries on the virtual clock, through the HTTP handlers and their request-level sweep: an MFA SMS code is accepted exactly at its lifetime and refused one second later with `INVALID_SESSION_INFO` while the pending credential survives, so the same pending credential can start a fresh code and finalize with it; the expired code stays dead. A pending credential is accepted exactly at its lifetime and gone one second later, so both finalize and start are refused. In that case the code was issued one second before the pending credential expired and is still valid on its own at the request (checked directly in the store before the request sweeps), so its removal is attributable to the pending sweep alone; disabling the orphaned-code sweep fails the test. Off-by-one mutations of the SMS and pending boundaries fail these tests.

## Disabled after the first factor

A second local correction: an account disabled after its pending credential was issued could still complete `mfaSignIn:finalize` and receive tokens, because neither core finalizer nor ID token issuance checked the disabled flag (password, refresh, and `mfaSignIn` first-factor paths already did). Both core finalizers now refuse with `USER_DISABLED` after the pending credential is found and before any factor is matched or consumed, and `mfaSignIn:start` refuses before issuing a code. The refusal is pre-finalization: the pending credential and its code survive, so a re-enabled account completes the same sign-in. The HTTP regression checks the refusal for both start and finalize, unchanged codes, pending count and last sign-in time, and the successful retry after re-enablement; the core regression checks that neither the TOTP step nor the sign-in time is recorded for a disabled account and that the same code succeeds once re-enabled. The same guard was added to TOTP enrollment finalization as defense in depth: over HTTP the ID token check already refuses a disabled account, but the core mutator now refuses too, keeping the pending enrollment for a re-enabled account. The HTTP TOTP regression covers the sign-in finalize (which has no adapter-level guard), enrollment start and enrollment finalize while disabled, and the retry after re-enablement. Deletion of the account already removes its pending credentials and codes; withdrawal of the factor is refused by the existing factor check. The production error precedence between `USER_DISABLED` and other refusals at this endpoint has not been observed. Token revocation is a separate, unverified transition: a pending credential carries its start time, but finalization does not compare it with `validSince`, so a password reset, an administrative password change or an explicit revocation after the first factor leaves the existing pending credential and code usable until they expire. Whether production refuses such a credential is unobserved and is tracked as an open issue rather than pinned here.

## Blocking hook path

With a blocking `beforeSignIn` hook, the finalize runs first on a cloned candidate store, the hook runs with no lock held, and the commit re-runs the finalize on the live store before applying the hook response and issuing tokens; the live store is replaced only when the whole commit succeeds. Two local regressions pin what that structure gives: a hook that rejects (503) discards the candidate, so the SMS code and the pending credential survive and the same credentials succeed once the hook passes; an account disabled while the hook runs (the live store changed by an administrator during the hook) is refused at the commit with `USER_DISABLED`, with nothing consumed or issued, because the commit re-runs the core finalize on the live store where the disabled guard applies. Removing that guard fails the second regression. Not covered: a hook response that itself sets `disabled` on the same request still issues tokens (filed separately, production behavior unobserved), and expiry during the hook is judged at the request's own logical time without a second sweep at the commit.

These tests are selected by `pending_retry` in the HTTP `auth_flows` and core `mfa` test binaries and run in compatibility CI. The first two regressions failed against the previous implementation: the SMS listing became empty after a pending mismatch, and the pending owner disappeared after a missing-factor refusal.

The guarantee is limited to the tested pre-finalization refusals. It does not promise rollback for every subsequent token issuance or signing failure, all disabled/revoked/expired-user transitions, expiry of pending credentials whose code was issued by a different request than the one being finalized, the enrollment purpose against the finalizer, tenant boundaries, or production error precedence. Existing historical evidence and approvals are preserved and checked at their pinned sources. The broader MFA/Auth audit remains incomplete.
