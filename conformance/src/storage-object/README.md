# Partial Storage object request declarations

`buildCorpus({ bucket, prefix })` produces deterministic request data for twenty-four of the twenty-six frozen behavior recipe IDs. It has no transport, credential discovery, authorization grant or response normalization. The prefix is limited to 256 characters as a planner bound, independently of any service limit.

The declarations cover simple Firebase upload, cross-dialect state, both dialects' download ranges, metadata changes and repeated deletion, Firebase overwrite, missing-object operations, and invalid ranges before and after an empty overwrite. Every metadata change, repeated deletion and negative range observation includes metadata and full-media readbacks. Upload and media bodies remain binary. HTTP status, all headers and raw body bytes are requested for private capture; no production response is assumed or normalized here.

The result declares at most 1,891 request entries per recording, including 262 preflight entries and 383 cleanup entries for 125 distinct names. Eighty-one continuation entries are conditional on prior list or rewrite tokens, resumable progress, or session cancellation. This count excludes credential acquisition/refresh, retries and all future transport machinery. It is not an authorized wire budget. Cleanup declarations never authorize deleting an object: a future runner must prove initial absence and ownership and preserve unresolved responsibility after uncertain outcomes.

The base corpus lists two behavior recipes in `remainingRecipeIds`; `buildAuthCorpus()` now declares those separately. The current-generation GCS download declaration now includes selected-generation observations. State admission between steps remains unimplemented: the future runner must refuse dependent observations when upload, metadata update or absence prerequisites were not established, and must preserve raw evidence when a supposedly nonmutating operation changed state. In particular, the two missing-object dialect sequences are not independently admissible if an earlier operation unexpectedly created the object. None of these declarations marks a frozen condition complete.

## Object-name boundary declarations

The object-name recipe owns separate names containing LF and separate 1,025-byte UTF-8 names for the Firebase and GCS dialects under one reserved prefix. Each dialect declares upload and GET with its own two invalid names. Every upload candidate is followed by both dialects' metadata and complete media reads for its attempted name plus four bounded collection page slots per dialect. The preflight includes the same bounded collection traversal. A nonempty continuation token after page four is incomplete, never an empty-prefix result. An omitted-name upload and empty-name GET have no owned object name on the wire, so they are not declared as executable steps; a prior review identified the risk of an undetected object created outside the owned scope. The two list requests with LF and oversized prefix filters are controls only: a list prefix is a filter, not an object-name argument. Missing-prefix bucket-wide listing is deliberately absent. `coverage: "partial-missing-name-and-list-path-semantics"` and the remaining obligation keep these gaps visible.

`validateStorageRoute()` therefore accepts a collection GET without `objectName` only when its bucket route is exact and both `scopePrefix` and `query.prefix` stay inside the owned run prefix. A collection request has no individual object path: the [GCS JSON list method](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/list) uses `GET /storage/v1/b/{bucket}/o` and applies `prefix` as a filter; the [Firebase Storage list API](https://firebase.google.com/docs/storage/web/list-files) uses the same list semantics. The validator rejects an unscoped list, another run's prefix, a collection mutation or an invented object name. This resolves the route-inventory failure without changing the declared object-name controls.

These are comparisons, not predicted errors or post-state. Even a rejected status does not prove that nothing was published. The declaration has no live pagination resolver for this recipe, no verified ownership journal and no safe cleanup admission. The future runner must bind all pre/post pages and names to one authorized run, stop on incomplete pages or surprising creation, and account for cleanup if an invalid-looking name is nevertheless accepted. The frozen closure condition remains pending. The name limits follow [Cloud Storage object naming requirements](https://docs.cloud.google.com/storage/docs/objects); Firebase dialect behavior still requires production recordings.

Two real production recordings, response-normalization decisions, a final-artifact comparison and an independent closure review are still required. Raw responses can contain private download tokens and must not be published before reviewed normalization.

## List declarations

Each list recipe seeds six small names under a dialect-specific owned prefix and reads back metadata and complete bytes after each upload. The two collection preflight requests declare an empty-prefix check through both dialects. Object baselines alone cannot establish that no unrelated object already exists under the prefix. Flat, delimited, subdirectory, empty-prefix and zero-limit collection requests use the bucket collection route. The GCS recipe additionally declares start/end offset and glob filters.

Each recipe declares twelve delimited page slots. Firebase uses `maxResults=2`; GCS uses `maxResults=3` so that a normally filled first page contains both object items and a directory prefix. The GCS pagination declaration explicitly requires a mixed item/prefix page in the eventual response. After the first slot, `continuation` names the preceding step as the source of `nextPageToken`, with a 4,096-byte token limit and a skip-on-missing declaration. No token is invented in the static query. Even if all twelve slots are used, a remaining token means the traversal is incomplete. A future runner must bind the exact request to its raw response and stop only on verified exhaustion. A service may return fewer entries than the requested maximum, so the fixture alone does not establish a mixed page. A missing or malformed response cannot be treated as exhaustion. The declarations contain no executable continuation logic, ownership gate or production authorization.

`evaluateListPages({recipe,pages,bucket})` checks a supplied page sequence against these declarations. Each supplied page carries its step ID, observed query, HTTP status and canonical raw body bytes in base64. The evaluator bounds and parses the raw list, checks the preceding token against each next query, enforces the per-page item/prefix limit, verifies owned direct names and prefixes, ordered complete fixture coverage without duplicates, a token-free final page, and the GCS mixed page. It returns only a frozen `MATCHED_SUPPLIED_PAGES` summary with send and cleanup authorization false. The supplied query and response can be fabricated; the evaluator has no durable request binding, temporal freshness, seed/preflight proof or production send ability. List filters, flat results and maxResults zero still require separate result evaluation and the two production recordings.

The request shapes follow [Firebase Storage list files](https://firebase.google.com/docs/storage/web/list-files), [Firebase SDK list request construction](https://github.com/firebase/firebase-js-sdk/blob/main/packages/storage/src/implementation/requests.ts) and the [GCS JSON objects.list API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/list). These sources define request parameters, not production behavior for the frozen comparison.

## Copy and rewrite declarations

The GCS copy/rewrite recipe owns a source, two success destinations, separate missing source/destination pairs for copy and rewrite, and two live destinations for conditional refusal. It records both dialects' metadata and complete media before and after each missing-source attempt and after all other transfer attempts. Initial absence is declared for all nine names; two refusal destinations are then seeded with bytes different from the source. Copy and rewrite use the documented `/storage/v1/.../copyTo/...` and `/storage/v1/.../rewriteTo/...` routes with destination `ifGenerationMatch=0`. Each first transfer request with a present source also references the prior GCS source metadata for `ifSourceGenerationMatch` and `ifSourceMetagenerationMatch`; missing-source controls have no source reference. Source metadata is marked before transfer, and the rewrite request specifies a different destination metadata marker. No result status or post-state is assumed.

Rewrite has eight bounded request slots. After the first, each slot declares a token from the preceding `done:false` response and omits the initial body and precondition fields, as allowed by the API. A future runner must validate `storage#rewriteResponse`, use the exact opaque token only while unfinished, and treat a still-unfinished eighth response as incomplete. If an earlier slot finishes, all later slots must be skipped. The current corpus does not resolve rewrite tokens, bind responses to requests, prove source freshness or destination ownership, decide conditional refusal, or authorize cleanup or production send. The recipe follows the [GCS copy API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/copy), [rewrite API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/rewrite) and [precondition guide](https://docs.cloud.google.com/storage/docs/request-preconditions).

`evaluateRewriteAttempts({recipe,attempts,bucket})` checks a caller-supplied sequence of at most eight raw rewrite responses and claimed request queries. It validates the declared route and source metadata reference, canonical bounded Base64 carrying UTF-8 JSON, HTTP status, response kind, uint64 progress, exact token continuity, final `done:true`, and the completed destination resource identity. An unfinished eighth response remains incomplete. The frozen result reports only `MATCHED_SUPPLIED_REWRITE`, with send and cleanup authorization false. This evaluator cannot prove that the supplied query or response came from HTTP, that the initial query used the observed source generation, that the source or destination was owned at send time, or that the final destination bytes match. Durable request/response binding, execution, state admission, two production recordings and final comparison remain required.

`local-copy.mjs` runs this recipe through the counted loopback sender. `sendRewriteStep()` resolves the initial source guards from its own captured responses and confirms source ownership; subsequent slots use only the preceding captured unfinished response. Bound progress must preserve source size, token order and the eight-call limit. A completed wrapper resource, current metadata and complete bytes must agree before the destination can be cleaned up. An uncertain continuation retains the pending destination while other confirmed objects receive fresh reads and conditional cleanup. A refused first rewrite is followed by both APIs' absence reads before stopping. Public failures use fixed codes so arbitrary transport exceptions cannot expose token-bearing URLs.

The recipe observes the first Firebase metadata read with three explicit metadata requests in GCS, Firebase, GCS order. Public observations contain only metageneration and token presence; raw token values remain private. Subsequent transfer readbacks use Firebase before GCS so source guards refer to the later GCS state. The three extra declaration entries bring the base total to 1,891. This ordering and the local observation do not establish production behavior or authorize a production send.

The GCS upload declares destination `ifGenerationMatch=0`, and GCS deletion matches the generation read after upload. The Firebase upload does not assume that the Firebase upload route implements that GCS JSON parameter. The recipe's `credentialContract` requests an owner ADC Google OAuth2 access token presented as a Bearer credential and retained only in private evidence. It does not contain or acquire any token.

This is a request declaration, not proof that the intended owner identity acquired the token, that the Bearer header reached either API, or that either API authorized the operation. A future runner must bind a verified owner ADC subject, token expiry, complete wire request and response, initial absence and ownership to the private journal. The Firebase upload and Firebase deletion need explicit race-safe admission decisions before production send because neither has a declared generation guard. The GCS deletion guard also requires genuine request-bound, fresh metadata and ownership evidence; a caller-supplied response map alone cannot authorize it. The [Cloud Storage JSON API parameters](https://docs.cloud.google.com/storage/docs/json_api/v1/parameters) define the Bearer header; the [Firebase Admin SDK setup guide](https://firebase.google.com/docs/admin/setup) describes ADC for privileged use.

## Firebase download token declaration

The `storage-object/firebase/download-tokens` recipe owns one object. It declares a Firebase upload, both-dialect readbacks, a `create_token` request, two metadata reads and two anonymous token-bearing media downloads, followed by `delete_token`, a download with the old token and both-dialect readbacks. The same typed private token reference selects exactly one token newly appearing between the pre-create Firebase metadata and the create response for every token-bearing request; no token value or URL is embedded in the corpus. Token mutations use the owner credential declaration while token-bearing downloads explicitly carry none. The sequence contains twenty-one static request entries, including preflight and cleanup.

This recipe grants neither send nor cleanup admission. A future runner must bind the raw create response to the exact request and owned object, validate the token's shape and lifetime, protect it in private evidence, and refuse unresolved or ambiguous values. If the pre-create and create-response token sets do not differ by exactly one value, it must not perform a token-bearing request or deletion. The fixed allow rule means a successful anonymous download cannot by itself prove that the token granted access, and a successful download after deletion cannot by itself prove that deletion failed. Token reuse, revocation and production response shapes require the two real recordings and reviewed normalization. The [Firebase download guide](https://firebase.google.com/docs/storage/web/download-files) describes token-bearing download URLs, but does not establish the REST response of these probe requests.

## Multipart and checksum declarations

Both dialects include a valid binary multipart request, malformed JSON metadata and a missing media part. The GCS recipe also includes a media-only insert. Each attempt owns a different name and records metadata and media through both APIs immediately afterward. Multipart framing preserves non-UTF-8 bytes with CRLF separators; each serialized request body is bounded by 2,048 bytes under the planner prefix limit.

Seven GCS checksum attempts use the fixed `123456789` input: valid MD5, valid CRC32C, both valid, individual mismatches and individually malformed declarations. The valid CRC32C check value is `0xe3069283` in big-endian base64 (`4waSgw==`). Every case has independent baseline and cleanup declarations. The malformed cases are observations: rejection and non-publication are not established until real responses and post-state are examined. Initial absence and resource ownership remain mandatory runtime obligations.

Request construction follows the [Firebase SDK multipart implementation](https://github.com/firebase/firebase-js-sdk/blob/main/packages/storage/src/implementation/requests.ts), [GCS object insertion API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/insert) and [GCS checksum validation documentation](https://docs.cloud.google.com/storage/docs/data-validation). These sources define request shapes; they do not substitute for production recordings.

## Generation and metageneration declarations

Generation guards cover match/not-match on upload, metadata read, media read and delete, each with current, stale, zero-with-live-object and zero-without-live-object controls. These 32 subjects each use a different owned name. Stale values come from a metadata read before an actual overwrite with different bytes; a declared prerequisite requires the later observed generation to differ. No generation number is guessed or incremented.

Metageneration guards cover match/not-match on PATCH, PUT and DELETE, each with current, stale, empty, negative, fractional and nonnumeric inputs. These 36 subjects also have separate names. Stale metageneration requires a metadata-only update, a changed observed metageneration, equal before/after generation, unchanged bytes and the updated metadata marker. Every metageneration request additionally matches the current observed generation. Every guarded subject is followed immediately by metadata and full-media readbacks through both APIs; responses and post-state are observations, including the malformed cases.

Dynamic query values use `{kind:"metadata-field",step,field,format:"positive-decimal-string"}`. References point backward to a GCS metadata GET for the same declared object, or to the declared transfer source for `ifSourceGenerationMatch` and `ifSourceMetagenerationMatch`. A future runner must resolve them from validated raw metadata while preserving the decimal string exactly, never converting long generation values through JavaScript `Number`. The `requires` declarations describe the necessary presence/absence, raw media bytes, metadata subset and field relations before a subject is admissible. They are data declarations; this corpus alone does not implement durable response binding or complete state admission. Serializing the reference object directly into a query is invalid. Unexpected setup or post-state must suspend dependent work and preserve evidence; this corpus does not authorize fallback or cleanup.
`resolveDeclaredQuery({recipe,stepIndex,responses,bucket})` is a separate, transportless implementation of the metadata-field reference boundary. `responses` is a `Map` keyed by the prior step ID; each entry supplies the captured HTTP `status` and exact raw `bodyBase64`. Resolution accepts only a prior unselected GCS metadata GET for the target object or declared transfer source and configured bucket, a 200 GCS object resource with matching identity, and canonical positive decimal-string generation fields. It checks that the target request route and upload name select the declared object or transfer endpoints, and preserves strings beyond JavaScript's safe integer range. The returned query is a copy and does not grant send or cleanup authorization. The runner must still bind its durable raw evidence to the actual request, evaluate every `requires` state/media/metadata/relation prerequisite, and refuse dependent operations on uncertainty. The corpus keeps `typed-reference-resolution-and-preconditions` as an open integration obligation until that boundary is wired and verified.

`evaluatePresentRequires({recipe,stepIndex,responses,bucket})` separately checks the 63 declared `state:"present"` prerequisites against supplied raw records. It requires prior unique same-object unselected metadata and full-media GET declarations, status 200, bounded canonical raw bytes, matching object identity, exact media bytes, metadata subsets and string generation relations. Its result says only `MATCHED_SUPPLIED_RECORDS` with send and cleanup authorization false. All eight `state:"absent"` subjects are rejected because a response status alone cannot prove ownership and absence. A `Map` keyed by step ID does not establish that bytes came from the declared request, that they are fresh, or that the initial object state was owned; durable request/response binding and the complete state admission gate remain open. Firebase metadata shape is checked conservatively and needs real production evidence before integration.

`evaluateSupplied404Reads({recipe,stepIndex,responses,bucket})` classifies the four supplied 404 metadata/full-media reads for each of the eight zero-absent generation controls. It checks the frozen subject and prior same-object routes in both dialects, plus bounded canonical raw response bytes. Its `MATCHED_SUPPLIED_404_READS` result explicitly leaves send and cleanup authorization false. A 404 can also indicate a missing API route, and the supplied step-ID map has no authentic request binding, freshness or ownership proof. The existing `evaluatePresentRequires` absence rejection and the runtime state-admission obligation remain unchanged.

Selected-current-generation download includes metadata, complete media and ranged media. Each selection uses the observed generation after the initial range sequence and is followed by unselected metadata/media readback. Subsequent selections require the current generation still to match that first observation. Archived generations and bucket versioning changes remain outside the frozen scope.

The request parameters follow the official [GCS get API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/get), [insert API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/insert), [PATCH API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/patch), [update API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/update) and [delete API](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/delete). The pairing of generation with metageneration and the zero-generation controls follows the [precondition guide](https://docs.cloud.google.com/storage/docs/request-preconditions). No documented status is substituted for a production recording.

## Firebase resumable upload declaration

The Firebase resumable recipe owns separate new objects for completion, wrong-offset refusal and cancellation. All three `start` requests declare a 262147-byte upload with the headers and JSON metadata construction used by the Firebase Web SDK; this size is above the SDK resumable threshold. The opaque `X-Goog-Upload-URL` from that response is represented by a private typed reference. Subsequent `query`, `upload`, `upload, finalize` and conditional `cancel` requests contain no literal session URL or upload ID. The completion session sends a 256 KiB chunk, queries the received offset, sends a three-byte final chunk and reads the object through both APIs. A separate session probes an intentionally wrong offset, four absent-state readbacks and a follow-up status query after the attempt, including unexpected or uncertain responses. The final chunk is declared only after a status query reports 262144 received bytes; static declarations cannot prove that the server actually reported them.

When the wrong-offset session query reports active, regardless of received byte count, the declaration attempts cancellation, queries again and reads absent object state through both APIs. Zero received bytes remains a comparison target rather than an admission condition. A third session is independently started for an attempted cancellation, a status query and both-dialect absence readbacks. These observations do not by themselves prove terminal cancellation. All three sessions have conditional cancellation and status queries in cleanup if their terminal state remains unconfirmed; unresolved sessions remain a responsibility rather than being treated as cleaned up. A future runner must bind the session URL to the exact start response, validate its origin, path, bucket and object, retain it only in private evidence, and stop on uncertain status or cancellation. The currently declared 4xx expectation for the wrong offset is a comparison target, not a production observation. Neither upload nor cleanup is authorized by this recipe. Its fifty-one static entries are not a wire budget.

The request construction follows the [Firebase Web SDK resumable implementation](https://github.com/firebase/firebase-js-sdk/blob/main/packages/storage/src/implementation/requests.ts), its [upload task threshold](https://github.com/firebase/firebase-js-sdk/blob/main/packages/storage/src/task.ts) and [Firebase upload guidance](https://firebase.google.com/docs/storage/web/upload-files). The code reference describes SDK request construction; production response behavior still requires two recordings.

## GCS resumable upload declaration

The GCS resumable recipe owns one new object. A guarded `POST /upload/storage/v1/b/{bucket}/o` starts a session with `uploadType=resumable`, `ifGenerationMatch=0` and metadata. Three subsequent `PUT` entries refer to the initiation's opaque `Location` URI; no upload ID or session URL is embedded in the corpus. The first data chunk is exactly 256 KiB of binary bytes, the status probe has an empty body and `Content-Range: bytes */262147`, and the three-byte final chunk is declared only after a status response of 308 with an exact `Range: bytes=0-262143`. Both APIs then read metadata and full media. This adds fifteen static request entries; it is not a wire budget or send authorization.

The session URI is a bearer-capable secret and must stay in private evidence. The typed `sessionUriReference` records the expected HTTPS origin, upload path, bucket and object name. `evaluateSuppliedSessionLocation({recipe,response,bucket})` checks a supplied status-200 initiation response with one `Location` header, an empty captured body, the complete locally generated recipe for the supplied prefix, exact HTTPS GCS origin/path/name, and a bounded single opaque `upload_id`. It returns only a frozen digest and explicitly denies send and cleanup admission; it never returns the URI. This shape check does not bind the prefix to an authorized run or prove response provenance. The strict URI shape follows the documented JSON API example and may need revision after real production evidence.

`evaluateSuppliedExactStatusRange({recipe,response,bucket})` checks only a supplied status-probe response against the complete local recipe. It classifies one HTTP 308 with an empty body and exactly one `Range: bytes=0-262143` header, the sole static condition for the declared final chunk. Missing, partial or ambiguous progress remains unresolved. The frozen result grants neither send nor cleanup admission. It cannot prove that the status response came from the same session or followed the declared chunk request; a future runner must bind the raw requests and responses before advancing.

For a session whose completion is unconfirmed, cleanup first declares `DELETE` to the same private URI with `Content-Length: 0`. A successful JSON API cancellation has status 499; a following zero-length status `PUT` is declared to check for a 4xx response before object cleanup. These entries are conditional declarations, not a determination that a session is unfinished or that cancellation succeeded. Object deletion alone does not cancel a session.

No authentic request/header binding, runner-bound URI resolver, redirect policy, runtime progress evaluator, URI redaction in an actual transport, cancellation evaluator, or runtime continuation gate exists yet. A future runner must check the raw `Location` and status responses and stop on partial or uncertain progress rather than advancing to the declared final offset. It must also confirm cancellation or retain unresolved responsibility before considering cleanup complete. This recipe and its cleanup declarations remain non-sending, even when all static entries are present.

Request shapes and chunk constraints follow the [GCS resumable upload guide](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads) and [objects.insert](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/insert). The official guide warns that anyone holding the session URI can upload to the target bucket; the local declaration makes no observation of production behavior.

## Lean recorder

`run.mjs record-production <1|2>` records one of the two production recordings; each recording is its own run, admitted on its own, at least thirty minutes after the last line any lane wrote on the project. `run.mjs pins` prints the digests a packet pins (the runner's sources, the plan and corpus shapes, the fixed Rules source) and the commit.

A run refuses, before it writes or sends anything, unless: the environment is clean (no proxy, extra CA, `NODE_OPTIONS` or emulator host; Node 24.14.0); the owner ledger approves the packet and the review is a clean approval; the packet's pins equal the code that would run; the tree is clean and at the approved commit; the shared ledger shows no open run, no line inside the quiet interval and a request budget left; and the project lock is free. It then writes a `started` row, runs the local aggregate for one recording through the lean wire, and writes exactly one closing row (`recorded`, `stopped-clean`, or `needs-recovery`, which keeps the project lock). Rows use only events and outcomes other lanes already write (`ledger-rows.mjs`; `storage-object-ledger-compat.test.mjs` feeds them to every other runner's admission).

The sender and the recipe replays run in their local mode against placeholder loopback origins. The lean wire (`lean-wire.mjs`) is the only place a request becomes a real one. It maps each request through a closed route table for one bucket, one run prefix and one project to the real Storage, identity and token hosts; swaps the owner's access token (from `gcloud auth application-default print-access-token`, held in memory) and the Web API key in; hashes tokens, keys and the Authorization header before a capture is written; spaces writes to one object by a second; never follows a redirect and never retries; and stops on a capture failure or an oversize response. Captures are at the `fetch` level (status, headers, body), not raw socket bytes. A run records nothing for the emulator: the private record (`captures.jsonl`, `events.jsonl`, `meta.json`, mode 0600, in a new 0700 directory that git ignores) may hold response bodies with download tokens and a disposable user's ID token.

Exit codes: 0 recorded, 2 refused or failed, 3 stopped clean (nothing recorded), 4 needs recovery. There is no in-run recovery: a run that may have left objects stops, and recovery is a separate reviewed packet.
