# STORAGE-RULES observation declarations

This directory defines a finite, partial REST corpus for the frozen STORAGE-RULES closure inventory. All twenty-two behavior recipes now have static declarations, including three management programs. It contains no integrated production sender, credential loader, Rules publisher, admission path or recovery executor. Original closure statuses remain pending. Production status codes, bodies, header values and Rules decisions remain unobserved.

## Declared behavior

The current nineteen recipes cover individual method grants and aliases, v1/v2 list boundaries, anonymous and UID ownership predicates, standard/custom token claims, six token refusal/control states, proposed metadata fields, simple/multipart/resumable upload fields, stored resource fields and direct null/non-null controls, create/update selection for absent and present uploads, delete `request.resource` null/non-null controls, bounded `request.time` predicates, bucket/leaf captures, recursive wildcard depth, Firebase denial shapes, GCS/Admin boundary controls, refusal precedence controls, the Firebase download-token boundary, and three Storage Rules to Firestore access obligations. Object cases use distinct owned namespaces and literal Storage rulesets. Cross-service transitions are separate finite `firestorePrograms` because a document change cannot be represented as one object request. Read/write observations require raw responses and privileged metadata/media state checks.

Three additional management programs declare compile rejection, release switching, and no-release behavior. `pendingRecipes` is empty because every behavior recipe has an input declaration; none is verified. Shared Rules language evidence is still subject to the frozen S3 decision. The new token, state-transition, time, precedence, download-token, upload and Firestore programs are static inputs; production authentication refusal, operation selection, delete-resource values, server-time, refusal order, download-token behavior, finalization fields and cross-service decisions are still unobserved.

## Management programs and local smoke

`storage-service-compile` retains all 338 distinct literal Rules sources referenced by the object cases, Firestore programs and release-switch program, plus one deliberately invalid Storage expression. The static sequence proposes [projects:test](https://firebase.google.com/docs/reference/rules/rest/v1/projects/test) with inline `Source` and no test suite for each source, bounded by reads that require the bucket-specific release to remain unchanged. The API documents syntactic and semantic source issues without creating a ruleset. The valid sources require no error issue; the invalid source requires an error issue with a source position. This does not prove that a later Rulesets create would accept every source, so the four sources actually published by a future runner still require create and GET source-digest readback. These are production Rules API inputs, not observed compile results or an approved request budget. The [Rulesets REST resource](https://firebase.google.com/docs/reference/rules/rest/v1/projects.rulesets) documents create, get and delete, while the [Releases REST resource](https://firebase.google.com/docs/reference/rules/rest/v1/projects.releases) documents the separate live release reference.

`release-switch` uses two literal sources that allow only opposite objects under the owned prefix. It declares both decisions under source A and again under source B, with release readback and effective-decision settling between them. `no-release` requires both bucket-specific and bucketless Storage releases to be absent, seeds one owned object through the Admin boundary, observes a Firebase read refusal and Admin readback, then deletes only that object and reconfirms release absence. Both programs assume the planned post-STORAGE-OBJECT absent-release baseline; a changed actual baseline requires a revised program and packet. Their step orders are obligations, not executable per-call production requests. The management programs do not implement a production sender, settle loop, failure recovery, or the full HTTP ceiling.

`local-smoke.mjs` is a local fireemu regression check using `/internal/setRules` for activation and the fireemu control API for readback and clearing. It validates all 338 valid sources through local activation/readback, confirms invalid-source atomicity, exercises the two opposite local authorization decisions, and checks no-rules refusal with Admin access. Run it through `fireemu exec` with `conformance/storage-rules-local.fireemu.json` and a port-registry claim. These endpoints replace a local rules generation; they are not the production Firebase Rules release API. Its results do not establish production compile acceptance, release propagation, or compatibility.

`local-equivalence.mjs` replays all 331 object cases and five Firestore programs against each isolated source and the corresponding v1/v2 bundle in one disposable fireemu session. It checks initial absence, source readback before each subject, paired subject status and object readback, local cleanup absence, and local allow/deny controls across both Rules versions and cross-service access. The three-distinct-document control expects denial because [Storage Rules permit at most two Firestore document accesses per evaluation](https://firebase.google.com/docs/storage/security/rules-conditions). Its emulator-profile tokens and literal owner credential are local fixtures only; it does not verify production credentials, production Rules compilation, or compatibility. All listeners use OS-assigned loopback ports, with the optional hub and logging listeners disabled:

```sh
fireemu exec --config conformance/storage-rules-equivalence-local.fireemu.json --only storage,firestore --project fireemu-oracle-query --storage-port 0 --firestore-port 0 --http-port 0 --hub-port 0 --logging-port 0 -- node conformance/src/storage-rules/local-equivalence.mjs
```

`publication.mjs` derives one Rules source per Rules version from the 336 case and Firestore source bodies. It retains each exact match body, requires each case prefix to equal the owned run prefix plus its ID, rejects duplicate or nested prefixes and noncanonical match bodies, and enforces the source text limit. Its output is an input candidate for a later reviewed publisher. The pure structural check and a local activation of both generated variants do not prove all case decisions are equal under production Rules or that production accepts the aggregate source.

`manifest.mjs` assigns stable IDs to the 3,799 declared object and Firestore requests in one recording and binds the ordered rows to a SHA-256 digest. It validates the frozen corpus first and remains a partial, non-sending input: Rules publication, authentication, settle checks, recovery and the complete HTTP ceiling are separate work.

`request-counter.mjs` is a pure draft attempt counter for one recording. It requires a durable started callback before any counted request, checks every declared preflight ID before admission, and writes a terminal row when a preflight check fails. It reserves each attempt before dispatch, fixes normal traffic at no more than 4,648 attempts and protects 2,000 recovery attempts within the draft 6,648 ceiling. A subject transport exception enters recovery without retrying the uncertain request, and a journal callback failure blocks further traffic. After admission a run closes as `finished`, `needs-recovery`, `stopped-no-mutation` (still normal, no recovery request) or `recovered` (in recovery, at least one recovery request); the counter and the journal check those conditions on counts, while the controller must prove that no mutation was attempted or that every residual is absent before it asks for the last two. It does not decide whether an endpoint is allowed, perform a request, or prove cleanup and terminal success.

`full-manifest.mjs` expands the canonical corpus and support operations into 6,172 unique typed request declarations: 4,638 normal/preflight and 1,534 recovery, including 19 explicit preflight IDs accepted by the existing counter. It preserves case subject inputs and cross-service state predicates, adds conditional owner writes and cleanup, retains four source-specific restoration witnesses, reads each witness anonymously (every witness source allows all reads), gives each publication phase the previous phase's positive witness as its negative, and declares bounded list pages, Auth/cache operations and eight owned session recovery sequences. Dynamic Ruleset names, versions, credentials and session URLs remain runtime references requiring durable proof. The fourteen additional preflight routes follow the [Google OAuth discovery document](https://www.googleapis.com/discovery/v1/apis/oauth2/v2/rest), [project permissions API](https://docs.cloud.google.com/resource-manager/reference/rest/v3/projects/testIamPermissions) and [API Keys API](https://docs.cloud.google.com/api-keys/docs/reference/rest/v2/projects.locations.keys/get); session query and cancel send no credential, because the upload URL is the capability, and their shapes follow the [Firebase SDK](https://github.com/firebase/firebase-android-sdk/tree/master/firebase-storage/src/main/java/com/google/firebase/storage/network). Ruleset lists use the [documented maximum page size of 100](https://firebase.google.com/docs/reference/rules/rest/v1/projects.rulesets/list), and release updates use the [documented PATCH body](https://firebase.google.com/docs/reference/rules/rest/v1/projects.releases/patch). The result is `LOCAL_FULL_DRAFT_NO_SEND`, with `sendAuthorized: false` and `controllerReady: false`. Row order is an inventory, not an executable schedule. Private input provenance, response/ref validation, stateful ordering, durable capture, live admission and final pinned review remain required; no credentials are resolved and no HTTP is sent.

`predicates.mjs` closes the vocabulary of the free-text conditions on manifest rows. The 55 `requires` tokens, the seven required states and the two `when` conditions form frozen tables; each token names a category (guard, proof, input, check, budget or policy), the ledger or input facts it reads, and whether a false answer stops the run or skips the row. `full-manifest.mjs` refuses any row outside the tables, and its test pins the reviewed registry by digest. Three explicit guards replace the previously implicit conditional cleanup: an object delete, a Firestore document delete or a session cancel is skipped, at no request cost, when the latest readback or query shows nothing to remove. The expansion also names each declared row's origin from a closed (service, dialect) table; it changes no other request field, and a test pins the digests of `corpus.mjs` and `manifest.mjs` and of the rows' requests without their origin.

`runtime-refs.mjs` holds the values that exist only after an accepted response: object generations and metagenerations, Firestore update times, Ruleset names (with the paths derived from them) and list page tokens. `buildRefTables` derives from the manifest which rows may produce and which may consume each declared reference. A bind needs a declared reference, a producer row and verdict from that table, a value inside the kind's grammar (canonical decimals, an existing UTC date, a Ruleset name in the query project, a bounded page-token alphabet) and a proof write that finishes first; the proof carries a salted digest, never the value, and a failed proof write leaves the store uncertain for every later call. A value resolves only for a declared consumer; a page token resolves once, a generation from a non-deletable source cannot feed a delete, and a later attempt supersedes an earlier generation, metageneration or update time but not the reverse. Auth fixtures and OAuth bodies are outside this store. Session URLs and download tokens live here too, in memory only: they bind once from the response that produced them (pinned to the start or create-token step), resolve for every declared consumer, and reach a proof only as a salted digest.

`acceptance.mjs` maps each of the 6,172 declared rows to one closed acceptance kind (families and stages are a closed table; an unknown row has no kind) and classifies one complete raw response of a row into a verdict with digest-only facts. It knows what a response is, not whether a step needs it: the controller decides that. Implemented kinds are subject and comparison observations, settle reads (allowed only for the exact witness digest, denied only for the closed Firebase 403), GCS seed uploads, conditional deletes, and GCS metadata and media reads (present, absent for the closed 404, or unexpected). JSON is accepted only as a single `application/json` header with no charset or UTF-8, strict UTF-8, no BOM and no trailing bytes. Download tokens and other bearer values never reach a fact. Every kind without a reviewed schema (Rules API, Firestore, sessions, preflight routes, Auth and the credential cache) fails closed; `unimplementedKinds()` lists them.

`acceptance.mjs` is now split by service: `acceptance-core.mjs` holds the shared response reader and helpers, `acceptance-rules.mjs` the Rules API schemas (rulesets, releases, list pages, source tests), `acceptance-firestore.mjs` the document schemas, `acceptance-sessions.mjs` token creation and the resumable-session protocol, and `acceptance-preflight.mjs` the ten environment probes. Only Auth and the credential cache, which their own modules carry, have no schema here. A result may hand the caller a bearer value (a session URL, a download token, a key string, an owner identity) in a frozen, non-enumerable `secretFacts` that never serializes.

`target.mjs` turns a manifest row into the exact request the transport may send. Each request must match one closed route for its origin, method and path, must stay inside the owned bucket, prefix, documents and Rules resources, and every run-time value comes from the caller's resolver and is checked against its grammar again. Authorization is not added here; the digest binds method, URL, headers, body and credential under a salt, and `verify` recognizes only a target this builder issued, unchanged. The transport-facing `spec` is non-enumerable so it never serializes.

`redaction.mjs` removes bearer material from response bytes, response headers and free text: secret JSON fields, secret URL parameters and assignments, JWTs, API keys, OAuth tokens, bearer headers, private keys and session URLs. Bytes are read as Latin-1 so offsets stay exact; a span keeps the original offset, length and a salted digest, never the value.

`capture-journal.mjs` appends closed intent, response, facts, proof and note rows to a private run file and stores each redacted response body as a content-addressed blob that is synced, with its directory, before the row that names it. Every writer redacts or refuses bearer material, and a failed write leaves the journal uncertain. `storage-rules-run-directory.test.mjs` runs the counter, both journals, the reference store, the target builder and the classifier over responses full of canary secrets and sweeps every file under the run directory.

`resource-ledger.mjs` tracks the 344 owned objects: baseline absence, attempted writes (a mutation is never attempted twice, whatever ID carries it), the latest readback and the guards that read them. A create whose answer is unknown is never owned. Guards for anything else are returned as unresolved so no caller reads a `go` as more than it is. `settle.mjs` is the pure reducer for the wait after a publication or a release removal: a cycle matches only when every witness gives exactly its expected verdict, the wait settles after the required consecutive matching cycles and is exhausted at the cycle limit, and an unclassified answer never stands in for a denial. `dispatch-gate.mjs` is the only object that holds the real transport: a request leaves after its intent and its reservation are durable, once per reservation, for the captured target and in the mode its ID belongs to; credential headers are added at that last step only, and a capture failure after a send poisons the gate. The modules that carry their own request bodies and credentials (`credential-cache.mjs`, `credential-session.mjs`) send through `gate.delegated`: a counter facade (`send`, `sendPreflight`, `snapshot`, `enterRecovery`) that adds the admission check, the capture-journal health check and a durable intent before the counter reserves, one request at a time, and an `http` function that reaches the real transport only inside an armed, counted attempt and only once per attempt. Those modules capture no response themselves; they record digests. The controller turns anything a delegate throws into a stop, keeping `admission refused` when the gate saw the refusal. The gate also requires an `admission` (`admission.mjs`): it proves the live approval before `start` and before every request, reads included, and a refusal stops the request before its intent is written. `admission.mjs` reads the owner ledger again at each check, validates it through `approval.mjs` against the packet and review copied at creation, and asks the project locks (`lease.verifyHeld()`) to prove they are still this run's; any failure refuses, and a refusal is permanent, so a ledger that looks valid again cannot resume the run. The controller reports it as the stop reason `admission refused`.

`schedule.mjs` fixes the order in which a recording may run and proves that every non-recovery row is covered exactly once (the manifest's own row order is only an inventory). Preflight runs in a reviewed order with the two credential IDs first; the four witnesses are seeded and read back before any release is written; compile checks and Ruleset creation precede publication; each publication is a before-read, the write, an after-read and a settle block before its cases; credentials are prepared before the first user-token subject and the foreign-project fixture wraps only its own subject; the restoration follows the release removal and precedes any witness deletion; all control readbacks precede any control delete; and the final list pages, the owned-prefix check and the credential cleanup come last. The manifest names which cases and Firestore programs each published bundle serves.

`run-ledger.mjs` holds the state of everything that is not an owned object (Firestore documents, resumable sessions, the four Rulesets, the bucket release, the witness and control readbacks, the settle results and the run-level flags) and answers the guards that read it before a request and the post-response checks that read the row's own response. A token it does not own is returned as unresolved. `enforcement.mjs` names, for every one of the registry's tokens, who answers it (the object ledger, the run ledger, a post-response check, admission from the approved private inputs, a credential delegate, the reference store, the schedule, or the acceptance schema), and its test pins each answer to the code that gives it. A cancel answer alone does not prove a resumable session finished (session policy), so each session is asked again right after its cancel by a normal-path `session-verify` query, and only a session verified `final` counts as cleaned.

`controller.mjs` runs the schedule. Each row goes through the guards of the ledgers, the run-time references it needs, its exact target, the ledgers' record of the intent, one send through the gate, the classification, the durable facts, the ledgers' record of the outcome, the post-response checks, the expected verdict and the references the response produced; any surprise stops the run at once. It never resends, never recovers by itself and reports what a separate recovery would have to clean. A stop before any write closes the counter as `stopped-no-mutation`; a preflight answer that is not the admitted one closes it as `preflight-failed`; after a write the counter stays open for recovery. `storage-rules-simulator.mjs` (tests only) stands in for production and lets a whole recording run: the controller test drives it end to end, injects failures (a foreign entry release, a dirty namespace, a rejected seed, a lost connection, a publication that never settles, a wrong compile verdict, a capture failure) and, with `STORAGE_RULES_SLOW_TESTS=1`, runs the real journals and sweeps the run directory for every bearer value the simulator handed out. The controller does not yet drive the credential modules (`credential-cache`, `credential-session`) or a recovery run: those steps are delegates, and the recovery rows have no executor. `controller.recover()` finishes what a stopped run left behind, through the same gate, ledgers and checks and only with the declared `recovery/` rows: `buildRecoverySchedule` (in `schedule.mjs`) orders them as release, restore settle, owner media, sessions, objects, documents, accounts (a delegated group), Rulesets, the final list and the owned-prefix check, and each group carries the ledger fact that enables it (`run.recoveryEnabled`: a release write was attempted and not yet deleted, a witness exists and the four owner readbacks are not done, a session was started, a Ruleset create was attempted). A disabled group is skipped and noted; a failed guard, an unexpected answer or an admission refusal stops recovery and closes the counter as `needs-recovery`. It closes as `recovered` only when the owned-prefix check, which sits behind every cleanup guard, was sent and accepted. Recovery runs once, never resends a delete whatever ID carries it and is refused when the counter is not open.

`approval.mjs` checks a local snapshot of the owner-decision ledger against a packet and a clean APPROVE review. It accepts an exact owner approval or a coordinator approval referring to one preceding approved envelope. An envelope may be approved by the owner or by the exact delegated coordinator actor with the required delegation reference, a unique approved owner delegation row, and a reservation of at most US$10. Additional rows for the delegation subject are refused regardless of date, so a later revocation cannot be ignored or revived by another approval. Envelope approvals require the same projects, sufficient request and reservation bounds, write/IAM/retry summaries, and an explicit in-envelope review. All five packet/source/runner/manifest/fixture pins must match. A revoked packet identity cannot be reused, and a newer concrete decision cannot fall back to an older matching SHA. `ledger-revocation.mjs` scans every ledger line, whatever its column count or spelling, after NFKC normalization and lower-casing on both sides: a line containing `revoked` that names the lane subject, the lane as a whole, the packet SHA, the source commit (full or at least eight digits) or the envelope ID stops the approval, and one that names the coordinator delegation makes every coordinator-written row unusable. A delegated envelope needs both the send delegation row and the envelope delegation row. Any line that contains a revocation word (`revoked`, `revocation`, `revoke`, `取消`, `取り消`, `撤回`, `withdrawn`, `withdraw`, on the NFKC lower-cased line) and names the lane anywhere (the task ID in the whole normalized line, or in the subject column once parenthetical qualifiers are stripped) stops the approval, unless it is a consumed revocation of an earlier version: it names no pin of this packet (no pin in full or by an 8-character prefix, no envelope ID), it carries at least one key-bound field (`packetSha256=`, `sourceCommit=`, `runnerSha256=`, `manifestSha256=`, `fixtureSchemaSha256=`, `envelopeId=`), every such field equals the same field of an earlier approval line of this lane in the same ledger, and no other digest, commit or envelope ID appears in it. The retry flow (version 1 approved, its consumed revocation written naming only the fields that differ, version 2 approved) therefore needs no allowlist entry, while a revocation that cites a review digest, a prefix, a free-text digest or another lane's line still stops. A historical line that mentions the lane and `revoked` without revoking anything is ignored only through an allowlist entry that pins the exact raw line by SHA-256 and states the reason. The two-recording draft limits are 12,344 requests (6,172 declared IDs per recording; the 6,648 counter ceiling is only the hard cap) and a US$2 reservation. Its frozen receipt has `sendAuthorized: false`: actual file hashes, coordinator go, live ledger admission, credentials and cleanup are separate sender obligations.

`fixture-proof.mjs` verifies a supplied immutable ID token with Node's RSA implementation, fixed RS256 padding and a bounded public-key snapshot. It checks the fixture's project, captured UID, run-owned email, password provider, absence of a tenant, typed custom claims, token time and key-cache expiry. A revoked fixture additionally binds an older token to a later `validSince` readback; it does not predict Storage's response. The frozen proof contains a salted token digest and selected claims, never token bytes, and remains `sendAuthorized: false`. The sender must separately prove that public keys came from Firebase's documented certificate endpoint, derive cache expiry from its `Cache-Control`, and bind actual issuance, lookup and cleanup receipts. This pure module acquires neither keys nor credentials. The checks follow [Firebase's ID token verification requirements](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

`auth-wire.mjs` connects the credential session's 29 fixed Auth steps and its delete/absence recovery steps to one injected HTTP attempt each. It checks the exact operation, project, origin, path, method, credential class and closed body schema, including the run's query UID/email and typed claims. Client calls use the corresponding API key without reading owner OAuth; Admin calls use a synchronous cached credential whose expiry exceeds the 30-second transport timeout. Plain input data is copied before callbacks, and bounded native response bytes must decode to finite UTF-8 JSON objects. Failures expose fixed errors without redirects, retries or implicit credential refresh. The injected hooks are trusted dependencies: owner refresh, key provenance, durable capture, foreign UID ownership, counted admission and production authority remain obligations of the session and final sender. Admin account routes follow the [Firebase Admin SDK](https://github.com/firebase/firebase-admin-node/blob/master/src/auth/auth-api-request.ts); client routes follow [Identity Platform password sign-in](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/signInWithPassword) and [sign-up](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/signUp).

`credential-cache.mjs` explicitly reserves owner OAuth refresh and Firebase signing-key fetches through the same request counter and injected HTTP transport. It permits 19 fixed phase-specific IDs, validates minimal authorized-user ADC data, and exposes synchronous cached getters that perform no HTTP. Expiry begins at dispatch, subtracts certificate cache Age, and is checked before and after durable proof recording. Expired or ambiguous caches, clock rollback, weak/non-RSA keys and journal failures stop use. Proofs contain source URLs, times and salted token or public-key digests, and remain `sendAuthorized: false`. Actual ADC provenance, owner identity/permissions, TLS dependency selection, redacted capture and complete sender admission still require final integration. Endpoint behavior follows [Google's OAuth refresh guide](https://developers.google.com/identity/protocols/oauth2/web-server#offline) and [Firebase's signing-key guidance](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

`reservation-journal.mjs` persists closed counter events through explicitly supplied Node filesystem methods. It creates a fresh mode-600 append file in a caller-controlled mode-700 run directory, binds its source and manifest metadata, and syncs each complete reservation before returning to the counter. Short writes are completed; file identity, mode, link count and size changes or sync failures leave the journal uncertain and block further events. Closing releases its handles while preserving the file. Counter receipts remain `sendAuthorized: false`. This journal covers request accounting; exact target capture, response redaction, resource ownership, shared-ledger admission and cleanup proof remain final-sender obligations. Directory ancestors and injected filesystem methods are trusted boundaries. File operations follow the [Node filesystem API](https://nodejs.org/api/fs.html).

`credential-session.mjs` connects the reviewed fixture lifecycle to a supplied request counter and transport. Its normal path uses 24 query and five idp Auth requests, separates user-a/plain snapshots on the same UID, verifies claim and revocation readbacks, and deletes the foreign account immediately after its subject. It journals confirmed creations and safe token proofs before subject access and requires account absence readbacks for cleanup. Counter state and token/key freshness are checked again after proof persistence and before subject access. Journal failure blocks further requests; an uncertain creation prevents a recovered outcome, and an uncertain delete receives only a later absence lookup rather than an automatic resend. Recovery is limited to confirmed owned accounts and uses the protected reserve when normal requests are exhausted. This module supplies no network transport, credential loader, file journal, production admission or send permission; token access is private runtime input to the future transport.

`http-transport.mjs` wraps one explicitly supplied Node `https.request` attempt. It fixes TLS certificate verification, prevents connection reuse, follows no redirect and performs no retry, bounds request/header/response bytes, and aborts both streams on a 30-second total deadline or incomplete response. It retains raw response bytes and header order, including duplicate headers, for private collection. Fixed errors omit URLs, credentials and lower-level messages. The allowed HTTPS hosts and exact Firebase certificate URL are transport boundaries only: the caller must separately bind each route to the reviewed project, manifest ID, credential, counter, current approval and exclusive window. No request implementation is selected automatically and no production entry point is enabled. The connection and raw-capture behavior follows the [Node HTTP API](https://nodejs.org/api/http.html).

`project-locks.mjs` acquires the reviewed project set in sorted order with exclusive mode-600 files in a mode-700 directory. It checks the legacy shared lock before and after acquisition, rolls back only owned partial acquisitions, verifies inode and body before release, and retains locks after an outbound failure. A sent callback must explicitly confirm closure after proving its terminal cleanup; unresolved or pending dispatch cannot release the locks. `lease.verifyHeld()` re-proves every owned lock (same file, same body, no legacy lock) without releasing it. This module is not yet connected to a production sender. Tests use disposable local directories, not the real sandbox locks.

`entry.mjs` is the one entry point a recording starts from. It resolves the main repository checkout (the nearest ancestor whose `.git` is a directory, so a linked worktree resolves to the checkout that owns it) and pins four paths under it: the owner ledger `docs.local/instructions/owner-decisions.md`, the lock directory `docs.local/runs/sandbox-locks`, the usage ledger `docs.local/runs/storage-rules-recording-usage.jsonl` and a fresh mode-700 run directory `docs.local/runs/storage-rules-<runId>` that must not exist yet. The options are a closed record (`inputsPath`, `closure`, `runId`, `sourceCommit`, `packet`, `review`); a caller cannot name a ledger, lock, usage or run path, a transport or a clock, and the exported `withStorageRulesRecording` builds the single-attempt HTTPS transport over `node:https` and the system clock itself. The owner ledger is read fresh for every admission as a regular file of this user that nobody else can write, without following a link, and the runs and lock directories must be private directories of this user. `bindStorageRulesEntry` takes a checkout root, a request function and a clock so tests can point the same code at a scratch checkout and a stub wire.

Five cross-service programs use only `fireemu-oracle-query/(default)/STORAGE-RULES/<run>-...` symbolic Firestore documents. The `get` program reads one captured document ID through a fully qualified Rules path after the same owned document is created with `allowed: true`, changed to false and deleted; it probes three fresh owned objects so a prior accepted upload cannot turn a later create into an update. The `exists` program reads a captured document ID against one seeded object before and after verified document deletion. Three budget programs evaluate two distinct documents, a third distinct document and an A-B-A repeat, with all referenced documents present to avoid an earlier missing-document short circuit. Each step declares a relative REST path, raw capture and the required document or object readback. Firestore updates and deletes carry typed `updateTime` references. Object cleanup carries a typed current generation and the originating own upload receipt; document cleanup requires the current update time to match this run's own write history. The program data does not resolve those references or send requests. A future runner must verify the bucket belongs to the same project, scoped service-agent IAM, exclusive Firestore and Storage windows, the original Rules release and cleanup ownership before doing any operation.

The upload matrix declares twenty-four cases: simple, multipart and resumable finalization crossed with `request.resource` size, contentType, name and custom `metadata.owner`, each with a matching and mismatching predicate. Every subject targets a new owned object with four received bytes and GCS owner metadata/media reads before and after. The simple upload has no `owner` custom metadata, so its pair checks key membership with `in`; a missing-member access would deny both branches. Multipart supplies exact `multipart/related` bytes with a fixed boundary and metadata part. Resumable initiation supplies metadata separately, then finalization supplies the bytes to a typed private reference to the initiation response's `X-Goog-Upload-URL`; the reference has no literal URL or upload ID. Its `path: null` means a future sender must validate and resolve the actual session URL before finalization or conditional cancellation. Cancellation is declared for an active or uncertain owned session, before object cleanup. A successful local parse/lint only checks local syntax; it does not establish the received resource values, URI provenance, status, or accepted/refused persistence in production. A future sender must not infer the finalization state from initiation metadata or send through the unresolved reference.

The token refusal cases send the same media GET against present, owned objects under a `request.auth != null` rule with missing, malformed, foreign-project, revoked and valid same-project credential references. They specify no expected status or Rules decision. The validator compares the entire declared data shape, including non-enumerable and symbol fields, and rejects extra secret or result fields. The malformed bearer value and all real tokens are prepared outside this corpus and kept private. An executor must verify the different-project origin, revocation after token issuance, and the valid control's same-project identity from independent fixture evidence. It must record the raw response and privileged before/after object state without storing token bytes in this declaration. An authentic expired token is an explicit unobserved S7 scope limit because waiting for it would hold the shared recording lock for about 130 minutes across two recordings. A valid token control does not prove that production checks revocation at this endpoint; that boundary remains an observation.

The sixteen precedence cases cross initially absent/present objects, Firebase/GCS JSON, valid/malformed credential references, and valid/malformed JSON bodies on metadata PATCH under an owned deny rule. The malformed body is the single byte `{`, transmitted as raw bytes with `Content-Type: application/json`; the valid body is `{}`. Eight more controls cross both object states, both dialects and both body states with a valid credential under an allow-write rule. Firebase uses the existing same-project user and malformed Firebase bearer references; GCS uses the owner OAuth reference and a separate malformed OAuth bearer reference. Actual header bytes are prepared outside this corpus. Every case retains privileged object readback before and after the subject PATCH. A future recording must establish that the malformed body is rejected as invalid JSON with a valid credential, that the valid-body controls reach the object operation, and that the malformed credentials are actually refused. The matrix does not predict which refusal wins. GCS JSON bypasses Storage Rules, so its rows measure the credential, validation and existence boundary only. Production behavior remains unobserved.

The download-token case uses one present owned object and a deny rule. It seeds the object with GCS owner requests, reads its token metadata, then declares an owner-only Firebase `create_token` request. The two anonymous Firebase media GETs use the same object and route; the first has no token, and the second carries a typed private reference to exactly one token newly appearing between the pre-create metadata and the create response. No token value or predicted response appears here. The future runner must verify the owner OAuth identity, the token-creation response's provenance and exact one-token difference, and the same object's metadata readback before resolving the reference. If token creation or resolution fails, it must not send the token-bearing GET. The local adapter's owner-only endpoint does not establish that production accepts an OAuth owner at this Firebase route. A token in a URL is secret: future raw URL logs and reports must redact it while retaining a private digest and provenance. This declaration supplies no resolver or send authority.

The four time cases use a fixed half-open 2000-01-01 to 2100-01-01 UTC window. One ruleset grants only an in-window request; another grants only an out-of-window request. Reads start with a present object and uploads with an absent object, with privileged state readbacks in both directions. A future recording must supply a trustworthy bounded interval for server evaluation time. If that interval is missing or overlaps either threshold, the outcome remains indeterminate; a local clock timestamp or HTTP status alone does not establish the predicate's intended direction. These fixed dates make the declaration reproducible, not a test of a near-boundary transition.

## Fixtures and protocol contract

Call `buildCorpus` with a plain bucket name, a fresh `STORAGE-RULES/<run>/` prefix and two distinct planned Firebase user IDs. Credential fields are symbolic references. `admin` requires an actual owner OAuth token and verified IAM capability; it never means the emulator-only literal `owner`. The owner excluded a valid IAM-denied OAuth principal because its preparation requires an out-of-scope IAM change. Seed, readback and cleanup still use privileged `admin`. User fixtures require real same-project ID tokens whose decoded and verified claims match the declaration. The `user-plain` token is a separate immutable snapshot with custom claims absent; minting and verifying these fixtures are future preparation work, not operations implemented here.

A case declares initial absence checks, an optional GCS seed and metadata update, a before-state readback, one subject request, an after-state readback, and bounded cleanup requests. A future executor must establish initial absence and ownership before any cleanup. Any unsuccessful or uncertain prerequisite prevents the subject operation. In particular, a rejected seed or unreadable baseline is not the declared initial state. GCS readbacks retain the complete body and headers, so bytes, generation, metageneration and metadata changes can be compared after writes and refusals.

List requests use the case's prefix and a finite result limit. Object paths encode the entire name as one segment; query values remain structured for later encoding. Raw response capture is mandatory. No normalizer or invented expected production response is provided. The source templates are test inputs; their acceptance by the local parser or remote compiler must be recorded separately.

## Release and budget prerequisites

Recording requires a reviewed exclusive Storage window after STORAGE-OBJECT, the actual effective release baseline saved privately, verified principal fixtures, an explicit compile/publish/settle procedure for each source, and restoration of the baseline release state with an effective-decision readback. The declared per-case ruleset is not automatically published by this module. A fresh ruleset may deliberately deny the subject request, so a future settle procedure needs independent evidence rather than treating a subject denial as proof of successful publication. If the baseline is absence, restoration requires absence readbacks rather than recreating STORAGE-OBJECT's removed rule.

`validateCorpus` counts declared Storage object and Firestore document API operations separately per recording, including conditional cleanup entries. Authentication, IAM, Rules source testing/publication/settling/restoration, retries, failure recovery, and a second recording are not included in those numbers. The management program declarations do not add an approved Rules request count. Later packets must partition and budget the full bounded procedure, including each of the 338 valid source tests, the invalid source test, and every release readback. This declaration grants no new production permission and cannot release the shared lock or close the parent.

## Sources

The [Storage Rules syntax guide](https://firebase.google.com/docs/storage/security/core-syntax) motivates isolated method/version/path controls. The [conditions guide](https://firebase.google.com/docs/storage/security/rules-conditions) motivates auth and existing/proposed resource inputs. The repository's `storage-probe/programs.mjs` and Rules files supply REST shape examples; their emulator credentials, response normalization, fixed paths and session runner are not reused. These references define test inputs and obligations, not recorded Firebase outcomes.

`delegates.mjs` (`createRunnerDelegates`) connects the controller's delegated steps to the modules that carry their own requests, all through `gate.delegated`: `preflight-cache` and `credential-cache` (the first normal refresh of each kind) run the counted credential cache; `prepare-query`, `cleanup-query` and `recover-accounts` run the fixture session over the Auth wire; `foreign-signup` and `foreign-cleanup` hold the foreign account open around the declared foreign row (the fixture session's subject is a promise the cleanup step resolves), and recovery abandons an open fixture so the session's own owned cleanup deletes the account. It also gives the gate its credential provider: anonymous sends nothing, `admin` sends the cached owner bearer with `x-goog-user-project` set to the request's project, the user principals send the pinned scheme `Authorization: Firebase <token>` (what the pinned web Storage SDK sends: `@firebase/storage` 0.14.5, `dist/index.esm.js:816`) with the fixture session's token, and the two malformed credentials send the values the runner supplies. `credentials.ensure` refreshes the owner token through the next declared refresh ID (`auth-shared/owner-token/2..8`, or `recovery/auth-shared/owner-token/1..8`) when fewer than five minutes remain; `credentials.fresh` is true only while the token it needs is still valid with a margin. Prepared targets carry the project the request is billed to (one of the two sandbox projects that agrees with the project the path names; a declared case with none is a query-project request) and the target digest binds it; the gate refuses any `x-goog-user-project` that differs from it, and a row cannot set that header itself; the Auth wire sends the same header on owner-credential requests.

The capture journal also takes the credential evidence as closed events: `credential-proof` (the cache's and the session's digest-only proofs, a plain record whose `status` is upper-case and whose `sendAuthorized` is false), `ownership` (account, project, uid, run prefix, a salted digest of the address, the creating request) and `cleanup` (account, project, uid, `absent: true`, the absence request). Each goes through the same redaction, and the delegates turn the session's receipts into these shapes so no raw address is written.

`private-inputs.mjs` loads the explicitly named private packet of expected values (`loadPrivateInputs`): a regular file of mode 0600 owned by this user with one link and no duplicate JSON keys, at most 64 KiB, parsed as a closed data record (no getters, proxies or extra fields) with the owner's address and subject as digests, both projects' numbers, key IDs, key UIDs and API-key restrictions, the bucket's location, uniform-access flag and policy digest, the database's location and type, and the query project's policy digest. Its API keys are only under a non-enumerable `secrets` property, so serialising or listing the record never shows them; the file's SHA-256 and size are kept as `provenance`. Every failure is the same error and echoes nothing. `readAdcFile` reads the ADC file the packet names (never searched for) and keeps the four fields the credential cache takes, and `generateRunSecrets` makes the run's salt, the four fixture passwords and the two deliberately malformed credentials from an injectable random source. `preflight-judge.mjs` (`createPreflightJudge`) compares each preflight probe's facts with that packet (identity and subject digests, project ID, number and state, key UID, restrictions and key string, permissions all granted, the bucket's project, location and access mode, the policy digests, the database's location and type) and accepts only when all of them match; the Rulesets-list and release entry reads are judged by their own verdicts. `locked-run.mjs` (`withLockedAdmission`) requires the lock set to be exactly the packet's (both projects, the task, the packet name and the source commit), makes every request's admission also prove the locks are still this run's (`lease.verifyHeld`), sends the gate's transport through the lease (`leaseTransport`) and releases the locks only when the caller confirms a finished or recovered result (`confirmCleanClose`); a stopped run, a transport failure or an unrecovered stop keeps them.

Header capture is an allowlist. `redaction.mjs` keeps the value of a header only when it is on the public list (content and caching headers, the `x-goog-*` object and upload-progress headers, and the like, as in the STORAGE-OBJECT lane's capture policy), still passed through the text patterns; every other header, including `x-guploader-uploadid`, `x-goog-upload-control-url`, `location` and `x-firebase-storage-download-tokens`, is stored as `<redacted:header:SHA-256>` with a salted digest. The simulator answers every session request with `X-GUploader-UploadID` equal to the session ID, and the run-directory canary test carries that header, `Location`, the control URL and the download-token header.

The real transport (`http-transport.mjs`) reaches the owner's userinfo read, the two projects' Resource Manager reads and IAM calls, and the two API keys' metadata and key strings only through exact (method, path) routes with no query; the other origins keep their origin-level allowance. `transport.validate(spec)` is the transport's own input check with nothing sent. The dispatch gate calls it before a target is admitted, written or counted, so a target the transport would refuse is "request not sent" and costs nothing (no counter movement); an input refusal that still reaches `send` carries `notSent` and is reported as not sent rather than as an uncertain outcome. A test prepares every counted row through the target builder and passes it through the real transport's validation.

The two-recording budget is enforced in code. An approval covers `RECORDINGS_PER_APPROVAL` (2) recordings. The admission takes the run's ID and a usage record (`recording-usage.mjs`, a private JSON-lines file with one durable line per started run of a packet SHA, closed in shape and refused whole on any malformed line); the gate's `start` calls `admission.begin()`, which is the same proof as a check followed by reading the usage record, refusing a run that is already marked or a third recording, marking the run started and reading the marker back before the counter starts. A refusal is permanent. `withLockedAdmission` takes the run ID and usage record too.

The target builder also refuses what the reviewed manifest never carries: a row header outside the four the manifest uses (`content-type` and the three `x-goog-upload-*`), a release write whose body does not name exactly this run's release with the Ruleset taken from a `ruleset-name` reference (POST body `{name, rulesetName}`, PATCH body `{release: {name, rulesetName}, updateMask: "rulesetName"}`), a Ruleset read or delete without the bound `ruleset-path` reference, and a numeric project path (or API key path) that does not carry the project number and key ID the run was built for, for the project the request is billed to.

The delegated seam is bound as tightly as the gate's own send: its entry points work only in their own mode (`sendPreflight` in preflight, `send` outside it), a request ID's prefix must agree with the phase (`preflight/` in preflight, `recovery/` in recovery, neither in the normal phase), and the exact request is bound durably before it leaves: `delegated.http` validates it with the transport, has the capture journal record it as a `delegated-target` event (the method, the URL with its `key` parameter redacted, the headers without the credential, a salted HMAC of the body and a salted HMAC over that record, recomputable from the row and the run's salt) and only then sends. The fixture session cleans up a foreign account that fails in recovery with the `recovery/auth/...` IDs.

A revocation that names no lane at all (the whole sandbox program, an unscoped "all") also stops this lane when it was written after this packet's decision line; one written before it was superseded, one that names another lane (`FS-...`, `AUTH-...`, `FUNCTIONS-...`, `STORAGE-<other>`, `HOSTING-...`, `FIRESTORE-...`) is that lane's, and the delegation rows follow their own, narrower word set (their prose uses 中止, 無効 and 取り下げ). The revocation words also include `rescind`, `中止`, `無効` and `取り下げ` for the lane and global rules. Only the lane's approval and envelope lines (`decision=APPROVE`, or an envelope row) feed the earlier pins a consumed revocation may cite.
