# Firestore and Storage Rules runtime repairs

The Rules evaluator now resolves user-defined function calls in the lexical scope where each function is declared. A function called from a nested `match` therefore does not accidentally bind to a same-named function declared at the call site. Firestore and Storage evaluations share this resolver and have dedicated regressions in `crates/fireemu-core-rules/tests/eval.rs`.

Rules activation also rejects every static linter diagnostic whose level is `Error`. The previous active generation remains published when a parseable candidate exceeds a source or structural limit. The activation regression is in `crates/fireemu-core-rules/tests/activation.rs`.

Rules activation now validates the declared version and recursive-wildcard structure before publication. Unknown versions, more than one recursive wildcard in a match, and non-terminal recursive wildcards under rules_version 1 are rejected without replacing the active generation.

The file supervisor reconciles the disk contents observed at startup with the active generation and checks a content signature in addition to file metadata. This catches a change that occurs before the supervisor starts and replacements that preserve size and modification time while retaining the last-known-good behavior for invalid candidates.

These are local runtime repairs. They do not claim production Rules parity or production compiler/watch behavior.

User-defined functions now restore the binding values captured at their declaration match as well as the declaration's function namespace. A caller's parameter or nested match capture cannot shadow a callee's lexical capture. The evaluator also visits recursive-wildcard path splits incrementally and charges a separate bounded matcher-work budget; it fails closed with an explicit evaluator budget reason instead of allocating every split up front. These local safety boundaries are not production limit claims.

Function declarations in one lexical scope now share one immutable function environment. A function call switches to that shared declaration environment and returns to the caller without cloning the declaration list, removing the per-request quadratic reference table while preserving lexical name resolution. The local regression asserts pointer sharing across a generated declaration set; production memory and performance parity remain unobserved.

Once an applicable allow has succeeded, later match-path exploration cannot turn that decision into a denial solely because the independent `FIREEMU-RULES-MATCH-WORK` budget is exhausted. The evaluator still propagates expression, call-depth, unsupported-operation and other budget failures, and it remains fail-closed when no allow has succeeded. Firestore and Storage regressions cover a successful allow followed by hundreds of non-matching recursive-wildcard matches; this is local evaluator evidence and does not claim a production compiler limit.

Before bounded match-path evaluation, the evaluator now applies a matcher-aligned reachability check. Literal, capture and recursive-wildcard transitions are evaluated against the requested segments, so structurally impossible sibling patterns are discarded without consuming the shared match-work budget. A valid allow remains reachable when it follows those siblings, while a request with no successful allow still fails closed. Firestore and Storage regressions cover 750 impossible recursive-wildcard siblings with the allow rule at the end; production matcher ordering and limit parity remain unobserved.

The evaluator now treats declaration metadata as required at call time: missing function scope or capture metadata is an unsupported evaluation that fails closed instead of falling back to the caller's environment. Declaration-level capture snapshots are shared through request-local reference-counted tables, so functions in one match do not each retain a duplicate static capture table. The dynamic caller-parameter and `let` regressions, nested declaration scopes, Firestore and Storage paths, and metadata-sharing checks pass on commit `a8a1f155`; production Rules parity remains unobserved.

Query proof abstraction now retains a parent-level `!=` / `not-in` exclusion when a child field also contributes a partial map constraint. The evaluator keeps the nested range and exclusion together, proves a concrete map is unequal when a required constrained key is absent or differs, and otherwise remains conservative. Firestore gRPC regressions cover both filter orders, parent and child rule conditions, positive and negative bounds, and a production-shaped composite index; production query-proof parity remains unobserved.

The follow-up repair at `33c78650` keeps a parent exclusion when a nested exclusion is added (including parent-first `FieldPath` ordering) and accounts for excluded values inside `RangeExcluding` when proving that a nested map differs from a concrete candidate. Source-level abstraction and evaluator regressions cover both cases, while the existing gRPC query-proof regression continues to exercise the real authorization path. Quint evidence for the affected Rules models was regenerated with the repository generator. These are local proofs only; saved production receipts and their original comparisons remain unchanged.

Query proof equality is now kept separate from concrete Rules equality. When a partial map is compared with a concrete Rules literal while proving a query constraint, integer and floating-point representations are treated as equivalent recursively inside arrays, maps and sets. This prevents representation-only differences from proving that every query result differs from a Rules literal; concrete Rules evaluation still uses its existing equality semantics. Core regressions cover nested list and map values plus a genuine nested difference, and the real gRPC authorization path covers a stored double array queried with an integer array. This closes a local query-proof soundness gap only; production Rules/query parity remains unobserved.
## Current query-proof transitive closure (`89ff069a`)

The follow-up query-proof closure at `89ff069a` preserves that conservative equality through declaration-scoped user functions, `let` aliases, list and set membership helpers, and transformations such as `toSet`, `removeAll`, union, intersection and difference. When the transformation cannot prove a result safely, the evaluator remains unknown and fails closed. Concrete Rules evaluation is unchanged.

## Numeric query-derived access guards (`1a944cf1`)

Query proofs now fail closed for representation-sensitive numeric access. Numeric query-derived indices, slice bounds and `path.bind()` values return `Unknown` before indexing, slicing or path interpolation. Provenance is preserved through direct expressions and declaration-scoped function/`let` aliases. Concrete Rules behavior and constant access remain unchanged. Core and real gRPC regressions cover integer query representatives against floating-point stored values, valid controls, owner stream completion, and denied user direct/query access.

`RegexAuthorization`, `RegexEvaluationCache` and `RulesetActivation` Quint evidence was regenerated with the official repository generator and validated. Workspace nextest passed 2,410 tests with 81 documented skips; workspace Clippy, rustfmt and diff checks passed. Independent Rules review and Security Specialist review found no blocker. These are local evaluator and evidence checks; production Rules/query parity remains unobserved.

## Current query-provenance sink closure (`8f456536`)

The change preserves the earlier conservative handling of query-derived arithmetic, direct comparisons, type checks, paths and aliases.
