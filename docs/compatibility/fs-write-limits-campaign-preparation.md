# Firestore write limits campaign preparation

`FS-DATA-WRITE-LIMITS-02` is an independent, owned-data campaign for the `FS-DATA-WRITE` parent. It covers four minimal cases: an accepted document-byte boundary, an immediately oversized document, an accepted nested boundary, and an immediately oversized nested document. The negative cases require typed refusal, typed absence readback, and unchanged accepted controls, so a transport status alone cannot complete the campaign.

The campaign uses a fresh nonce below `oracle/{freshNonce}/limits-02/` and does not mutate Rules, indexes, databases or shared settings. Its locks are a write lock for that owned document prefix and read locks for the default database indexes and ruleset. It can run beside unrelated campaigns when the nonce and resource lock checks pass. The original v1 proposal reserved 24 requests, 180 seconds wall time, and 90 seconds recovery. Those historical numbers are insufficient for the compiled operation sequence and must not be used for admission. The current local plan declares 16 observation operations and 12 recovery stages, four owned documents, one in-flight request, 420 seconds wall time, and 180 seconds recovery. Environment/credential preflight requests require a separate production allocation. The original proposed USD 1.00 planning ceiling is not tariff acceptance or a frozen permission envelope.

## FS-WRITE-LIMITS-03: the BatchWrite continuation residue and every write-path limit

`FS-WRITE-LIMITS-03` is a second, independent owned-data campaign on the same limits lane. It exists because the FS-DATA-WRITE receipt audit reduced the parent's open write conditions to a finite residue, and it covers all of it. Its machine-readable package is [`fs-write-limits-03.json`](../../spec/compatibility/broad-runs/fs-write-limits-03.json), its binding is [`fs-write-limits-03-binding.json`](../../spec/compatibility/broad-runs/fs-write-limits-03-binding.json), and its completed local execution record is [`fs-write-limits-03-local-shadow.json`](../../spec/compatibility/broad-runs/fs-write-limits-03-local-shadow.json). Production remains `unobserved`; nothing here promotes the parent.

The campaign carries twelve cases. Three ask whether a BatchWrite is evaluated per position or refused as a whole: a three-write request whose middle item carries no operation, one whose middle value cannot be decoded into the protobuf, and the duplicate-document request that production is already recorded as answering with a whole-request 400 and no publication. The other nine are the write-path catalog limits, each at its exact boundary: collection id bytes, subcollection depth, document name bytes, the three index-entry limits, indexed field value bytes, field path bytes and field value bytes. `FS-LIMIT-API-REQUEST-BYTES` is the one write-path surface this campaign leaves out, and it is assigned to the request-byte collector rather than dropped, because its refusal is expected to be transport-level rather than a typed Firestore error.

Nothing is excluded, and no index configuration change is required. Every index boundary is reached under the project's default single-field configuration, in which each field carries ascending, descending and array-membership modes at collection scope. The entry-bytes boundary is tuned with the document and parent document name bytes, since an entry is charged both; the entry-count boundary with the number of distinct array elements, since each one carries two membership entries; and the entry-sum boundary with both, plus a filler field whose name length is solved for so the sum lands exactly on 8,388,608. `conformance/firestore.indexes.json` therefore needs no addition and its preflight digest does not change, which the manifest records under `indexConfiguration`.

Two limits could not be written as the ordinary accept-then-refuse pair, and forcing them into that shape would have encoded behaviour production does not have. `FS-LIMIT-INDEXED-FIELD-VALUE-BYTES` is a truncating maximum: the catalog states that production truncates the indexed representation at 1,500 bytes and warns against replacing that with a plain rejection. It is written as two accepted writes whose entries both sit exactly at the entry maximum under truncation, where the second carries a value twice the ceiling; if the indexed value were charged in full its entry would be 9,180 bytes and the write would be refused, so accepting both is what confirms the truncation. `FS-LIMIT-FIELD-VALUE-BYTES` is observable only through its refusal: just 89 bytes separate it from `FS-LIMIT-DOCUMENT-BYTES`, and an owned document's name and ownership marker cost more than that, so a value at the accepted boundary cannot fit in any document in the owned namespace. The refused document breaches both maxima at once, so the diagnostic text is the only thing that says which limit production enforced, and this campaign's comparator compares it.

Rows for the three limits the catalog still records as unsupported state the documented production behaviour and are marked pending, so a local difference on them is recorded as evidence about the local runtime rather than as a campaign failure. The completed shadow produced exactly one: an update mask whose canonical field path is 1,501 bytes is reported by the local runtime as a per-item BatchWrite status rather than as a whole-request refusal. The declared expectation is extrapolated from the production matrix row `errors/rest-shapes#mask-with-invalid-path`, which is a Commit, so whether a BatchWrite reports a field-path violation per item is itself part of the same question the first three cases ask. The other two pending limits agreed: the local runtime truncates the indexed value at 1,500 bytes, and it refuses an over-long field value with production's own wording.

Two earlier shapes the shadow refused are recorded here because a reviewer would otherwise expect what the audit proposed. A name that exceeds a request-stage identifier limit is not a resource the API will read back: a read of a 1501-byte collection id is refused with `INVALID_ARGUMENT`, not answered with a typed `NOT_FOUND`. Such names cannot be owned Gate resources, because typed absence is unprovable for them and the Gate cannot release them; they are probed instead, with a readback that must be refused exactly as the write was. An unexpected acceptance still stops the campaign, because the Gate refuses a creation proof for a name outside the declared resources. Separately, `FS-LIMIT-DOCUMENT-NAME-BYTES` cannot be observed with a create at all: an index entry is charged the document name and its parent's name, so the smallest possible entry for a document named at 6,144 bytes is 11,040 bytes against a 7,680-byte maximum. That boundary is probed by requests that carry the name without creating an index entry. The compiler now refuses to emit any created document that would breach a limit it is not testing, so neither confound can return silently.

The envelope is 63 observation requests and 60 recovery requests over twenty owned documents and four probed names, plus six management calls in each phase: 135 requests, 1,200 seconds of wall time with 810 seconds reserved for recovery, and a proposed ceiling of 53,500 micro-USD against the standing 1.00 USD planning cap. That is the same manifest, permission, lock and comparator shape O7 reviewed for limits-02. The comparator keeps the limits-02 contract unchanged and adds one additive per-row field that reports status and post-state shape with diagnostic wording removed, so the known message-text difference on the duplicate-document control cannot hide the continuation answer inside a `SEMANTIC_MISMATCH`.

`collector.py` and `comparator.py` are byte-for-byte unchanged, so the frozen limits-02 collector and comparator source digests still resolve. The new campaign lives in sibling modules: `compiler_03.py`, `expectations_03.py`, `collector_03.py`, `comparator_03.py` and `shadow_03.py`.
