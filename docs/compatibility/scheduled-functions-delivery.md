# Scheduled functions: delivery and retry, against production

SCHEDULED-FUNCTIONS is IMPLEMENTING (`docs/compatibility/scheduled-functions.md`). This page records what the second production delivery recording showed about how Cloud Scheduler hands a scheduled run to a function and retries a failed one, what the strict profile now does about it, and what is still different. Nothing here promotes a closure condition: the frozen inventory needs two recordings of each corpus and a comparison on the final artifact.

## The recording

Run `156715222b86ea44` (2026-10-05, sandbox project `fireemu-oracle-sbx`, region `us-central1`): one Firebase CLI deploy of five functions (three Gen2 `onSchedule`, two Gen1 `pubsub.schedule`; `conformance/scheduled-delivery/fixture`), two observation passes (a forced `:run` of every job, then six minutes of natural fires), 97 handler frames, 177 Cloud Scheduler execution entries and 17 pulled Pub/Sub messages, cleaned up and read back absent. Four extra REST jobs probed the retry rules. The public digest the local comparison reads is `conformance/scheduled-delivery/local/production-run2.json` (no project number, trace id or client address).

What production did, in the terms a handler sees:

- **Gen2.** Cloud Scheduler sends `POST /` with `x-cloudscheduler: true`, `user-agent: Google-Cloud-Scheduler`, `content-length: 0`, an OIDC `authorization` header, the job's **id** in `x-cloudscheduler-jobname` (`firebase-schedule-<name>-us-central1`) and the schedule time in `x-cloudscheduler-scheduletime`, written **in America/Los_Angeles with its offset** (`2026-10-05T01:41:00-07:00`) for a UTC job and an Asia/Tokyo job alike. The SDK builds the event from those headers: `jobName` and `scheduleTime`, and a non-enumerable `context` getter. A handler that throws is answered 500 and the attempt is retried per the job.
- **Gen1.** The handler gets one argument, the context of the Pub/Sub message the job published: a 17-digit `eventId`, `resource` `{name: projects/<p>/topics/<job id>, service, type: type.googleapis.com/google.pubsub.v1.PubsubMessage}`, the message's publish time (milliseconds at most, trailing zeros dropped) as `timestamp`. The message has empty data and the attribute `scheduled: "true"`. A Gen1 handler that throws is not retried: `schedFailV1` threw at each of its 4 occurrences and ran once per occurrence (4 frames, 4 message ids), and every attempt of its job finished without an error. The job declared no `retryCount`, so a Gen1 count is covered by the next recording.
- **Time zones.** An omitted zone reads back as `UTC` for Gen2 and `America/Los_Angeles` for Gen1 (the Firebase CLI writes them).
- **Retry.** `retryCount: 4` (min 4 s, max 50 s, 2 doublings): five attempts at 0, 4.6, 13.2, 29.7, 48.2 s. `retryCount: 5` (defaults): six attempts at 0, 5.6, 16.3, 36.8, 77.3, 158.0 s. `retryCount: 0`: one attempt. A retry window with no count (`maxRetryDuration: 30s`, min 4 s, max 10 s): four attempts at 0, 4.6, 13.2, 23.7 s, the next being past the window. A count and a window together (run `f123d4fa2d61c5f5`: `retryCount: 3`, `maxRetryDuration: 20s`, min 4 s, max 10 s): four attempts at 0, 4.65, 13.26, 23.88 s and 0, 4.5, 13.02, 23.68 s, the fourth past the window, so the chain goes on until both limits are used up. `minBackoffDuration: "0s"` with `maxBackoffDuration: "0s"` and a window of 10 s: Cloud Scheduler stored `5s` and `3600s` and made two attempts, 5.62 s apart, in both passes. After the doublings the gap grows by a constant 2 s (run `ecef353d18975246`, latency taken off: min 4 s with one doubling 4, 8, 10, 12, 14; min 2 s with three 2, 4, 8, 16, 18; min 4 s with two 4, 8, 16, 18), not by `min * 2^doublings` as Cloud Scheduler's documentation says. A `maxDoublings` of 0 is stored as the default 5 (the create answer read 5; the chain doubled every time: 3, 6, 12, 24, 48). The occurrence's schedule time is the same on every attempt.
- **Refusals.** A job with `retryCount: 6` is refused (400, `invalid retry count. The retry_count must be a positive integer less than 5: invalid argument`) although 5 is accepted; a retry window of `20.5s` is refused (400, `retryConfig.max_retry_duration.nanos cannot be set: invalid argument`).
- **Timeouts and overlap.** A handler that outlasts its function timeout (100 s against 90 s) is answered 504 at 90 s and keeps running to its end. Production started no occurrence of the job while a run of it was in flight: the `every 1 minutes` job with that handler started its natural runs every 2 to 3 minutes (at 0, 243, 363, 483, 663, 783 and 903 s of the recording), and the occurrences in between never ran. A forced run (`:run`) did start while a natural one was in flight (at 535 s, inside the run begun at 483 s), and a natural occurrence that fell inside it was skipped too. The recording does not say whether "in flight" ends at the 504 or at the handler's end: both fell before the next boundary.

## What the strict profile does now

| Behaviour | Strict | Emulator profile |
|---|---|---|
| Gen2 delivery | the function's HTTP wrapper is called with the recorded headers (job id, Los Angeles time, empty body), so the SDK builds the event, the `context` getter, runs its init hook and maps a throw to 500 | unchanged: the handler is called directly with the job's resource name and a UTC time |
| Gen1 context | the Pub/Sub context above (17-digit id, topic, `PubsubMessage` type) | unchanged |
| Zone of a schedule that names none | Gen1: America/Los_Angeles; Gen2: UTC | UTC (or `scheduler.defaultTimeZone`) |
| Gen2 retry window with no count | retries until the window ends | the same (a retry model change, not a refusal; the official emulator never retries a scheduled function) |
| Gen1 retry (any declaration, a window or a count) | the handler is never retried: its job targets Pub/Sub, so Cloud Scheduler's retry covers the publish; the recorded Gen1 handler that threw ran once per occurrence and every attempt of its job finished without an error | the same (the official emulator never retries a scheduled function) |
| An occurrence while a handler of the function is running | dropped (`skipped: in flight`); a manual run is still started, and the occurrences of one clock move do not count against each other | allowed, as before (`scheduler.overlap` `allow`; the official emulator never schedules a function, so it skips nothing); `scheduler.overlap: skip-in-flight` selects the strict behaviour |
| `retryCount` 6 or more, fractional `maxRetrySeconds` | refused at startup with production's message | accepted, as the official emulator accepts them (it creates no Scheduler job and reads no retry configuration of a schedule trigger) |

A manual run (`functions/{name}:run`) is Fireemu control, not Cloud Scheduler's run-now, and uses the same event shape as a scheduled one.

## What still differs

Unreproducible: the OIDC `authorization` header, the trace headers (`traceparent`, `x-cloud-trace-context`), `forwarded` and `x-forwarded-for` (a trace id and a client address); the constant `accept-encoding`, `x-forwarded-proto` and `host` are sent. Not determined by the recording:

- The **phase of an interval schedule**. The first natural occurrence of the `every 1 minutes` job `schedOkV2` was on the minute (the `scheduleTime` of the create response), and every later one carried the same fraction of a second (`.416739` across 15 occurrences); the jobs' phases (`:01.416739`, `:03.352477`, `:01.751605`) do not follow their creation instants (`userUpdateTime` 08:40:31.496745, 08:40:32.682527, 08:40:33.554275), so the anchor is not the creation second or its fraction, and nothing in the recording says what it is. fireemu runs an interval on the minute.
- The **alignment of an `every 5 minutes` job** after forced runs: the occurrence after a forced run moved (the 01:45:00 occurrence was not run naturally and the next was 01:48:01.75), while the forced run of the `every 1 minutes` job did not displace its natural occurrence (01:43:01.416739 was delivered twice). fireemu runs the job on the five-minute boundary.
- What a Cloud Scheduler **run-now** carries: the job's next schedule time; fireemu's manual run carries the current logical time.
- The **fourth gap of the `retryCount: 4` chain**: about 18.5 s, seen twice in this recording with one parameter set (forced chains at 01:45:00 and 01:53:01.75), where the documented rule (double `maxDoublings` times, then grow linearly by 2^maxDoublings x the minimum, capped) gives 32 s. Strict follows the recorded 2 s linear step after the doublings (runs 3 and 4), which differs from the documented formula.

Not recorded: a zero minimum or a zero maximum backoff alone (only the pair `0s`/`0s` was sent; each alone is kept as declared), what a Gen1 job's own retry does to the publish, and whether a pending retry keeps the next occurrence from starting.

Documented, not recorded: when the count is used up while the window still has room, strict keeps retrying. The [Cloud Scheduler REST reference for `RetryConfig.maxRetryDuration`](https://cloud.google.com/scheduler/docs/reference/rest/v1/projects.locations.jobs#RetryConfig) says: "If specified with `retryCount`, the job will be retried until both limits are reached." The recorded case is run 3's `count` job: four attempts, the fourth past the 20 s window; it does not record the count being used up inside the window.

Run `f123d4fa2d61c5f5` (the third delivery recording, same project and region; digest `conformance/scheduled-delivery/local/production-run3.json`) pulled 25 more messages from the Gen1 topics (and ran `schedRetryV1`, a Gen1 function declared with `retryCount` 1 whose handler throws, four times with four message ids: one invocation per message). Every pulled message of both recordings (17 and 25) has the attribute `scheduled: "true"`, no data, a 17-digit id that is the `eventId` of exactly one handler frame of its function, and a publish time equal to that frame's `context.timestamp`.

Implemented, strict profile only: a first-generation schedule has the topic `firebase-schedule-<name>-<region>` (the id of its job; a Gen2 schedule has none, as in production) and no emulator subscription, and every occurrence and every manual run of it publishes the message above to that topic, with the message id the handler's context reports and the occurrence's time as the publish time (`PubSubHandle::publish_with_message_ids`; the runtime reserves capacity, publishes before enqueueing the handler, and records a publication refusal as a failed attempt without invoking the handler). The emulator profile keeps the official emulator's topic `firebase-schedule-<name>` with its subscription and publishes nothing. Not implemented: no Cloud Scheduler job resource or execution log exists.

## Re-running the comparison

`conformance/scheduled-delivery/local/run-compare.mjs` runs the recorded fixture and a retry-probe fixture under both profiles with a pinned logical clock and prints one row per observation with a verdict per profile (`MATCH`, `DIVERGES`, `NOT_COMPARABLE`). It needs a fireemu binary (built with `RUSTC_WRAPPER=` so that no compiler cache is involved), a Node 22 and a `node_modules` holding firebase-functions 7.3.2. `local-delivery.test.mjs` runs the delivery rows end to end when `FIREEMU_BIN`, `FIREEMU_NODE` and `FIREEMU_DEPS` are set.
