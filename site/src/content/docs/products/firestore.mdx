Fireemu serves Cloud Firestore over gRPC, REST and the WebChannel transport the Web SDK uses, with Firestore Security Rules. Connect to it at `127.0.0.1:8080` (see [Connect your app](../../getting-started/connect/)).

## Editions and API modes

Select the database edition and API mode in `fireemu.toml`. `fireemu init` writes the Standard edition with the Native API:

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
schemaVersion = 1

[firestore]
edition = "standard"
apiMode = "native"
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "firestore": {
    "edition": "standard",
    "apiMode": "native"
  }
}
```

</TabItem>
</Tabs>

`edition` accepts `standard` and `enterprise`. The Enterprise Pipeline API supports a limited subset of read operations; see [Enterprise pipelines](#enterprise-pipelines) and [Limitations](../../compatibility/limitations/).

## Enterprise pipelines

On an Enterprise database, fireemu runs pipelines from the Admin SDK (gRPC) and the Web SDK's `firebase/firestore/lite/pipelines` (REST `:executePipeline`). The supported subset starts with a `collection`, `collection_group` or `documents` input, followed by `where`, `select`, `sort`, `add_fields`, `remove_fields`, `distinct`, `aggregate`, `offset` and `limit` stages in any order and number. Aggregates include `count`, `count_distinct`, `sum`, `average`, `minimum` and `maximum`, with or without groups.

| Expression | Supported |
|---|---|
| Fields | Nested paths (`a.b`) and `__name__` (the document reference) |
| Literals | Values of every type, including arrays and maps of literals and vectors of doubles |
| Comparisons | `equal`, `not_equal`, `less_than`, `less_than_or_equal`, `greater_than` and `greater_than_or_equal`, anywhere an expression stands |
| Construction | `array(...)` and `map(...)` |
| Document functions | `documentId`, `collectionId` and `parent` |
| Logic, existence, type and membership | `and`, `or`, `not`, `xor`, `nor`, `exists`, `is_absent`, `is_error`, `type`, `is_type`, `array_contains`, `array_contains_all`, `array_contains_any`, `equal_any` and `not_equal_any` |
| String | `concat`, `to_lower`, `to_upper`, `starts_with`, `ends_with`, `string_contains`, `char_length`, `substring`, `trim`, `ltrim`, `rtrim` and `split` |
| Math | `add`, `subtract`, `multiply`, `divide`, `mod`, `abs`, `round`, `floor`, `ceil` and `pow` |

A `where` keeps a row only when its condition (a comparison, a field or another supported function) is `true`. A `select` sets at most 64 fields, as in production. Results without a `select` carry the document's name, create time and update time, and answers normally carry the execution time; a `documents` input whose only path is missing currently returns an empty element without it. A small answer comes as production frames it: all results in one response message over gRPC, or in one array element over REST. Fireemu cuts a larger answer at about 1 MiB of results; production recordings show variable boundaries; large-answer framing is not verified. `select({__name__: field("__name__")})` answers the document name, including the recorded forms beside other aliases or with quoted aliases and values; unrecorded forms remain `UNIMPLEMENTED` under `strict`. Without `sort`, recorded collection reads follow ascending CRC-32 of document IDs; collection groups use parent path then that order. Non-ASCII IDs and CRC-32 ties are unverified, as are aggregate group order and ordering of ties under a limit. A stored `-0.0` reads back as `-0.0`, as in production; the official emulator stores it as `0.0`.

The recorded matching answers cover specific request shapes from the FS-ENT-ORACLE observations, including comparisons, literal values, select aliases, document functions, stage ordering and the supported string and math functions. Other recorded and unrecorded shapes remain unverified. Under `strict`, a refusal is answered only when the request has the shape of a request production refused, with that request's text, and is `UNIMPLEMENTED` otherwise. A shape keeps the stages, function names, value kinds and every map's entries in order, and replaces only plain field names and values of the same kind, so `select({total: documentId(field)})` is answered like the recorded `select({v: documentId(field)})`. A REST body keeps its key order; over gRPC a map of two or more entries has no order, so `strict` answers no refusal of such a request there. Where production has not been observed, the profiles differ:

| Input | `strict` | `emulator` |
|---|---|---|
| A document function of a collection reference with a non-ASCII name | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the index counted in UTF-16 units |
| A literal holding a field or function under a map key that is not a plain name | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, naming a reserved key first |
| A document function of a double, timestamp, geo point, bytes, array or vector | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, naming the type |
| A `map(...)` key that is a double, null or another type than an integer or boolean | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, naming the type |
| A vector literal with integer or NaN elements, no element, without `value` or with another key | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the official text |
| A vector literal with an infinite element | `UNIMPLEMENTED` | The vector |
| A `__type__` key that is not a string, or a reference literal that names no document | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the official text |
| Two refusals in one pipeline | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, one of them |
| A refusal production recorded only in another stage, such as a literal holding a field inside a `where` condition | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the official text |
| A vector literal with a negative-zero element | `UNIMPLEMENTED` | The vector |
| A literal with more than one empty or reserved key, or the key `__name__` | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, naming one key |
| A `limit` of another type than an integer or string; an `offset` that is negative or of another type than an integer or string | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the official text |
| A `limit` of 0 or an `offset` of 0 | `UNIMPLEMENTED` | The rows |
| A `select` alias inside another in another order than production's `{m, m.r}`, such as `{a.b, a}` | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, naming the later alias over REST (as the official emulator does) and the child over gRPC |
| Two `select` fields that both fail when evaluated, such as `{a: documentId("s"), b: parent(true)}` | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the first in key order |
| A vector inside an array, or a `__type__` key beside other keys in a literal | `UNIMPLEMENTED` | The official answer |
| An unrecorded wrong argument count for a supported function | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, fireemu's text |
| Function options | `UNIMPLEMENTED` | Ignored, as the official emulator ignores them |
| An empty `select` map or a later stage's check after a function or stage value fireemu does not check (production names an unknown function first) | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the empty map or the later check |
| An empty map or another refusal beside a function call that fails on its constants, such as `map(1.5, i)`, or beside any other part `strict` does not answer | `UNIMPLEMENTED` | `INVALID_ARGUMENT`, the empty map or the other refusal |
| An unrecorded stage argument count or options | `UNIMPLEMENTED` | Depends on the stage and argument shape |
| An empty `array()` or `map()` | `UNIMPLEMENTED` | An empty array or map |
| An `aggregate` without its groups argument | `INVALID_ARGUMENT` with production's arity text for the recorded shape (directly after the collection, a non-empty map of plain aliases to `count`), else `UNIMPLEMENTED` | `INVALID_ARGUMENT` with the same text |

Unsupported functions and stages, including regex functions, timestamp and map functions, the remaining math functions, `union`, `unnest`, `sample`, `find_nearest` and `replace_with`, are refused with `UNIMPLEMENTED`, never ignored. Recorded matches establish compatibility only for the recorded request shapes; other shapes remain unverified.

## Composite indexes

Production refuses a query whose composite index is not defined. The official emulator assumes every index exists, so a missing index is usually found only after deploying. Fireemu checks each query against the indexes declared in `firestore.indexes.json` (referenced from `firebase.json`), as production does.

| `firestore.missingIndexes` | Behavior |
|---|---|
| `refuse` (default) | The query is refused with `FAILED_PRECONDITION` and the console link, as production refuses it. |
| `report` | The query runs. Each missing index is reported once per database on standard error, with production's refusal text and the `firestore.indexes.json` entry to add. |

The `emulator` profile always runs the query, as the official emulator does, while reporting missing-index suggestions on standard error.

An OR query can require a separate composite index for each branch. Since v0.26.0, supplementary diagnostics list all distinct missing branch indexes in one attempt. Under `strict` with `refuse`, the SDK still receives its existing `FAILED_PRECONDITION` response and first creation link; the additional branch definitions are on standard error. Under `report`, the control API report also collects the distinct missing definitions.

### Fail a CI job on a missing index

The report on standard error is easy to miss in a CI log. Under `strict` with `"report"`, the control API also lists every index that was missing, so a job can fail on a non-empty list. Turn the report on:

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
schemaVersion = 1
profile = "strict"

[firestore]
missingIndexes = "report"
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "profile": "strict",
  "firestore": {
    "missingIndexes": "report"
  }
}
```

</TabItem>
</Tabs>

`fireemu exec` gives its command `FIREEMU_CONTROL_URL` (ending in `/v1/`) and `FIREEMU_CONTROL_TOKEN`, so the script that runs your tests can check the list when they are done:

```sh
npx fireemu exec -- sh -c '
  npm test
  status=$?
  curl -fsS -H "Authorization: Bearer $FIREEMU_CONTROL_TOKEN" \
    "${FIREEMU_CONTROL_URL}firestore/missingIndexes" > missing-indexes.json || exit 1
  [ "$(jq .count missing-indexes.json)" = 0 ] || { jq .indexesJson missing-indexes.json; exit 1; }
  exit $status
'
```

`GET /v1/firestore/missingIndexes` answers:

```json
{
  "count": 1,
  "truncated": false,
  "dropped": 0,
  "missingIndexes": [
    {
      "project": "demo-app",
      "database": "(default)",
      "name": "projects/demo-app/databases/(default)",
      "index": {
        "collectionGroup": "notes",
        "queryScope": "COLLECTION",
        "fields": [
          { "fieldPath": "owner", "order": "ASCENDING" },
          { "fieldPath": "created", "order": "ASCENDING" }
        ]
      },
      "message": "The query requires an index. You can create it here: https://console.firebase.google.com/..."
    }
  ],
  "indexesJson": {
    "projects/demo-app/databases/(default)": {
      "indexes": [{ "collectionGroup": "notes", "queryScope": "COLLECTION", "fields": ["..."] }]
    }
  }
}
```

- Each entry is one index per database, in the order it was first needed, with production's refusal text. `indexesJson` groups the entries per database in the shape `firestore.indexes.json` holds, so you can merge the `indexes` array of a database into that file.
- `GET /v1/sessions/{session}/firestore/missingIndexes` lists only the session's project; `GET /v1/firestore/missingIndexes` lists every project. A session `reset` does not clear the list, so a suite that resets between cases still reports every index it missed, and deleting a session clears its project's entries.
- The list holds at most 1,000 entries. Past that, `truncated` is `true` and `dropped` counts the queries served whose index is not listed. A project whose every index was dropped is answered with `409` and a message that the list is full, never with an empty list, so a check on `count` cannot pass on an incomplete list. Clear the list and run again.
- `DELETE` on either route clears the list and the dropped count and answers `{"cleared": <count>}`. The session route clears that session's project only; the route without a session clears every session's entries, so a test world that shares a daemon with others should use the session route. An index that is needed again afterwards is reported again.
- Where nothing is reported (the `emulator` profile, `strict` with `"refuse"`, or Firestore not selected), `GET` answers `409` with `FAILED_PRECONDITION`, so a check that depends on the list cannot pass on an empty answer. `DELETE` still answers `{"cleared": 0}`.
- A page in a browser needs `Authorization: Bearer <control token>` for both methods, as for the resource report, because the entries name the fields your queries filter and order on.
- With `fireemu/testing`, call `world.control('GET', '/v1/sessions/default/firestore/missingIndexes')` and `world.control('DELETE', ...)` on the same path, so the read and the clear stay within your world's project.

### Checks on `firestore.indexes.json`

Under `strict`, Fireemu refuses at start-up (and keeps the previous indexes when the file changes while it runs) what `firebase deploy` refuses, and the message names the entry:

- A composite index with a single field, such as `indexes[3]` with only `{"fieldPath": "n", "order": "ASCENDING"}`. Production answers "this index is not necessary, configure using single field index controls". Declare it under `fieldOverrides` instead, which is also how a collection-group query on one field is enabled. `(field, __name__ DESC)`, `(__name__ DESC)` and a single vector field are accepted, as production accepts them.
- An entry without a `fields` array, which is what a misspelled key such as `feilds` looks like.
- A `fieldOverrides` entry without an `indexes` array. A TTL-only override needs `"indexes": []`.
- A `fieldOverrides` index that has only a `vectorConfig`: each override index needs exactly one of `order` and `arrayConfig`. Declare a single vector field as a composite index instead, as production does.

A missing or empty `queryScope` is read as `COLLECTION`, and the older `collectionId` and field `mode` keys are read as `collectionGroup` and `order` / `arrayConfig`, as `firebase deploy` reads them. The limits of at most 200 composite indexes, 100 fields per index and one array field per index apply under both profiles. The Admin API's `indexes.create` applies the same checks, and counts the indexes of the file and the ones created at run time together against the 200.

The `emulator` profile loads the file as before, because the official emulator never reads it.

Supported text definitions in `firestore.indexes.json` (`searchConfig.textSpec`) enter the local text catalog on Enterprise databases and serve `collection(...).search({ query: documentMatches(...) })`. Search indexes remain separate from ordinary query planning. Standard edition still accepts valid search-index configuration without serving search, and geo search is unsupported.

The local `fireemu-lexical-v1` engine uses deterministic Unicode normalization and word segmentation, AND terms, positional phrases, exclusions and indexed-field restrictions. Creation-time ordering is supported, and score ordering follows the recorded production result orders; numeric `score()` values are approximations. There is no stemming, synonym expansion, typo correction or language autodetection. `productionExact` refuses search until corresponding production behavior is recorded. Explicit Fireemu control actions advance, complete, fail and repair a generation-scoped build. See the [local text search guide](https://github.com/t-k/fireemu/blob/main/docs/text-search.md) for setup, controls and exact limits. Text search was added in v0.30.0.

## Query limits

Under the `strict` profile, the Standard edition query limits are enforced as production enforces them. Setting `firestore.enforceLimits` to `false` lets queries pass that production refuses, so leave it on unless you have a specific reason. Under `strict` the key switches only these query limits (at most 30 disjunctions, 10 `in` values, and so on): the limits on writes, transactions and indexes, and the wire shapes of the REST and WebChannel surfaces, stay production's. Under the `emulator` profile, `true` also asks for those production limits.

## Listen streams

Production ends an end user's native gRPC `Listen` stream with `INTERNAL` an hour after it opened. By default Fireemu keeps the stream open however long it is held (`firestore.listenStreamLifetime: "unlimited"`). To test a client's reconnect, either set it to `"oneHour"` (the default with `productionExact`), or call `POST /v1/firestore/listen:expire` on the control API to end every held end-user stream at once with production's status.

## Transactions and history

Like production, Fireemu keeps every version of a document written in the last hour, so a `read_time` read, a read-only transaction or a resumed listener can see it. Transactions lock what they read, as production does. Starting with v0.27.0, contended gRPC and WebChannel writes wait without occupying runtime workers. Canceling a waiting Commit ends that request's deadlock wait; its transaction keeps read locks until it commits, rolls back or expires.

A test that updates the same documents many times therefore holds many versions in memory. These local limits, which production does not have, bound it:

- Each database retains at most 1 GiB of logical history bytes and 1,000,000 versions, each session 1 GiB and 1,000,000 versions, and the daemon 4 GiB and 4,000,000 versions. Logical bytes follow Firestore's storage size model and are not the process's memory, which can be several times larger.
- On a pinned clock (`daemon.clockStart`), time does not pass on its own, so a database keeps at most 1,024 versions of any one document. This limit works like `maxVersionsPerPath` below: once a document goes past it, older snapshots are released for the whole database.
- Starting with v0.27.0, strict Listen retains the latest 4,096 boundary records per live database. A resumed stream echoes the original boundary's `read_time`, then sends the new snapshot time with `CURRENT`. Token bytes are opaque and may change without a write. An expired record or expired document history triggers `RESET` and a full replay; reset, restore and daemon restart discard the records. This bound is local to Fireemu and is not a production limit.
- A commit that would cross a limit is refused whole with `RESOURCE_EXHAUSTED` and the message `Firestore retained history capacity is exhausted`.

Versions older than an hour are released by the next commit after the clock passes them. To use less memory, lower the limits in `firestore.history`:

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
schemaVersion = 1

[firestore]
edition = "standard"
apiMode = "native"

[firestore.history]
maxVersionsPerPath = 16
maxBytes = 268435456
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "firestore": {
    "edition": "standard",
    "apiMode": "native",
    "history": {
      "maxVersionsPerPath": 16,
      "maxBytes": 268435456
    }
  }
}
```

</TabItem>
</Tabs>

- `maxVersionsPerPath` (1 to 1,000,000) sets the most versions of one document a database keeps, on either clock, in place of the defaults above.
- `maxBytes` (1 MiB to 1 GiB) lowers the logical history bytes one database retains. An import (`--import`) is not checked against it: a larger import starts with a `warning:` line naming the database, its bytes and the limit (a snapshot restore above it logs the same line), and every later write that would grow the history is refused with `RESOURCE_EXHAUSTED`.

Without these keys the defaults apply.

The version cap applies to each document separately, but its effect reaches the whole database. Snapshots stay exact for every document, so once any document has more versions than the cap, the database keeps no snapshot older than that document's oldest kept version. After that:

- A `read_time` read older than that point is refused with `FAILED_PRECONDITION` (`The requested 'read_time' is no longer retained by this database.`). So is a new read-only transaction at such a `read_time` (`read_time is no longer retained by this database`).
- A transaction already open on an older snapshot fails its next read or commit with `ABORTED` (`The referenced transaction has expired or is no longer valid.`), even if it only touches other documents.
- A listener resuming from an older point is reset and sent the full result again.

Client SDKs retry `ABORTED` transactions, so avoid very small caps: choose a cap above the number of times any document is updated while your longest transaction is open.

`fireemu doctor --connect <control URL>` reports the retained versions and bytes of a running daemon: its `history.*` lines give the retained versions and logical bytes against the session and daemon limits, and how many bytes the next compaction would release.

## Security Rules

Rules are read from the `firestore.rules` file named in `firebase.json`, or from `rules.source` in `fireemu.toml`. Under `strict`, a project without rules refuses every client request, as a production project without a rules release does. See [Security Rules](../../guides/security-rules/).

## Named databases

Declare each named database in the `firestore` array of `firebase.json`, with the `rules` and `indexes` files it uses, or create it through the Admin API. Under `strict` a request to a database that is neither declared nor created gets `NOT_FOUND`, as in production, and a declared database id must be one production could create (4 to 63 characters of `[a-z0-9-]`, starting with a letter), or Fireemu does not start.

Production governs a database only by its own rules release. So a database created at run time has no Security Rules, and refuses every client request, until you set some for it; the `(default)` database's rules do not apply to it. Declare the database in `firebase.json` with its `rules` file, or load them at run time:

```
PUT /emulator/v1/projects/{project}/databases/{database}:securityRules
{"rules": {"files": [{"name": "firestore.rules", "content": "..."}]}}
```

This is the route `PUT /emulator/v1/projects/{project}:securityRules` uses for the `(default)` database, with the same body and answers. The rules set this way last until the database is deleted; they are not part of a snapshot. The `emulator` profile keeps the official emulator's behavior: a database that has no rules of its own is served by the `(default)` database's rules (rules loaded for it with the route above apply to it).
