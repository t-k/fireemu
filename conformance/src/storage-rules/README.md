# STORAGE-RULES observation declarations

This directory defines a finite, partial REST corpus for the frozen STORAGE-RULES closure inventory. All twenty-two behavior recipes now have static declarations, including three management programs. It contains no production sender, credential loader, Rules publisher, admission gate or recovery executor. Original closure statuses remain pending. Production status codes, bodies, header values and Rules decisions remain unobserved.

## Declared behavior

The current nineteen recipes cover individual method grants and aliases, v1/v2 list boundaries, anonymous and UID ownership predicates, standard/custom token claims, six token refusal/control states, proposed metadata fields, simple/multipart/resumable upload fields, stored resource fields and direct null/non-null controls, create/update selection for absent and present uploads, delete `request.resource` null/non-null controls, bounded `request.time` predicates, bucket/leaf captures, recursive wildcard depth, Firebase denial shapes, GCS/Admin boundary controls, refusal precedence controls, the Firebase download-token boundary, and three Storage Rules to Firestore access obligations. Object cases use distinct owned namespaces and literal Storage rulesets. Cross-service transitions are separate finite `firestorePrograms` because a document change cannot be represented as one object request. Read/write observations require raw responses and privileged metadata/media state checks.

Three additional management programs declare compile rejection, release switching, and no-release behavior. `pendingRecipes` is empty because every behavior recipe has an input declaration; none is verified. Shared Rules language evidence is still subject to the frozen S3 decision. The new token, state-transition, time, precedence, download-token, upload and Firestore programs are static inputs; production authentication refusal, operation selection, delete-resource values, server-time, refusal order, download-token behavior, finalization fields and cross-service decisions are still unobserved.

## Management programs and local smoke

`storage-service-compile` retains all 338 distinct literal Rules sources referenced by the object cases, Firestore programs and release-switch program, plus one deliberately invalid Storage expression. The static sequence proposes [projects:test](https://firebase.google.com/docs/reference/rules/rest/v1/projects/test) with inline `Source` and no test suite for each source, bounded by reads that require the bucket-specific release to remain unchanged. The API documents syntactic and semantic source issues without creating a ruleset. The valid sources require no error issue; the invalid source requires an error issue with a source position. This does not prove that a later Rulesets create would accept every source, so the four sources actually published by a future runner still require create and GET source-digest readback. These are production Rules API inputs, not observed compile results or an approved request budget. The [Rulesets REST resource](https://firebase.google.com/docs/reference/rules/rest/v1/projects.rulesets) documents create, get and delete, while the [Releases REST resource](https://firebase.google.com/docs/reference/rules/rest/v1/projects.releases) documents the separate live release reference.

`release-switch` uses two literal sources that allow only opposite objects under the owned prefix. It declares both decisions under source A and again under source B, with release readback and effective-decision settling between them. `no-release` requires both bucket-specific and bucketless Storage releases to be absent, seeds one owned object through the Admin boundary, observes a Firebase read refusal and Admin readback, then deletes only that object and reconfirms release absence. Both programs assume the planned post-STORAGE-OBJECT absent-release baseline; a changed actual baseline requires a revised program and packet. Their step orders are obligations, not executable per-call production requests. The management programs do not implement a production sender, settle loop, failure recovery, or the full HTTP ceiling.

`local-smoke.mjs` is a local fireemu regression check using `/internal/setRules` for activation and the fireemu control API for readback and clearing. It validates all 338 valid sources through local activation/readback, confirms invalid-source atomicity, exercises the two opposite local authorization decisions, and checks no-rules refusal with Admin access. Run it through `fireemu exec` with `conformance/storage-rules-local.fireemu.json` and a port-registry claim. These endpoints replace a local rules generation; they are not the production Firebase Rules release API. Its results do not establish production compile acceptance, release propagation, or compatibility.

`local-equivalence.mjs` replays all 331 object cases and five Firestore programs against each isolated source and the corresponding v1/v2 bundle in one disposable fireemu session. It checks initial absence, source readback before each subject, paired subject status and object readback, local cleanup absence, and local allow/deny controls across both Rules versions and cross-service access. The three-distinct-document control expects denial because [Storage Rules permit at most two Firestore document accesses per evaluation](https://firebase.google.com/docs/storage/security/rules-conditions). Its emulator-profile tokens and literal owner credential are local fixtures only; it does not verify production credentials, production Rules compilation, or compatibility. All listeners use OS-assigned loopback ports, with the optional hub and logging listeners disabled:

```sh
fireemu exec --config conformance/storage-rules-equivalence-local.fireemu.json --only storage,firestore --project fireemu-oracle-query --storage-port 0 --firestore-port 0 --http-port 0 --hub-port 0 --logging-port 0 -- node conformance/src/storage-rules/local-equivalence.mjs
```

`publication.mjs` derives one Rules source per Rules version from the 336 case and Firestore source bodies. It retains each exact match body, requires each case prefix to equal the owned run prefix plus its ID, rejects duplicate or nested prefixes and noncanonical match bodies, and enforces the source text limit. Its output is an input candidate for a later reviewed publisher. The pure structural check and a local activation of both generated variants do not prove all case decisions are equal under production Rules or that production accepts the aggregate source.

`manifest.mjs` assigns stable IDs to the 3,799 declared object and Firestore requests in one recording and binds the ordered rows to a SHA-256 digest. It validates the frozen corpus first and remains a partial, non-sending input: Rules publication, authentication, settle checks, recovery and the complete HTTP ceiling are separate work.

`request-counter.mjs` is a pure draft attempt counter for one recording. It requires a durable started callback before any counted request, checks every declared preflight ID before admission, and writes a terminal row when a preflight check fails. It reserves each attempt before dispatch, fixes normal traffic at no more than 4,648 attempts and protects 2,000 recovery attempts within the draft 6,648 ceiling. A subject transport exception enters recovery without retrying the uncertain request, and a journal callback failure blocks further traffic. It does not decide whether an endpoint is allowed, perform a request, or prove cleanup and terminal success.

Five cross-service programs use only `fireemu-oracle-query/(default)/STORAGE-RULES/<run>-...` symbolic Firestore documents. The `get` program reads one captured document ID through a fully qualified Rules path after the same owned document is created with `allowed: true`, changed to false and deleted; it probes three fresh owned objects so a prior accepted upload cannot turn a later create into an update. The `exists` program reads a captured document ID against one seeded object before and after verified document deletion. Three budget programs evaluate two distinct documents, a third distinct document and an A-B-A repeat, with all referenced documents present to avoid an earlier missing-document short circuit. Each step declares a relative REST path, raw capture and the required document or object readback. Firestore updates and deletes carry typed `updateTime` references. Object cleanup carries a typed current generation and the originating own upload receipt; document cleanup requires the current update time to match this run's own write history. The program data does not resolve those references or send requests. A future runner must verify the bucket belongs to the same project, scoped service-agent IAM, exclusive Firestore and Storage windows, the original Rules release and cleanup ownership before doing any operation.

The upload matrix declares twenty-four cases: simple, multipart and resumable finalization crossed with `request.resource` size, contentType, name and custom `metadata.owner`, each with a matching and mismatching predicate. Every subject targets a new owned object with four received bytes and GCS owner metadata/media reads before and after. The simple upload has no `owner` custom metadata, so its pair checks key membership with `in`; a missing-member access would deny both branches. Multipart supplies exact `multipart/related` bytes with a fixed boundary and metadata part. Resumable initiation supplies metadata separately, then finalization supplies the bytes to a typed private reference to the initiation response's `X-Goog-Upload-URL`; the reference has no literal URL or upload ID. Its `path: null` means a future sender must validate and resolve the actual session URL before finalization or conditional cancellation. Cancellation is declared for an active or uncertain owned session, before object cleanup. A successful local parse/lint only checks local syntax; it does not establish the received resource values, URI provenance, status, or accepted/refused persistence in production. A future sender must not infer the finalization state from initiation metadata or send through the unresolved reference.

The token refusal cases send the same media GET against present, owned objects under a `request.auth != null` rule with missing, malformed, foreign-project, revoked and valid same-project credential references. They specify no expected status or Rules decision. The validator compares the entire declared data shape, including non-enumerable and symbol fields, and rejects extra secret or result fields. The malformed bearer value and all real tokens are prepared outside this corpus and kept private. An executor must verify the different-project origin, revocation after token issuance, and the valid control's same-project identity from independent fixture evidence. It must record the raw response and privileged before/after object state without storing token bytes in this declaration. An authentic expired token is an explicit unobserved S7 scope limit because waiting for it would hold the shared recording lock for about 130 minutes across two recordings. A valid token control does not prove that production checks revocation at this endpoint; that boundary remains an observation.

The sixteen precedence cases cross initially absent/present objects, Firebase/GCS JSON, valid/malformed credential references, and valid/malformed JSON bodies on metadata PATCH under an owned deny rule. The malformed body is the single byte `{`, transmitted as raw bytes with `Content-Type: application/json`; the valid body is `{}`. Eight more controls cross both object states, both dialects and both body states with a valid credential under an allow-write rule. Firebase uses the existing same-project user and malformed Firebase bearer references; GCS uses the owner OAuth reference and a separate malformed OAuth bearer reference. Actual header bytes are prepared outside this corpus. Every case retains privileged object readback before and after the subject PATCH. A future recording must establish that the malformed body is rejected as invalid JSON with a valid credential, that the valid-body controls reach the object operation, and that the malformed credentials are actually refused. The matrix does not predict which refusal wins. GCS JSON bypasses Storage Rules, so its rows measure the credential, validation and existence boundary only. Production behavior remains unobserved.

The download-token case uses one present owned object and a deny rule. It seeds the object with GCS owner requests, reads its token metadata, then declares an owner-only Firebase `create_token` request. The two anonymous Firebase media GETs use the same object and route; the first has no token, and the second carries a typed private reference to exactly one token newly appearing between the pre-create metadata and the create response. No token value or predicted response appears here. The future runner must verify the owner OAuth identity, the token-creation response's provenance and exact one-token difference, and the same object's metadata readback before resolving the reference. If token creation or resolution fails, it must not send the token-bearing GET. The local adapter's owner-only endpoint does not establish that production accepts an OAuth owner at this Firebase route. A token in a URL is secret: future raw URL logs and reports must redact it while retaining a private digest and provenance. This declaration supplies no resolver or send authority.

The four time cases use a fixed half-open 2000-01-01 to 2100-01-01 UTC window. One ruleset grants only an in-window request; another grants only an out-of-window request. Reads start with a present object and uploads with an absent object, with privileged state readbacks in both directions. A future recording must supply a trustworthy bounded interval for server evaluation time. If that interval is missing or overlaps either threshold, the outcome remains indeterminate; a local clock timestamp or HTTP status alone does not establish the predicate's intended direction. These fixed dates make the declaration reproducible, not a test of a near-boundary transition.

## Fixtures and protocol contract

Call `buildCorpus` with a plain bucket name, a fresh `STORAGE-RULES/<run>/` prefix and two distinct planned Firebase user IDs. Credential fields are symbolic references. `admin` requires an actual owner OAuth token and verified IAM capability; it never means the emulator-only literal `owner`. The owner excluded a valid IAM-denied OAuth principal because its preparation requires an out-of-scope IAM change. Seed, readback and cleanup still use privileged `admin`. User fixtures require real same-project ID tokens whose decoded and verified claims match the declaration. The `user-plain` token is a separate immutable snapshot with custom claims absent; minting and verifying these fixtures are future preparation work, not operations implemented here.

A case declares initial absence checks, an optional GCS seed and metadata update, a before-state readback, one subject request, an after-state readback, and bounded cleanup requests. A future executor must establish initial absence and ownership before any cleanup. Any unsuccessful or uncertain prerequisite prevents the subject operation. In particular, a rejected seed or unreadable baseline is not the declared initial state. GCS readbacks retain the complete body and headers, so bytes, generation, metageneration and metadata changes can be compared after writes and refusals.

List requests use the case's prefix and a finite result limit. Object paths encode the entire name as one segment; query values remain structured for later encoding. Raw response capture is mandatory. No normalizer or invented expected production response is provided. The source templates are test inputs; their acceptance by the local parser or remote compiler must be recorded separately.

## Release and budget prerequisites

Recording requires a reviewed exclusive Storage window after STORAGE-OBJECT, the actual effective release baseline saved privately, verified principal fixtures, an explicit compile/publish/settle procedure for each source, and restoration of the baseline release state with an effective-decision readback. The declared per-case ruleset is not automatically published by this module. A fresh ruleset may deliberately deny the subject request, so a future settle procedure needs independent evidence rather than treating a subject denial as proof of successful publication. If the baseline is absence, restoration requires absence readbacks rather than recreating STORAGE-OBJECT's removed rule.

`validateCorpus` counts declared Storage object and Firestore document API operations separately per recording, including conditional cleanup entries. Authentication, IAM, Rules source testing/publication/settling/restoration, retries, failure recovery, and a second recording are not included in those numbers. The management program declarations do not add an approved Rules request count. Later packets must partition and budget the full bounded procedure, including each of the 338 valid source tests, the invalid source test, and every release readback. This declaration grants no new production permission and cannot release the shared lock or close the parent.
