# Firestore write limits campaign preparation

`FS-DATA-WRITE-LIMITS-02` is an independent, owned-data campaign for the `FS-DATA-WRITE` parent. It covers four minimal cases: an accepted document-byte boundary, an immediately oversized document, an accepted nested boundary, and an immediately oversized nested document. The negative cases require typed refusal, typed absence readback, and unchanged accepted controls, so a transport status alone cannot complete the campaign.

The campaign uses a fresh nonce below `oracle/{freshNonce}/limits-02/` and does not mutate Rules, indexes, databases or shared settings. Its locks are a write lock for that owned document prefix and read locks for the default database indexes and ruleset. It can run beside unrelated campaigns when the nonce and resource lock checks pass. The original v1 proposal reserved 24 requests, 180 seconds wall time, and 90 seconds recovery. Those historical numbers are insufficient for the compiled operation sequence and must not be used for admission. The current local plan declares 16 observation operations and 12 recovery stages, four owned documents, one in-flight request, 420 seconds wall time, and 180 seconds recovery. Environment/credential preflight requests require a separate production allocation. The original proposed USD 1.00 planning ceiling is not tariff acceptance or a frozen permission envelope.

## FS-WRITE-LIMITS-03: the BatchWrite continuation residue and every write-path limit

`FS-WRITE-LIMITS-03` is a second, independent owned-data campaign on the same limits lane. It exists because the FS-DATA-WRITE receipt audit reduced the parent's open write conditions to a finite residue, and it covers all of it. Its machine-readable package is [`fs-write-limits-03.json`](../../spec/compatibility/broad-runs/fs-write-limits-03.json), its binding is [`fs-write-limits-03-binding.json`](../../spec/compatibility/broad-runs/fs-write-limits-03-binding.json), and its completed local execution record is [`fs-write-limits-03-local-shadow.json`](../../spec/compatibility/broad-runs/fs-write-limits-03-local-shadow.json). Production remains `unobserved`; nothing here promotes the parent.

It runs as two admitted parts. The Gate caps an allocation at 1,200 seconds of wall time, and the campaign declares a reservation per scheduled slot, taken from each request's own payload, rather than one plan-wide bound that could not be honest for a campaign mixing a megabyte upload with a cleanup read. That brings part A to 847 seconds and part B to 732, both well inside the ceiling, but it does not make one allocation possible: a combined campaign carrying all twenty-nine owned documents needs 1,277 seconds of schedule before any slack. The compiler refuses to compile it and a test pins both that refusal and the measured need. Part A carries the three BatchWrite continuation cases and the identifier and index limits over eighteen owned documents; part B carries the value and path limits over eleven. The split is arithmetic, not a reduction in scope, and each part takes its own fresh nonce.

The campaign covers sixteen cases. Three ask whether a BatchWrite is evaluated per position or refused as a whole: a three-write request whose middle item carries no operation, one whose middle value cannot be decoded into the protobuf, and the duplicate-document request that production is already recorded as answering with a whole-request 400. The other thirteen are the write-path catalog limits: collection id bytes, subcollection depth, document name bytes, the three index-entry limits, indexed field value bytes, field path bytes in three shapes, and field value bytes in three shapes. `FS-LIMIT-API-REQUEST-BYTES` is the one write-path surface left out, and it is assigned to the request-byte collector rather than dropped.

Only one index configuration change is required, and it is declared as an owner precondition applied by the executor before the run. The three index-entry boundaries are reached under the default single-field configuration, in which each field carries ascending, descending and array-membership modes at collection scope: the entry-bytes boundary is tuned with the document and parent document name bytes, since an entry is charged both; the entry-count boundary with the number of distinct array elements, since each one carries two membership entries; and the entry-sum boundary with both, plus a filler field whose name length is solved for. `FS-LIMIT-DOCUMENT-NAME-BYTES` is the exception, and only for documents that carry the ownership marker. The storage name charge reduces to 17 plus the relative path length, so it does not depend on how a name is split and is smallest when the final identifiers are as long as the identifier limit allows. At a 6,144-byte protocol name that floor is a name sum of 9,214 bytes, so the smallest entry any document with at least one indexed field can have is 9,249 bytes against a 7,680-byte maximum, and the smallest a marker-bearing document can have is 10,759. Every document this campaign owns must carry the marker for the Gate to verify and reclaim it, so none is writable at that name without an exemption; a document with no fields at all generates no entries and would be, which is why the claim is scoped rather than universal. The campaign declares a single-field exemption on its own collection group, `nx`, which cannot reach the padding collection the index cases use, and the manifest records the exact `fieldOverrides` entry, the digest of `conformance/firestore.indexes.json` before and after it, and the figures above as values the compiler computes rather than constants.

Two limits could not be written as an ordinary accept-then-refuse pair, and forcing them into that shape would have encoded behaviour production does not have. `FS-LIMIT-INDEXED-FIELD-VALUE-BYTES` is a truncating maximum: the catalog states that production truncates the indexed representation at 1,500 bytes, that the truncation is what the index-entry size limits are charged on, and warns against replacing it with a rejection. It is written as two accepted writes whose entries both sit exactly at the entry maximum under truncation, the second carrying a value twice the ceiling; if the indexed value were charged in full its entry would be 9,180 bytes and the write would be refused, so accepting both and reading both back with their values intact is what confirms that the truncation is of the index and not of the stored value. `FS-LIMIT-FIELD-VALUE-BYTES` is observable only through its refusal: 89 bytes separate it from `FS-LIMIT-DOCUMENT-BYTES`, and an owned name and marker cost more than that.

The aggregate field-value metric gets its own pair of cases, because the runtime reads the same maximum two ways one byte apart, which the catalog now records: a string or bytes payload on its raw length under either profile, a map or an array with the official storage-size formula under the strict profile only. A string-only document at the maximum has a raw payload exactly at it and a logical size one byte over, so a diagnostic naming the property says production reads an aggregate as logical bytes while a diagnostic about the document size says it reads raw payload bytes. A nested-map document one byte over makes the same distinction from the other side, because a map has no raw payload at all and the raw reading can never refuse it. Neither member of either pair can be accepted, so the diagnostic text is the evidence, and this campaign's comparator compares it. Every published boundary pair names the unit it is expressed in, because the catalog's `unit` field and its notes give different answers for this limit.

The field path is probed in three shapes: a path the client names in an update mask, a path a document implies by nesting maps, and a path a document implies through a map held inside an array. Automatic index accounting walks the second and never the third, so the catalog records the map shape as refused under both profiles and the array shape under the strict profile only. A path a client names is parsed per write, so the runtime reports an over-long update mask path as that write's own BatchWrite status; the production row `errors/rest-shapes#mask-with-invalid-path` is a Commit, which has no per-item statuses and so does not settle what a BatchWrite does. That row is where the campaign asks the R3 question for a field path.

Every case reads its implementation status, unit and boundary class from the catalog rather than restating them, so a case cannot drift from it. With the write-path lanes integrated, all nine limits are recorded as implemented and every expectation is derived from the runtime rather than from the catalog alone. One reason for a pending row survives: the local shadow supervisor pins a historical index configuration by commit and verifies its digest, so it cannot apply the declared exemption and the document-name rows show the index-entry refusal the exemption exists to remove. A pending row is also excused from the write-safety predicate, because a row the campaign cannot predict cannot serve as a local safety invariant. The manifest records the index configuration each shadow actually ran under alongside the one it declares, and states why the difference is immaterial to every other case.

A name that exceeds a request-stage identifier limit is not a resource the API will read back: a read of a 1501-byte collection id is refused with `INVALID_ARGUMENT`, not answered with a typed `NOT_FOUND`. Such names cannot be owned Gate resources, so they are probed instead, with a readback that must be refused exactly as the write was. The compiler refuses to emit any created document that would breach a limit it is not testing, and the one place where two limits genuinely cannot be separated is declared in the case with its reason.

The envelope is 122 requests and 52,200 micro-USD for part A and 78 requests and 47,800 micro-USD for part B, each against the standing 1.00 USD planning cap. The published data cost is a breakdown of the per-request tariff the envelope already charges, not an additional term. `collector.py`, `comparator.py` and `compiler.py` are byte-for-byte unchanged, so the frozen limits-02 digests still resolve. The new campaign lives in sibling modules: `compiler_03.py`, `expectations_03.py`, `collector_03.py`, `comparator_03.py`, `shadow_03.py` and `shadow_03b.py`.
