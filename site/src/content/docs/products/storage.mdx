Fireemu serves Cloud Storage for Firebase at `127.0.0.1:9199`, with both API dialects:

- the Firebase Storage protocol the client SDKs use, including resumable uploads and download tokens;
- the Cloud Storage JSON API the Admin SDK and the Google Cloud client libraries use, including copy and rewrite.

Both dialects share one store, so an object uploaded through one is visible through the other. The Storage emulator keeps its objects in memory.

## Connect

Storage listens on `127.0.0.1:9199` by default (`--storage-port` or `firebase.json` changes it).

```js
// Web SDK
import { getStorage, connectStorageEmulator } from 'firebase/storage';
connectStorageEmulator(getStorage(app), '127.0.0.1', 9199);
```

The Admin SDK and the Google Cloud client libraries read environment variables. Under `fireemu exec` they are set for your command; with `fireemu up`, set them yourself:

```sh
STORAGE_EMULATOR_HOST=http://127.0.0.1:9199             # with the scheme
FIREBASE_STORAGE_EMULATOR_HOST=127.0.0.1:9199           # host:port, no scheme
```

See [Connect your app](../../getting-started/connect/) and the [environment variables](../../reference/environment-variables/).

## Configure

All Storage settings are optional. This file sets each of them:

<Tabs syncKey="config-format">
<TabItem label="TOML">

```toml
schemaVersion = 1
profile = "strict"

[storage]
# Path of the Storage Security Rules file (or name it in firebase.json)
rules = "storage.rules"
# Which default bucket exists: "both" (default), "firebasestorage.app" or "appspot.com"
defaultBucket = "both"
# Buckets the project owns besides its default ones: 3 to 222 characters each
buckets = ["uploads-bucket", "exports.example.com"]
# Buckets whose objects the public URL serves without a credential: 3 to 222 characters each
publicBuckets = ["public-assets.example.com"]
# Local cap on stored object data in bytes (an integer of at least 1); unset means no cap
maxStoredBytes = 1073741824
```

</TabItem>
<TabItem label="JSON">

```json
{
  "schemaVersion": 1,
  "profile": "strict",
  "storage": {
    "rules": "storage.rules",
    "defaultBucket": "both",
    "buckets": ["uploads-bucket", "exports.example.com"],
    "publicBuckets": ["public-assets.example.com"],
    "maxStoredBytes": 1073741824
  }
}
```

</TabItem>
</Tabs>

| Setting | Effect |
|---|---|
| `storage.rules` | The Storage Security Rules file; see [Security Rules](#security-rules). |
| `storage.defaultBucket` | Which of the project's two default buckets exist under `strict` ([below](#buckets-that-do-not-exist)). |
| `storage.buckets`, `storage.publicBuckets` | Declare buckets, and buckets whose public URL needs no credential. Ignored by the `emulator` profile. |
| `storage.undeclaredBuckets` | What an object operation on a bucket nothing declared does under `strict`: `"warn"` (default) serves the first write, creates the bucket and prints one note; `"create"` does the same silently; `"refuse"` answers production's 404 ([below](#buckets-that-do-not-exist)). The `emulator` profile always creates the bucket silently. |
| `storage.cors` | Per-bucket CORS configuration in the Cloud Storage `cors` JSON, applied under `strict` ([below](#bucket-cors)). A bucket that is not listed keeps the permissive answer. |
| `storage.signedUrlKeys` | Public keys (or the private key or service-account JSON a test signed with) that V4 signed URLs are verified against under `strict` ([below](#signed-url-signatures)). Unset, the signature is not verified. |
| `storage.maxStoredBytes` | A local cap on stored bytes. A write that would pass it is refused with HTTP 402 (`storage.maxStoredBytes limit exceeded`); see [Limit the stored bytes](#limit-the-stored-bytes). Production has no such limit. |
| `storage.maxObjectBytes` | Per-object size limit, default 256 MiB (maximum 2143289343). Larger uploads are refused with HTTP 413; see [Limit the stored bytes](#limit-the-stored-bytes). |
| `storage.bufferedBodyBudgetBytes` | Process-wide budget for buffered request bodies, default 1 GiB. A request past it gets HTTP 503 with `Retry-After: 1`. |

## Buckets that do not exist

Production answers 404 `The specified bucket does not exist.` for an object operation on a bucket nobody created. The Storage emulator serves it instead, and creates the bucket on the first write, so a test needs no setup; `storage.undeclaredBuckets` changes that under `strict`. Under `strict` it prints one `note:` line on standard error the first time an object is written to a bucket that is not a default bucket of the project (`<project>.appspot.com` or `<project>.firebasestorage.app`), a `firebase.json` storage target, imported data, a bucket a deployed Storage trigger names, or listed in the configuration. A typo in a bucket name is visible that way. To silence the note for a bucket that exists in production, list it in `storage.buckets` ([Configure](#configure)).

To make a bucket-name typo fail the test, set `storage.undeclaredBuckets` to `"refuse"` (`strict` only; `"warn"` is the default, `"create"` is the `warn` behaviour without the note). Every operation that names a bucket which does not exist is then answered as Cloud Storage answers it, and nothing is created: on the JSON API 404 `The specified bucket does not exist.` (reason `notFound`), on the XML API and the form upload 404 `NoSuchBucket`, on the Firebase API (`/v0`) the not-found answer it gives for a bucket it cannot reach. A copy or rewrite checks both of its buckets, and a resumable upload is checked when it starts. A bucket exists when it is a default bucket, is listed in `storage.buckets` or `storage.publicBuckets`, is a `firebase.json` storage target, is named by a deployed Storage trigger or holds imported data.

- **Measured against production.** The JSON API's 404 for the bucket resource (`GET /storage/v1/b/{bucket}`) was recorded. The answers of the object routes on a missing bucket, the XML API's `NoSuchBucket` body and the Firebase API's answer follow Cloud Storage's documented shapes and have not been observed. The `emulator` profile rejects `"warn"` and `"refuse"`, because the official emulator creates every bucket on first use.

Each name must be one Cloud Storage accepts. `storage.publicBuckets` lists buckets whose objects the public URL serves without a credential, and also counts as declaring them. `storage.buckets` and `storage.publicBuckets` are ignored by the `emulator` profile.

A production project has one default bucket: `<project>.firebasestorage.app` if Storage was set up after 2024-10-30, `<project>.appspot.com` before. A local run cannot know which, so both exist by default. To catch an app configuration copied from the other kind of project, set `storage.defaultBucket` to `"firebasestorage.app"` or `"appspot.com"` (default `"both"`): the other name then counts as an undeclared bucket, so its first write prints the note and `GET /storage/v1/b/{bucket}` answers 404.

## Bucket CORS

Production answers a browser's cross-origin request according to the bucket's CORS configuration, and a new bucket has none, so a page that uploads or downloads in Playwright against a permissive local server can fail in production. Under `strict`, `storage.cors` maps a bucket name to its rules in the Cloud Storage `cors` JSON:

```json
{
  "storage": {
    "cors": {
      "demo-app.appspot.com": [
        {
          "origin": ["http://localhost:3000"],
          "method": ["GET", "PUT"],
          "responseHeader": ["Content-Type", "x-goog-content-length-range"],
          "maxAgeSeconds": 3600
        }
      ]
    }
  }
}
```

A bucket that is listed follows its rules; a bucket that is not listed keeps the permissive answer, and `[]` is a bucket with no CORS configuration, as a new bucket in production is. For a request that carries an `Origin`, the first rule whose `origin` (or `*`) and `method` (or `*`) match decides:

- An actual request gets `Access-Control-Allow-Origin` (the origin, or `*` for a rule that lists `*`), `Vary: Origin` when the origin was echoed, and `Access-Control-Expose-Headers` for the `responseHeader` list.
- A preflight (`OPTIONS`) additionally needs every header in `Access-Control-Request-Headers` to be in `responseHeader` (or `*`), and then also gets `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers` and `Access-Control-Max-Age` (`maxAgeSeconds`, 3600 when unset).
- A request no rule matches is answered without any CORS header, and succeeds all the same: the browser refuses to hand the answer to the page.

The rules apply to the JSON API, the XML API (including signed URLs and the form upload) and the media reads of the Firebase API (`alt=media`, which is what a download URL is). The Firebase API's JSON answers and its resumable protocol keep the permissive answer, because the Firebase API sends its own CORS headers for them. The server still refuses a request whose `Origin` is not a local one (403), whatever a rule lists, so a rule is exercised by a page served from `localhost` or a loopback address. The `emulator` profile rejects the key, because the official emulator ignores bucket CORS.

- **Measured against production.** On a bucket with no CORS configuration, the XML API answered an `OPTIONS` preflight and a `PUT` with an `Origin` with `200` and no `Access-Control-*` header (two recordings). Everything about a bucket that has rules follows Cloud Storage's documentation and was not observed: whether `*` is answered as `*` or as the echoed origin, the value of `Access-Control-Allow-Methods`, the default `maxAgeSeconds`, the status of a preflight no rule matches, and the Firebase API's media reads with a configuration.

## Signed URL signatures

Cloud Storage verifies a V4 signed URL against the signing service account's public key. fireemu has no such account, so by default it checks the expiry and the signed headers' presence but not the signature. To check it, register the key a test signs with in `storage.signedUrlKeys`, a list of file paths: a PEM public key, a PEM private key (only its public half is kept), a service-account JSON (`private_key`, `client_email`) or an RSA JWK. Under `strict`, a V4 request whose signature does not verify is answered `403 SignatureDoesNotMatch` with the `StringToSign` and `CanonicalRequest` the server calculated, the body production gave when a signature was altered, when the `Content-Type` or the range header differed from the signed one, and when the object name differed (four recorded causes). The canonical request is the one Cloud Storage documents: the method, the percent-encoded path, the sorted query without `X-Goog-Signature`, the signed headers with their values (`host` is the `Host` the request arrived with, with or without its port: the Admin SDK signs the host name alone for a local endpoint, so a URL it builds verifies as it is), the signed header list and `UNSIGNED-PAYLOAD`. A key file that cannot be read, is not RSA or is shorter than 2048 bits stops the start. A service account's `client_email` ties its key to that account's credentials. Only public keys are kept in memory and nothing about a key is logged.

V2 signed URLs are not verified, only the signed headers the server reads (`Content-Type`, `x-goog-content-length-range` and the other headers it forwards) can be part of a signature that verifies, and the `emulator` profile rejects the key. This is a local check of what a test signed, not an authorization boundary.

## Security Rules

Storage Security Rules are read from the `storage.rules` file named in `firebase.json`, or `storage.rules` in `fireemu.toml`. A Storage rule can read Firestore documents with `firestore.get()` and `firestore.exists()`. Under `strict`, a project without rules refuses every end-user request with production's 400 "bucket has not been set up" answer. See [Security Rules](../../guides/security-rules/).

## Production behavior

Under `strict`, generation and metageneration preconditions and declared checksums are honored as production honors them. The official emulator verifies no checksum.

Under `strict` the Storage emulator also refuses what production refuses and the official emulator accepts (a bucket that does not exist is the exception, see [Buckets that do not exist](#buckets-that-do-not-exist)). In short:

| Request | `strict` answer |
|---|---|
| End-user request in a project without Security Rules | 400, "bucket has not been set up" |
| `GET /{bucket}/{object}` (public URL) for a private object | 403 `AccessDenied` |
| Signed URL past its lifetime | 400 `ExpiredToken` |
| Signed upload: a signed header missing, a body outside the signed range, an unsigned upload | 400 `MalformedSecurityHeader`, `EntityTooLarge` or `EntityTooSmall`; an unsigned upload is refused |
| Signed URL naming every signing parameter but the signature | 400 `MissingSecurityHeader` |
| Form upload without a signed policy | Refused; the policy's expiry and conditions are enforced |
| Firebase ID token as an OAuth bearer on the JSON API | 401 `Invalid Credentials` |
| An ACL entry Cloud Storage does not know | 400 |
| A bucket name Cloud Storage never accepts | 400 `Invalid bucket name` (JSON API), 400 `InvalidBucketName` (XML routes), 404 (Firebase routes) |
| Write past `storage.maxStoredBytes` (a local cap, not a production rule) | 402 `storage.maxStoredBytes limit exceeded` |

The details of each refusal follow; nothing is omitted from them.

<details>
<summary>A public URL for a private object</summary>

`GET /{bucket}/{object}`, which is what `file.publicUrl()` builds, answers 403 `AccessDenied` unless the request carries a non-empty `Bearer` `Authorization` header, comes from a Google client library (these send `x-goog-api-client`, and the Go library, so the Firebase Admin Go SDK, reads through this URL with no credential while `STORAGE_EMULATOR_HOST` is set; the Python, Java and Node libraries read through the JSON API and are never refused), is a signed URL that has not expired, or the object is public. An object is public when application code made it so (`file.makePublic()`, `predefinedAcl=publicRead` on an upload, patch, copy (`destinationPredefinedAcl`) or rewrite, an `allUsers` `READER` entry in the `acl` of an uploaded or patched resource, or `POST .../acl`), for that generation of the object only: an overwrite is private again. `file.makePrivate()` (`predefinedAcl=private`), a patched `acl` without that entry and `DELETE .../acl/allUsers` end it. An `acl` in the metadata that starts a resumable upload is not read. A bucket whose IAM grants `allUsers` the object viewer role, which production sets in the console, is listed in `storage.publicBuckets`. The 403 names both ways. Firebase download-token URLs are not affected.

</details>

<details>
<summary>An expired signed URL</summary>

A V4 or V2 signed URL past its lifetime answers 400 `ExpiredToken`, and a V4 lifetime over seven days or an unreadable `X-Goog-Date` answers 400. The signature itself is not verified unless `storage.signedUrlKeys` registers the key it was made with ([Signed URL signatures](#signed-url-signatures)), because that needs the signing service account's key; without one, any signature is accepted.

</details>

<details>
<summary>Signed XML uploads</summary>

`PUT /{bucket}/{object}` accepts a V4 signed URL for local uploads. Set `FIREBASE_STORAGE_EMULATOR_HOST` to the host and port without a scheme, or `STORAGE_EMULATOR_HOST` to the HTTP URL, before initializing the Admin SDK. The SDK still needs signing credentials; a locally generated test service account key can be used for development. Strict mode rejects an unsigned upload. This upload path stores `Content-Type`; other object metadata and conditional write headers are not supported. Only `Content-Type` and `x-goog-content-length-range` are forwarded for this use; arbitrary signed extension headers are not supported. The range is inclusive.
- **Measured against production** (a real Firebase project, 2026-11-03, `getSignedUrl` V4 `write` for `image/png` with `x-goog-content-length-range: 0,10485760`, two recordings of 16 cases). A signed header missing from the request is `400 MalformedSecurityHeader` naming it (`content-type` and the range header were measured). A body above or below the range is `400 EntityTooLarge` or `400 EntityTooSmall`. An expired URL is `400 ExpiredToken` naming the end of the signed lifetime. These refusals, and the success headers (`ETag`, `x-goog-generation`, `x-goog-metageneration`, `x-goog-hash`, `x-goog-stored-content-length`, `x-goog-stored-content-encoding`), have production's body and values in both profiles. Under `strict`, a URL that names every signing parameter but the signature is `400 MissingSecurityHeader`, and the range header sent without being among the signed headers is `400 MalformedSecurityHeader`; the `emulator` profile keeps accepting both, as it did before (what firebase-tools 15.28.2 does with them was not measured).
- **Not verified by default, a documented difference.** Production answers `403 SignatureDoesNotMatch` when the signature is altered, when the `Content-Type` or the range value differs from the signed one, and when the object name differs from the signed one. fireemu has no key to check a signature with unless `storage.signedUrlKeys` registers one (see [Signed URL signatures](#signed-url-signatures)), and otherwise accepts all four in both profiles, so changes to the method or signed header values cannot be authenticated; do not use this behavior as an authorization check. Without `storage.cors`, CORS is permissive in both profiles: a successful `OPTIONS` preflight answers `204` with CORS headers, and a `PUT` that carries an `Origin` gets them. Production depends on the bucket's CORS configuration and answered `200` with no CORS headers for a bucket that has none; list the bucket in `storage.cors` to get that under `strict` ([Bucket CORS](#bucket-cors)).
- Under `strict`, every occurrence of `X-Goog-SignedHeaders` is enforced, including repeated, differently cased and percent-encoded names. Conflicting repeated `X-Goog-Date`, `X-Goog-Expires` or `Expires` values return `400 InvalidArgument`; remove the conflicting parameters. That refusal has not been observed in production. The `emulator` profile keeps its existing query interpretation.

</details>

<details>
<summary>A form upload without a signed policy</summary>

`POST /{bucket}` with a multipart form needs a `policy` and a signature field. The policy's expiry and conditions (`bucket`, `eq`, `starts-with`, `content-length-range`) are enforced; the signature is not verified.

</details>

<details>
<summary>A Firebase ID token as an OAuth bearer</summary>

on the JSON API: 401 `Invalid Credentials`. Any other credential, or none, is served as the owner, because a local run cannot judge an access token.

</details>

<details>
<summary>An ACL entry Cloud Storage does not know</summary>

(400). Only `allUsers` with role `READER` has an effect.

</details>

<details>
<summary>A bucket name Cloud Storage never accepts</summary>

(for example `ab`, `goog-x` or `1.2.3.4`): 400 `Invalid bucket name` on the JSON API, 400 `InvalidBucketName` on the XML routes and 404 on the Firebase routes, unless a bucket of that name exists (imported or declared).

</details>

The `emulator` profile retains its existing behavior except for the signed-upload responses described above; those responses follow production, and official-emulator parity for them is not claimed.

In both profiles, a Firebase Storage request (`/v0/b/{bucket}/o/...`) whose object name or list prefix has an empty path segment, such as an interior `//`, a leading `/` or a trailing `/` on an object name, answers `400` with `The path may not end with '/' or contain two consecutive '/'s` before any Security Rule is evaluated. Production answered reads, metadata reads and lists this way on 2026-11-08, also under an allow-all rule; uploads, `PATCH`, `DELETE` and token management follow from that and were not recorded. The `strict` profile keeps `/x`, `x` and `x/` as three objects, as Cloud Storage does; the `emulator` profile still drops one leading `/` of an uploaded name, as the official emulator does. A Firebase list leaves out a prefix that an object like `a//x` would produce, and a name it leaves out never takes a place in a page or becomes a `nextPageToken`.

### Listing a prefix with single-segment attachment rules

**Why this matters.** A `list` rule is decided from the requested prefix, not from the objects that happen to exist. A rule that passes in a test because every current object matches it can be refused by production once the prefix is listed. Under `strict` Fireemu evaluates `list` the way production does, using the outcomes recorded below (two production recordings from 2026-10-16 and the 2026-11-08 observations), so such a rule fails in a local test too, before you deploy.

In the `strict` profile, list authorization proves access to the possible entries under the requested prefix. With `delimiter=/`, each entry is one immediate child; without a delimiter, entries can have arbitrary depth. Authorization does not depend on whether the prefix is empty or on which objects happen to exist.

For `prefix=teams/T/requests/R/&delimiter=/`, a rule matching `/teams/{team}/requests/{id}/{attachment}` with `allow list: if member(team)` can authorize the listing. The team and request ID are fixed by the prefix, while the attachment name is unknown. A condition requiring a particular attachment name does not authorize a directory listing merely because all current objects match that name.

A targeted production comparison on 2026-10-16 used authenticated UID-to-team membership, separate upload/get controls and two recordings. `strict` matches the following observed outcomes. The ancestor prefix is `teams/T/requests/`; the request prefix is `teams/T/requests/R/`.

| Rules granting `list` to the member | Prefix | Delimiter | Production and `strict` |
| --- | --- | --- | --- |
| Single attachment capture | Request | `/` | 200 |
| Single attachment capture | Request | Omitted | 403 |
| Same rules plus explicit parent match | Request | `/` | 200 |
| Same rules plus explicit parent match | Request | Omitted | 403 |
| Same rules plus explicit parent match | Ancestor | `/` | 200 |
| Same rules plus recursive `list` match | Request | `/` or omitted | 200 |
| Same rules plus recursive `list` match | Ancestor | `/` | 200 |

Empty request prefixes have the same authorization decisions as populated ones. Non-member, anonymous and other-team request listings remain denied. The `emulator` profile retains its existing concrete-prefix authorization, except that a listing with `delimiter=/` is allowed when every entry one level below the prefix is allowed (`match /p/{f} { allow list: if true; }` with `prefix=p/&delimiter=/`), as production and `strict` allow it. Non-slash delimiters use a conservative arbitrary-depth proof; the production comparison covered `/` and an omitted delimiter, not every custom delimiter or resource-dependent condition. The [Firebase granular operations documentation](https://firebase.google.com/docs/storage/security/core-syntax#granular_operations) provides further background.

In the `strict` profile, a listing without a delimiter is also allowed for `allow list: if [file] != null` and for `request.path == /b/$(bucket)/o/<prefix>` under `match /p/{file=**}`, as production answered on 2026-11-08. A single-segment capture, a bare capture and the path of another prefix are still refused, and `request.path` of a delimited listing stays refused until production is recorded for it.

An explicit parent rule is not needed for the single-capture SDK request above. Adding one can change production permissions:

```text
match /teams/{team}/requests/{id} {
  allow list: if member(team);
}
```

In the measured rules, this also permits listing the ancestor's child prefixes. It does not authorize delimiter-free recursive enumeration of the request's attachments. Keep attachment `get`, `create`, `update` and `delete` conditions unchanged. Do not replace them with a broad recursive `allow read`: `read` includes both `get` and `list`. Listing permission exposes names under the prefix even when a particular object's content cannot be read; it does not grant content access or filter the list to objects with `get` permission.

## Limit the stored bytes

Each object is limited to 256 MiB by default. Set `storage.maxObjectBytes` to change that limit; the HTTP request body limit is 4 MiB larger to allow multipart overhead. `storage.bufferedBodyBudgetBytes` bounds the request bodies buffered across the process and defaults to 1 GiB. Requests that exceed the available budget receive HTTP 503 with `Retry-After: 1`. Both settings accept positive whole numbers of bytes; the maximum is 2143289343 for `maxObjectBytes` and 2147483647 for `bufferedBodyBudgetBytes`. A budget smaller than a request can refuse it even when the object is within its limit. Resumable uploads also have a separate 1 GiB aggregate retained-upload limit, and import has a separate 1 GiB total limit.

The Storage emulator keeps every object in memory, and by default nothing bounds how much. To cap it, set `storage.maxStoredBytes` to a number of bytes of at least 1 ([Configure](#configure)). This limit is local to Fireemu; production has none.

- Each object counts its bytes once, and a copy counts again. Replacing an object counts only the difference in size.
- An upload, a resumable upload's final request or a copy that would grow the total past the limit is refused with HTTP 402 and the message `storage.maxStoredBytes limit exceeded` (in the JSON API, with the reason `storageCapacityExceeded`). There is no `Retry-After`. Delete objects to make room. The Firebase client SDKs report a 402 at once as `storage/quota-exceeded` without retrying; the Cloud Storage client libraries do not retry it either.
- A write that does not grow the total, such as an equal or smaller replacement, always passes, even while the store holds more than the limit (after an import, a restore or a lowered limit).
- A refused write changes nothing. A resumable upload stays open: its offset does not advance, so you can send the same final chunk again after making room, or cancel the upload.
- An import (`--import`) and a snapshot restore are not checked against the limit. An import above it starts with a `warning:` line naming the stored bytes and the limit, and a snapshot restore above it logs the same line.

`fireemu doctor --connect <control URL>` reports the stored bytes as `objects.bytes` against this limit.

## Not supported

Verifying the signature of a signed URL or a POST policy, object ACLs other than `allUsers` read, IAM and bucket-level public access, object composition (`compose`) and notification configuration are not supported. Object versioning is served on the JSON API: `PATCH /storage/v1/b/{bucket}` with `{"versioning":{"enabled":true}}` turns it on, as in production.

:::caution[Keep the Storage port on localhost]
Like the official emulator, the Storage port reflects the requested object name in the HTML body of its 404 for a missing media read. A web page opened on your machine could run script on that origin.

- By default every listener is on loopback, so only processes on your machine reach it. The Host guard also answers a request that names a `Host` other than `localhost`, an IP address or a name you listed in `network.allowedHosts` with 403, as a defence against DNS rebinding (see [Host names the emulators answer](../../guides/ci-and-containers/#host-names-the-emulators-answer)).
- The port is reachable from other hosts only if you opt in: `network.allowNonLoopbackHosts` in `fireemu.toml` together with a non-loopback `emulators.storage.host` in `firebase.json` (see [Serve the emulators from a container](../../guides/ci-and-containers/#serve-the-emulators-from-a-container)). Such a listener serves without a credential, so do not expose it on an untrusted network.
- The `strict` profile sends no `X-Content-Type-Options: nosniff` on the JSON API answers where production sends none, so it does not add that defence in depth; the `emulator` profile keeps the official emulator's header.
:::
