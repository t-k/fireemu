# Production Query Explain campaign 01

This package prepares one bounded production comparison for six Firestore Standard REST Query Explain recipes: `runQuery` and `runAggregationQuery`, each in plan-only, analyze and empty-analyze forms. The campaign owns exactly two fresh-namespace documents. Each run records absence preflight, conditional creation, typed observations, state readback, journaled conditional deletion and final 404 receipts.

The fixed manifest is [prod-campaign-explain-01.json](../../spec/compatibility/broad-runs/prod-campaign-explain-01.json). Thin campaign Gate, ProductionGate and DataAdapter classes bind the same campaign observer digest while reusing the existing shared scheduler, adapter transport, ownership journal and credential coordinator. Historical shared collectors retain their admission behavior. Campaign cleanup additionally requires a durable, typed successful `exists=false` creation receipt for the exact path. DELETE is restricted to that creation updateTime. A conflict, ambiguous response, malformed creation receipt or replacement version retains uncertainty and cannot authorize deletion. The generic shared collector requires a separate ownership-race repair before reuse by later campaigns. The strict campaign validator checks each side independently against the concrete manifest before comparing responses, including when both sides contain the same wrong request.

The scope is six cases, 18 observation requests, 12 recovery requests and 30 total requests at concurrency one. The wall ceiling is 1,200 seconds with 300 seconds reserved for recovery. The internal ceiling is 10,000 micro-USD (USD 0.01). Thirty requests at 100 micro-USD each plus a 1,000 micro-USD fixed reserve produce a 4,000 micro-USD planning bound. Reviewed [Firestore pricing](https://firebase.google.com/docs/firestore/pricing) and [Query Explain pricing](https://firebase.google.com/docs/firestore/query-data/query-explain) sources, the 2026-09-14 check date, location and tariff inputs are bound into the accepted configuration.

The accepted configuration also binds the saved raw database response digest and `database-settings-v2` semantic projection, Auth digest, API-key digest and ownership, and owner/cost/recovery permission baseline. The raw response is retained for audit; only the reviewed v2 exclusions (`etag` and `earliestVersionTime`) may change during live database preflight. Live metadata must match this baseline. A new response never silently becomes the approved baseline. API-key bytes and credentials are never included in the package.

Commit all reviewed changes before running the local shadow, then run this exact command from the repository root with a fresh output directory:

```sh
uv run --project tools/compat-inventory --locked --python 3.12 python tools/compat-broad/campaign_explain_shadow.py --output /absolute/private/campaign-explain-shadow
```

The shadow invokes `broad.run` and `broad.supervise` to build the current artifact and execute the campaign against real local Auth and Firestore listeners. All ports use OS allocation (`0`). It records the actual executable/configuration hashes, parent/child identities, listener origins, request dispatch, state and cleanup receipts. The supervisor stops the owned processes and verifies listener closure before writing the envelope to `result.json`. `shadow-hashes.json` indexes the private artifact, input, process and cleanup files. No fixture wire or Cloud request is used. Local control identity checks are separate from the production request budget.

Production requires a current permission for the clean frozen commit, the validated local envelope's canonical typed JSON digest, matching accepted configuration, verified credential lifetime and a fresh generated 32-hex nonce. The permission reference is `conversation-2026-09-14-autonomous-production-under-usd10`; the checked-in manifest itself is not executable permission. The `--execute --permission ... --local .../result.json --output ...` command validates the full local envelope and companion files before consuming a nonce or acquiring credentials. It persists the production result and immediately writes `comparison.json` in the same lifecycle. Complete semantic differences remain `mismatch` evidence and return zero; incomplete collection, source/configuration/binding drift or missing cleanup returns `indeterminate` and a nonzero exit. Comparison normalizes owned namespaces and typed absolute times using the existing Firestore normalizer; other response differences remain visible.
