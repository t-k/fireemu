## Start in one command

Node.js 20 or newer is required. Fireemu is published on npm as [`fireemu`](https://www.npmjs.com/package/fireemu).

<Tabs>
<TabItem label="Automated tests (CI/local)">

```sh
npm install --save-dev fireemu
npx fireemu init

# Run your tests against the emulators, then stop them
npx fireemu exec -- npm test
```

`init` creates `fireemu.toml` (see [Install and run](getting-started/install/#create-fireemutoml)). `exec` starts the emulators, sets the Firebase SDK emulator environment variables for your command, stops the emulators when the command ends, and exits with its status.

</TabItem>
<TabItem label="Local development & UI">

```sh
npm install --save-dev fireemu
npx fireemu up
```

`up` keeps the emulators running until you press `Ctrl+C`, with the Emulator UI at `http://127.0.0.1:4000/ui/` (port 4000; change it with `--ui-port`, or use `--ui-port 0` for no UI). Without `fireemu.toml`, `up` uses the `firebase.json` it finds in the project, or built-in defaults.

</TabItem>
</Tabs>

## Why Fireemu

<CardGrid>
	<Card title="Behaves like production" icon="approve-check">
		Under the recommended `strict` profile, a query with no composite index fails as it does in production, with the same error. The few [development defaults](guides/profiles/#where-fireemu-departs-from-production-on-purpose) are documented and can each be switched. See [Why Fireemu](getting-started/why-fireemu/) for a comparison with the Local Emulator Suite.
	</Card>
	<Card title="Verified against real Firebase" icon="magnifier">
		<VerifiedAreaCount /> areas, from Firestore transactions to Storage Security Rules, are compared with recordings from real Firebase projects.
	</Card>
	<Card title="Built for tests" icon="puzzle">
		TOTP multi-factor authentication and App Check debug tokens, which the official emulator does not provide, a virtual clock for scheduled functions, and Security Rules denials that show each evaluated condition.
	</Card>
	<Card title="Small and quick to start" icon="rocket">
		A single native binary. In one benchmark run on a GitHub Actions Linux runner, Fireemu started 21.6x faster than the official Firestore emulator and used about 1/34th of its idle memory ([conditions and details](compatibility/performance/)).
	</Card>
</CardGrid>

## Supported products

| Product | Status | What you can test |
|---|---|---|
| [Cloud Firestore](products/firestore/) | <Badge text="Supported" variant="success" /> | Standard and Enterprise editions, composite index validation, Security Rules |
| [Firebase Authentication](products/auth/) (Identity Platform) | <Badge text="Supported" variant="success" /> | Sign-in methods, TOTP and SMS MFA, multi-tenancy, OIDC and SAML providers, blocking functions |
| [Cloud Storage for Firebase](products/storage/) | <Badge text="Supported" variant="success" /> | Firebase and JSON APIs, Security Rules |
| [Cloud Functions for Firebase](products/functions/) | <Badge text="Supported" variant="success" /> | HTTP, callable, event, scheduled, task queue and blocking functions, from Node.js codebases and, on macOS and Linux, [Python codebases](products/functions-python/) |
| [Cloud Pub/Sub, Eventarc](products/pubsub-eventarc/), Cloud Tasks | <Badge text="Supported" variant="success" /> | Topics, subscriptions, push and pull delivery, custom events, task queues |
| [Firebase App Check](products/app-check/) | <Badge text="Local testing" variant="note" /> | Debug tokens |
| [Firebase Realtime Database](products/realtime-database/) | <Badge text="Partial" variant="caution" /> | REST, realtime protocol, Security Rules, export and import, Functions triggers |
| [Firebase Hosting](products/hosting/) | <Badge text="Partial" variant="caution" /> | One `firebase.json` site: static files, redirects, rewrites (including to local functions), headers, clean URLs, localization |
| App Hosting, Data Connect | <Badge text="Not yet supported" variant="default" /> | |
| Firebase Extensions | <Badge text="Not planned" variant="danger" /> | |

**Partial** means served, with a narrower production claim: the Realtime Database is verified against production for recorded cases only, and Hosting is served without a production parity claim yet. Details are in [Limitations](compatibility/limitations/#partially-supported-products). The [compatibility tables](compatibility/) show the production verification status of each area.

The default `strict` profile can refuse requests the official emulator completes, such as a query without its composite index; the [migration guide](getting-started/migrate/) lists these and the other differences.
