# FS-CONFIG-LIFECYCLE management-contract campaign preparation

Status: `PREPARATION_ONLY`. Parent group `FS-CONFIG-LIFECYCLE` stays `WAITING_ORACLE`. Production-unobserved conditions reduced: **0**. Parent promotions: **0**. The campaign described here has not run against production, no credential was acquired, and no existing receipt, manifest, index configuration or comparison count changed. One local rehearsal against an owned fireemu is recorded below; it is local evidence and nothing else.

This page prepares the second half of the blocking condition on the `FS-CONFIG-LIFECYCLE` row of [the parent table](ip-fs-production-compatibility.md): a bounded, cheap and reversible observation of representative management behavior. The classification that answers the first half is in [the surface classification](fs-config-lifecycle-classification.md). Nothing here is an owner permission; the permission is a separate artifact this repository does not contain.

## Scope decision of 2026-09-18

The first revision of this campaign planned 25 cases, thirteen of which created, deleted or probed creation of a named database (OC-03 to OC-12 and OC-23 to OC-25). Creating and deleting databases is managed infrastructure, and the plan required a pay-as-you-go billing contract; both are excluded by the owner scope decision recorded in [the parent table](ip-fs-production-compatibility.md) under "Scope decisions". Those thirteen cases are dropped, not renumbered, so the surviving identifiers keep their meaning across both revisions. The manifest records the decision, and a test asserts that no case and no required permission names `databases.create`, `databases.delete` or `databases.update`.

## What the campaign observes

12 abstract cases, compiled by `tools/compat-broad/fs-config-lifecycle/cases.py` from one 32-character hexadecimal nonce. Every case's request keys are checked against the parameters and request body the pinned Discovery document declares for that method, so a request carrying a parameter the API does not have cannot reach a run.

| Group | Cases | What it separates |
| --- | --- | --- |
| Inventory controls | OC-01, OC-02 | The default database projection, whose digest must equal the frozen baseline before anything is patched, and the enumeration the closing reconciliation compares against. |
| Time-to-live | OC-13, OC-14, OC-15, OC-16 | Baseline capture, the patch that enables a time-to-live policy, the readback, and the revert. |
| Single-field exemption | OC-17, OC-18, OC-19, OC-20 | Baseline capture, the patch that exempts a field from single-field indexing, the readback, and the revert. |
| Enumeration and operations | OC-21, OC-22 | The filtered field listing and the bounded poll of the operation the time-to-live patch returned. |

The two configuration changes are locked steps. Each step is a baseline read whose body digest and body reference are saved, the patch, a bounded poll of the operation it returned, a readback, the revert, and a verifying readback whose digest must equal the baseline digest. The execution order is OC-01, OC-02, OC-13, OC-14, OC-22, OC-15, OC-16, OC-17, OC-18, OC-19, OC-20, OC-21; a revert always follows the readback of the patch it reverts. Ownership is journaled before a patch leaves: the step is recorded as uncertain under the gate lock before the send, downgraded to not applied only when the gate refused before the wire, upgraded to applied only from a complete 2xx whose operation name parses, and recorded as refused only for a typed 4xx or a typed 501 `UNIMPLEMENTED`, the one 5xx that proves the method is not served. A 500, 503 or 504, an untyped answer, a 2xx without an owned operation name or an exception at the patch line all leave the field owned, and recovery reverts it.

Every case carries the expected local result, read from the classification matrix rather than from a running process. The `indexConfig` half of `fields.patch` is refused locally with `UNIMPLEMENTED` (`FS-CONFIG-RT-004`), so OC-18 is expected to be refused and OC-19 and OC-20 to be unreached on the local side. That expectation is a statement about this source tree, not about production, and the comparator reports it as an expected local deviation rather than a match or a mismatch.

## Scope, cost and isolation

The run creates no database, patches exactly two field configurations, and performs zero document operations. No document is read, written or deleted, and the two patches build single-field index entries over empty collection groups. The estimated tariff is 0 micro-USD. The shared Ledger still charges one micro-USD of admission allowance per request, so the reservation is 128 micro-USD, the request bound, under the hard ceiling of 1,000,000 micro-USD (US$1.0), which exists only so that an unexpected metered charge stops the run rather than letting it continue.

The bounds are enforced, not declared. `lifecycle_gate.py` charges every request before it is sent and refuses one that would exceed 128 requests, the 900 second wall, the cost ceiling or the owner permission's expiry. The observation phase may spend only the first 540 seconds; the remaining 360 seconds are the recovery reserve for the reverts and the reconciliation, and no observation request can eat into it. Each request reserves a 6 second slot. An operation is polled at most 16 times within 120 seconds with backoff from 2 to 15 seconds; at most 6 operations are polled (two patches, two reverts, and one recovery re-revert per step). The derivation is 1 credential preflight, 2 controls, 2 steps of 5 requests, 1 listing, 96 polls, 4 recovery reverts and verifies, and 5 reconciliation reads, 119 requests, rounded up to 128. The Ledger's `accounts` dimension is the published `maxAccounts` of 1: one authorized principal's quota is spent and no account is created.

Isolation comes from the nonce. The two patched collection groups are named `fsconfig_ttl_<first twelve nonce characters>` and `fsconfig_exempt_<first twelve nonce characters>`, so no collection group another lane uses is touched. The default database is never created, patched, deleted, restored or cloned; only those nonce-owned field configurations under it are changed, and each is reverted in the same run.

## Shared Ledger locks

The run reserves in the shared Ledger with an EXCLUSIVE lock on each field configuration it patches, `project/fireemu-35fe6/firestore/(default)/fields/<collectionGroup>/<field>`, which the Ledger's segment grammar accepts directly, plus READ locks on `project/fireemu-35fe6/firestore/(default)/database`, `project/fireemu-35fe6/firestore/(default)/indexes` and `project/fireemu-35fe6/identity`. A document lock under the same database is a sibling of the field keys and does not overlap, so a data campaign is refused only when it names the same field; the READ locks state what the run depends on staying unchanged. The Ledger budget is 128 requests, 1 account, 0 document resources and 128 micro-USD, and the claim's duration is the 900 second wall.

## Owner preconditions

The owner confirms all of the following before the run starts. The collector never establishes any of them itself.

1. The default database's projection digest, computed under the `database-settings-v2` contract from the `databases.get` answer, equals the digest frozen in the owner permission as `databaseProjectionDigest`. The collector reads the projection first and stops before patching anything when it differs.
2. The two field configurations are patched only on collection groups whose names carry this run's nonce.
3. The default database is never created, patched, deleted, restored or cloned.
4. The run holds the EXCLUSIVE and READ locks above for its duration, so a data campaign that depends on the same configuration cannot start while it is held.
5. No named database exists beyond the ones enumerated in the frozen baseline. The closing reconciliation compares the enumeration again and fails the run when it changed.

## Permission envelope

8 permissions are required, all of them configuration reads and one configuration write: get, read metadata for and list databases, get, list and update indexes (the `fields` methods are governed by the `datastore.indexes.*` permissions), and get and list operations. 17 permissions are explicitly excluded, including every document permission, database create, delete and update, export, import, restore and all three backup permissions, along with service-account key creation and project deletion or policy changes. A collector defect therefore cannot read or destroy data and cannot create or delete a database, because it never holds a permission that would let it.

## Abort rules and recovery

The run stops, rather than retrying, on projection drift before any mutation, on a request that would exceed the request bound, the observation wall or the cost ceiling, on a credential refusal, on an operation that has not finished within the poll deadline, and on a revert whose verifying readback differs from the baseline. A retry is a new run with a new nonce and a new owner permission, never an automatic repeat.

Recovery runs on every stop path and in the clean path alike. In reverse step order, every step still owned (applied, uncertain, unverified, or refused by an answer that does not prove the refusal permanent) is reverted, its operation polled, and its configuration read back and compared with the baseline digest; a refused revert gets exactly one recovery attempt unless the refusal was a 401, 403 or 404. Then both owned collection groups are listed twice, under `indexConfig.usesAncestorConfig:false` and under `ttlConfig:*` (a field whose only override is a time-to-live policy keeps `usesAncestorConfig` and is invisible under the first filter in production), and both listings must be empty; then the database enumeration is read and must equal the one OC-02 captured. A step whose revert was refused or whose verification differs is an unrecovered resource: the run reports it with a typed record naming the saved pre-value, exits non-zero, and leaves the shared Ledger reservation held until the owner restores the field by hand and closes the reservation through the escalation path. A stop before any patch left (a refused credential preflight, projection drift, an unavailable control) spends no request on reconciliation and ends with the typed `held-no-mutation` disposition.

`tools/compat-broad/fs-config-lifecycle/rehearsal.py` replays that path offline under nine injected failures: none, projection drift, a refused patch, a poll deadline, a stop after the time-to-live patch, an exhausted observation wall, a credential refusal, a refused revert, and a reconciliation mismatch. It issues no request. Only the clean outcome exits zero, an unrecovered resource is always reported as such, a stop after the time-to-live patch reverts that field and never touches the exemption field, and a refused patch needs no revert. The collector's own tests then drive the same paths against an in-memory Admin API, including a patch whose answer raised after it was applied, a 2xx answer without an owned operation, a typed 5xx, a revert acknowledged but not applied (the verifying readback must differ), a revert that raised after the wire, and a permanent refusal that is not retried.

## Collector, descriptor and launcher

`lifecycle_collector.py` drives the cases through an injected transport behind the gate; it never chooses a transport. Every response body is written to the private run directory with owner-only permissions and enters the result only as a digest and a type shape (field presence, JSON types and enum spelling), which is the raw-retention boundary. `lifecycle_descriptor.py` declares the campaign for the shared O8 core: the schema kinds, the 900 second wall and 360 second recovery window, the source map over the whole lane and the shared closure, the plan compiler, the budget, the lock scopes, the collector, the comparator, the cost model, the permission bindings, and the worker binding of `lifecycle_https_worker.py`, whose digest `lifecycle_remote_transport.py` pins and which accepts exactly the campaign's own Admin API routes as whole-route alternatives (a test feeds every case route, both reconciliation listings per group and an operation path through the pattern and refuses joined routes, other databases, documents and foreign projects). The descriptor refuses construction with any member missing. One documented divergence from the shared Gate: after a credential refusal the shared Gate refuses every further send, while this gate still charges the recovery reverts with the refused credential, because an attempt is cheap, its 401 is journaled, and the alternative is leaving the field patched without trying.

`lifecycle_admission.py` freezes the inputs over a clean committed source snapshot, runs the shared O7 check set (approval bound to the running launcher, the resolved Ledger root, the execution host and a window that covers the whole run), requires the owner-frozen projection digest, real owner and recovery identities, a frozen credential principal and a permission reference, and compiles the Ledger claim. `lifecycle_o8.py` is the launcher: admission, provenance, capability issuance, the read-only fresh-nonce check, then the reservation, the gate, and only then the credential handoff on a private descriptor. The first charged request is the credential preflight (`PRE-01`): one tokeninfo exchange verified by the request-byte lane's reviewed `verify_token`, which must confirm the frozen `clientId` and subject or verified email, the `cloud-platform` scope and a remaining lifetime of at least the wall plus the recovery reserve (1260 seconds), so a token cannot expire between a patch and its revert; only an attestation of digests and booleans is persisted, and a refusal stops the run before OC-01 with nothing patched. Exit 0 means restore verified and reservation released; exit 1 means the run started and its reservation is held with `receipt.json` written; exit 2 means admission refused before anything was sent.

```sh
uv run --python 3.12 python tools/compat-broad/fs-config-lifecycle/lifecycle_o8.py \
  --inputs <pkg>/lifecycle-frozen-inputs-v1.json --approval <private>/lifecycle-o8-approval-v1.json \
  --manifest <pkg>/lifecycle-o8-manifest-v1.json --permission <pkg>/lifecycle-owner-execution-permission-v1.json \
  --source <frozen checkout> --artifact <retained fireemu> --ledger <canonical shared Ledger root> \
  --output <fresh private directory> --credential-fd 3  3< <private handoff>
```

The handoff is `{"kind": "fs-config-lifecycle-bearer-token-v1", "permissionDigest": <digest of the permission>, "token": <bearer>}`, at most 16 KiB, read within 5 seconds, only after the reservation exists.

## What the shared core cannot do yet

The shared Ledger cannot release a configuration-only reservation. `tools/compat-broad/shared_gate.py` refuses to create a Gate for a plan whose jobs own no document, and every terminal Ledger transition re-reads that Gate and proves cleanup by typed document absence. This campaign owns two field configurations and no document. `lifecycle_admission.release_supported()` states this in code, so a clean production run ends with the reservation held and a typed `fs-config-lifecycle-release-blocked-v1` record in its receipt instead of a release the core would refuse; exit 0 is unreachable until the core admits a management-only plan or a configuration policy module. The gate plan already carries the Gate-shaped projection the Ledger reads at reservation time, so the plan the Ledger binds and the plan the gate journals are the same bytes.

## Temporary-Ledger integration proof

`test_fs_config_o8.py` runs the reservation-to-receipt path against a temporary Ledger the test creates and marks as a proof; the production module refuses any Ledger without that marker when a transport is injected, and the injected transport is checked not to reach the production wire. The proof shows all twelve cases observed with both fields restored and the reservation held under the EXCLUSIVE field locks, a second admission of the same nonce or the same permission refused, a conflicting field lock refused by the Ledger, a stop after the time-to-live patch reverted in recovery before the release disposition with the exemption field never touched, a refused revert held with the typed unrecovered record and its saved pre-value, and a credential refusal that stops before any wire with the reservation already taken.

## Local rehearsal

`lifecycle_local.py` rehearses the campaign against an owned fireemu built from the committed tree, over a loopback transport carrying the emulator's fixed owner token, with the same collector and gate. The record `spec/compatibility/broad-runs/fs-config-lifecycle-local-rehearsal-v7.json` binds the lane module digests and the runtime source commit of the integrated tree it was run on; a test fails when either drifts, and a new run is published as a new versioned record, never over an old one (`v1`, from `acdefbf53`, predates the review fixes; `v2` was run on the lane branch before it was rebased onto the integration branch and cites a commit id that no longer exists there; `v3` predates the verified-acquisition comparator and `v4` its identity registry and synthetic-anchor marker; `v5` predates the comparator contract v3 record-integrity checks below; all are kept as history).

The comparator moved to comparison contract v3 (LIFECYCLE-COMPARE-INTEGRITY-007): a duplicate, unknown or out-of-order observation identity makes the whole comparison INDETERMINATE rather than silently keeping the first-seen row; only observation-phase case rows are joined, so a recovery-phase retry can never stand in for a missing observation; `completed`, `stopPoint`, `failure` and `cleanupComplete` are checked independently of per-row completeness, so a cleanup that finished cleanly no longer hides an aborted or failed run; a row's `complete` must be the literal boolean `True`; a run that mixes a confirmed MISMATCH with a missing row stays INDETERMINATE overall while the per-row MISMATCH is still visible; EXPECTED_LOCAL_DEVIATION now propagates to the whole-run classification instead of folding into MATCH; and `compare()` takes an explicit `local_nonce` (defaulting to the production nonce) so a saved local rehearsal recorded under a different nonce is bound on purpose. 401/403/429 responses are treated as INDETERMINATE for this Admin field-configuration campaign, since it is not a credential or quota test.

Result: 17 charged requests, the time-to-live step patched, polled, read back, reverted and verified against its baseline digest; the exemption patch refused `UNIMPLEMENTED` and recorded as the expected local deviation with OC-19 and OC-20 unreached; all four field listings empty and the enumeration unchanged; the owned fireemu stopped with its listener closed. The local database projection carries the same field set as the saved production response (`FS-CONFIG-RT-003` is fixed), and its digest differs because `uid`, `createTime` and `updateTime` are local values, so the local baseline is read once before the gate is created. The record's execution kind is the injected local transport; the comparator refuses to classify it as a match against anything but a fixed-production-wire record.

## Comparator contract

`tools/compat-broad/fs-config-lifecycle/comparator.py` lines two collection records up case by case on the rows the collector marked as cases and compares HTTP status, typed error code and status, and the body type shape. Values are never compared; `earliestVersionTime`, `etag`, `createTime`, `updateTime`, `deleteTime`, `uid`, `snapshotTime`, `startTime`, `endTime` and `name` collapse to their type. Field presence and absence, JSON types, array order, enum spelling, and the status and canonical error code are all significant. Error message prose, operation progress counters, latency and the number of polls are reported but not required to match. A case one side never reached, a transport failure, a credential refusal and an incomplete cleanup are indeterminate. A row is an expected local deviation only when the local side answered the typed `UNIMPLEMENTED` refusal the classification matrix names and the production side served the request with a 2xx; a refusal on both sides is compared like any other row and reads MATCH or MISMATCH visibly. It classifies MATCH only when the production side is bound to a verified acquisition, both cleanups completed, and every case is a match or an expected local deviation. The verified acquisition is a `VerifiedAcquisition` object that only `lifecycle_production.verify_saved` builds: that function re-reads a saved O8 receipt directory and checks the receipt's kind and campaign, the `fixed-production-wire` execution kind with `productionExecuted`, the reviewed worker digest, every evidence file digest the receipt names, the frozen inputs and their digests, the gate snapshot against `gateDigest` and the charged totals, the saved `collection/result.json` against the receipt's collection, the attested credential preflight row, and the shared Ledger row the ticket points at (claim digest, campaign, gate plan digest, nonce digest, generation, and that the receipt directory sits at the gate path the claim names). `verify_saved` registers each object it builds by identity, and refuses a proof Ledger as the anchor unless `synthetic=True` is passed explicitly, in which case the object and the comparison carry `synthetic: true` and `acquisitionValidated` stays false whatever the rows say. The comparator re-checks the object it is handed: that it is one the boundary registered (a dict is a copy and an instance constructed elsewhere is a construction, not a verification), the campaign, the execution kind, the production origin, well-formed digests, and that the collection digest it names is the digest of the collection on the production side. The Ledger anchor binds the reservation (claim digest, gate plan digest, generation, nonce digest and gate path), not the bytes observed after it: the receipt, gate snapshot and collection digests are checked against each other inside the receipt directory, so a directory rewritten consistently after the run is not detected by the anchor. A shared `attach_evidence` Ledger transition written right after the receipt is the missing piece and is tracked as a shared-core item. A production record without that object, or with one bound to another collection, is REFUSED with `production-acquisition-unverified` or `production-acquisition-binding` in `errors` and no rows, so the `executionKind` label alone never yields a production comparison and an exact copy of the local collection relabelled as production is refused (owner review d7f7ce184, finding 2). `acquisitionValidated` is true only when the object is bound, its anchor is not synthetic, and the whole-run classification is MATCH or MISMATCH; `promotionReady` is always false here. Because OC-19 and OC-20 are unreached locally until `FS-CONFIG-RT-004` lands, the whole-run classification against any production run can only be INDETERMINATE until then; per-row MATCH remains usable. The nonce is a required argument, so the manifest is recompiled and compared on every call. Promotion is never decided here.

## What is still missing

No owner permission, nonce reservation or validity window is supplied here. Production error shapes for a refused patch or revert remain unknown. The long-running-operation metadata shapes are declared from the method and schema names in the pinned Discovery input, not from any response; that input carries locators only, so it can supply an enumeration of names but never a message shape. The runtime transition for the `indexConfig` patch (`FS-CONFIG-RT-004`) is a separate Rust packet, so the local side of the exemption cases stays a recorded deviation until it lands. And the release gap above belongs to the shared core.
