# Changelog

All notable changes to fireemu are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Until 1.0.0, a minor release may change configuration, unsupported behavior, and edge-case semantics.

Each release is a Git tag; the binaries and the npm packages are built from that tag by the release workflow. Behavior described as "matching production" was measured against a real Firebase project on the date named in the commit that introduced it.

## [0.10.0] - 2026-10-01

### Added

- Both profiles: `PATCH /storage/v1/b/<bucket>/o/<object>` updates the object's metadata, as the Cloud Storage JSON API does in production (recorded 2026-09-30): a 200 with the `storage#object` resource, `null` removes a custom metadata key, `ifGenerationMatch` and `ifMetagenerationMatch` are honoured, and an absent object answers the 404 `No such object` JSON error. The documented `/storage/v1` `copyTo` and `rewriteTo` routes are accepted too. The official emulator registers PATCH and copy on the short `/b/...` spelling only and answers these spellings with 501 Not Implemented; the difference is a published divergence.
- `auth.mfa` in the canonical configuration (Fireemu-only): the project's initial multi-factor configuration, in the Identity Platform `Config.mfa` shape, so TOTP can be enabled from the config file under the strict profile (where `auth.totp` alone enables nothing, as in production) instead of through the Admin API in every session. It is validated as the Admin API validates an update of `mfa`, is the project's configuration at start in both profiles and that of every project created later, and is what `POST /v1/sessions/{s}/reset` returns to; without it a reset leaves an Admin-set configuration alone, as before. An Admin update still replaces it and disabling refuses TOTP as production does; the emulator profile keeps `auth.totp`. Strict with `auth.totp` and no enabling `auth.mfa` prints a start-up warning naming the key.
- `firestore.indexes.json`: a `fieldOverrides[].ttl: true` now declares a time-to-live policy, as `firebase deploy` creates one from that file. Before, the key was read and dropped without a word, and a policy could only be set with the Admin `fields.patch`. The declared policy is in force for every project of the database, is reported by `fields.get` like a patched one, survives a session reset, and is read again when the file is reloaded. It is checked like a patch (not `__name__`, not the wildcard field, one field per collection group, at most 64); a file that names a `ttl` that is not a boolean, or a policy no patch could set, stops the daemon at start and keeps the last good policies on reload. **Existing files that already carry `ttl: true` now take effect, in both profiles** (the official emulator does no TTL, and the emulator profile already ran the sweep for policies set with `fields.patch`): documents whose field has expired are deleted when the virtual clock moves past the sweep interval or the sweep route is called. The file is the desired state, which differs from `firebase deploy`: `ttl: false` or an absent `ttl` declares nothing (it does not clear a policy a project patched or imported), and dropping `ttl` on a reload removes the declaration. A project that patches or clears TTL starts from the declared policies and then owns its copy: it no longer follows later reloads, a snapshot restore keeps what it cleared cleared, and an export does not record a clear.
- `auth.authorizedDomains` declares the initial project-wide action-link domain list in either profile, validated through the existing Admin API rules. The list replaces defaults, initializes later session and routed projects, and is restored on session reset only when declared. Admin updates change the live list; account clearing and export/import keep their existing behavior. Strict continues to enforce live domains, and the emulator profile keeps its permissive continue-URL handling. Tenant-scoped strict action links currently check the tenant's default domains rather than this project declaration; support for the parent project's live list is pending. (Fireemu-only)
- `auth.multiTenant` and `auth.tenants[]` in the canonical configuration (Fireemu-only): the default project's multi-tenancy switch and its tenants, so a run starts with them instead of creating them through the Admin API in every session. Each tenant is an Admin v2 `Tenant` document with its `tenantId` (production's `displayName-xxxxx` shape in both profiles), read by the code the Admin create route reads a document with, and created empty when the daemon starts for the default project and every session project, and again by a session's reset (`POST /v1/sessions/{s}/reset`, the default session's included), which also returns the switch to the declared value; a namespace the emulator profile creates for an unknown project id is seeded when it is created. Under the strict profile declaring tenants needs `auth.multiTenant.allowTenants: true`, as production creates tenants only in a project that allows them; the emulator profile takes tenants without the switch. An `--import` is authoritative for a tenant of the same id, and a startup warning names a declared tenant an import replaced with other settings.

### Changed

- Strict profile: a 200 from Identity Toolkit `accounts:signUp`, `accounts:lookup` (both spellings) and `projects/{project}/accounts:delete` is framed as production sends it (recorded, lean-v5): `no-cache` headers with an `Expires` in 1990, `X-Frame-Options: SAMEORIGIN`, `X-XSS-Protection: 0`, `X-Content-Type-Options: nosniff`, a three-valued `Vary`, `Content-Type: application/json; charset=UTF-8`, a gzip body when the request accepts gzip (stored blocks: any decoder reads them, production's compressed bytes are not reproduced), no CORS headers unless the request carries an `Origin` (then it is reflected), two-space JSON with a final line feed and the recorded member order (the layout and final line feed of `accounts:signUp` are inferred from the lookup and delete rows, the recorder having hashed its refresh token, so they are not recorded; an explicit `gzip;q=0` in `Accept-Encoding` wins over `*`) (`kind`, `idToken`, `email`, `refreshToken`, `expiresIn`, `localId`; a user's `localId`, `email`, `passwordHash`, `emailVerified`, `passwordUpdatedAt`, `providerUserInfo`, `validSince`, `lastLoginAt`, `createdAt`, `lastRefreshAt`; a provider's `providerId`, `federatedId`, `email`, `rawId`). Other routes, other statuses and the emulator profile keep the official emulator's framing.
- Both profiles: `lastRefreshAt` in an Identity Toolkit lookup has millisecond precision (24 characters), as the official emulator writes it (`toISOString`, always three fraction digits) and production answers it (a protobuf Timestamp: the fewest digits, three for a millisecond instant); it carried nanoseconds. The strict profile uses the Timestamp spelling, the emulator profile the three-digit one.
- Strict profile: Storage answers carry production's headers and body layout for the request shapes the STORAGE-OBJECT recordings cover (2026-09-30, 2026-10-01); a request that carries an `Origin` (which no recording did) is answered with the origin reflected and the official emulator's exposed headers on both dialects, so that a browser can read the upload headers. JSON API answers: `Vary: Origin, X-Origin` always; reads of metadata and lists `private, max-age=0, must-revalidate, no-transform` with an `Expires` of now and the object's `etag` as a header; every other answer `no-cache, no-store, max-age=0, must-revalidate`, an `Expires` in 1990 and `Pragma: no-cache`; a media 404, 412, 416 or 304 `private, max-age=0`; media 200 and 206 add `Last-Modified` (the generation's creation second), the validator and the `x-goog-*` object headers, `attachment` as the disposition and no checksum on a partial answer; no `X-Content-Type-Options` or CORS headers unless the request sent an `Origin`. Firebase v0 answers: `Access-Control-Allow-Origin: *`, `Access-Control-Expose-Headers: Content-Range, X-Firebase-Storage-XSRF` and `nosniff` on JSON, `private, max-age=0` and an `Expires` of now on GET and DELETE; media 200 without CORS, `no-cache` for the owner and `private, max-age=0` for a Firebase ID token or a download token (inferred from 4 of 179 recorded reads), the quoted MD5 as `ETag` and the XML 416 with the object's headers. JSON bodies: two-space layout, a final line feed on the JSON API only, and the recorded member order (object `kind`, `id`, `selfLink`, `mediaLink`, `name`, `bucket`, ... `metadata`, `owner`; v0 `name`, `bucket`, ... `downloadTokens`, `metadata`; list `kind`, `nextPageToken`, `prefixes`, `items` / `prefixes`, `items`, `nextPageToken`). The emulator profile keeps the official emulator's headers and bodies.
- Strict profile: Storage identities and ordering follow production. A generation is the commit's microsecond timestamp of the clock (16 digits; it never repeats or runs backwards), the object `etag` is the base64 of the protobuf of generation and metageneration (it was `<generation>-<metageneration>`), a minted download token is listed first, and a JSON API 308 carries `x-goog-running-hash` and `x-range-md5` of the bytes the session holds. The emulator profile keeps counting generations from 1, appending tokens and its own etag.
- Both profiles: a read of an object name longer than 1,024 bytes is a 404 on both dialects, as in production and the official emulator (it was a 400). A `PUT` on the JSON API object also clears the `cacheControl`, `contentDisposition`, `contentEncoding` and `contentLanguage` it omits (recorded for `cacheControl`).
- Strict profile: an upload whose declared checksum does not match is refused in production's words (`Provided MD5 hash "..." doesn't match calculated MD5 hash "...".`, the same for CRC32C, `Provided value (...) is not a base64-encoded 128-bit MD5 hash.`, `Invalid argument.` for a malformed CRC32C); the emulator profile no longer verifies declared checksums on any upload path, resumable sessions included, as the official emulator does not (a wrong declared MD5 was refused before). A JSON API upload name with a line feed or over 1,024 characters is production's 400 (a JSON body typed `text/html`). A Firebase multipart upload is typed by its data part when the metadata names no type, and a body that is not two parts is a plain-text 400 (`Multipart body does not contain 2 or 3 parts.`); a JSON API multipart body that is not two parts is `invalidPayloadSize`. The Firebase resumable protocol answers as production does: granularity 262144, a control URL equal to the session URL, no `x-gupload-uploadid`, empty bodies, `x-goog-upload-status: cancelled` on a cancel and `Client uploaded to the wrong offset (1 instead of 0).` for a chunk at the wrong offset. `copyTo` and `rewriteTo` name an `owner.entity`.
- The npm package page is now generated from the repository README at pack time (`npm/scripts/prepare-launcher.mjs`), so the two no longer drift apart. Relative links in the README are rewritten to GitHub URLs at the release tag, and the page opens with a note naming its source. The separately maintained `npm/README.md` is removed.
- Functions: a Firestore event handler now sees the event the way production delivers it. In both profiles the event's `id` is a UUID (derived from the session and the event counter, so a recorded run still replays) instead of `<session>-<n>`, the event's `time` prints the shortest exact fraction of zero, three, six or nine digits instead of always nine, and a 1st gen handler's `context.eventId` is that id followed by `-0`. Only a create delivery was recorded in production (2026-09-30); the other kinds follow the same forms by inference. Other products keep their ids and times. A 2nd gen handler's `event.source` still differs from production's.
- Strict profile: the JSON API list with `maxResults=0` answers the bare `{"kind": "storage#objects"}` production answers (the official emulator adds a next-page token, which the emulator profile keeps), and a media read carries production's headers (`x-goog-metageneration`, the stored content encoding and length, `pragma`, `vary` on the JSON API, `accept-ranges` and the `x-goog-meta-*` headers of the custom metadata and the download token on the Firebase dialect, no empty `content-encoding`, the disposition only as stored with `attachment` on the JSON API). The emulator profile keeps the official emulator's headers.
- JSON API object guards under the strict profile answer as production does (recorded 2026-09-30): a not-match guard that names the current value is a 304 with no body and `Content-Type: application/json` on PATCH, PUT, DELETE, upload and a metadata read (`application/octet-stream` on a media read); a match guard that does not hold, or whose value is a negative number (recorded: `-1`), is production's 412 body (`conditionNotMet`, `locationType: header`, `location: If-Match`), a bare `text/html` sentence on a media read; a not-match guard with a negative value (recorded: `-1`) is accepted, so the request goes ahead; a value that is no `long` (`1.5`, text, an empty value) is production's 400 `Invalid long value: '<v>'.` naming the parameter (`invalidParameter`, `locationType: parameter`), for the match and the not-match guards alike, and the write is not done (a DELETE keeps the object). The same parser reads the generation guards, the `ifSource*` guards of a copy and the guards of a read; only the metageneration guards of PATCH, PUT and DELETE were recorded with such values. The emulator profile now ignores every guard, as the official emulator does (it reads none; it used to answer 412 and 304 like strict, and 400 for a malformed value).
- `PUT /storage/v1/b/<bucket>/o/<object>` (and the short `/b/...` spelling) updates the object's metadata and answers the object resource with the metageneration one higher, as production does (recorded, probe-v4) in both profiles; it answered 501 before, as the official emulator still does (measured), so the emulator profile accepts what the official emulator refuses. Unlike `PATCH`, a `PUT` that carries a `metadata` object replaces the custom metadata and drops the download tokens, so a download URL made before it stops working (recorded, lean-v4: the earlier key and the token are gone after the `PUT`). What a `PUT` does to the other writable fields it omits, or to custom metadata it omits, was not recorded: they stay as a `PATCH` leaves them.
- Strict profile: an unsatisfiable range answers as production does: the JSON API's 416 is the sentence `Request range not satisfiable` typed `text/html` with `Content-Range: bytes */N`, the Firebase dialect's 416 is an XML `InvalidRange` error naming the range asked for, and a nonzero suffix of an empty object is an empty 206 with `Content-Range: bytes 0-0/0` on the JSON API. The emulator profile keeps the official emulator's whole-object answer.
- A read of an object name that contains a line feed is a 404 on both dialects (the Firebase JSON `Not Found.`, the JSON API's `No such object` or media sentence), as production answers it; it was a 400. The official emulator also answers 404 (measured), with its own `Not Found` text on the Firebase dialect.
- The Firebase list pages as production does (recorded 2026-09-30): the page token is the standard base64 of the full name of the last entry returned (items and prefixes in one merged name order) instead of the raw name of the next entry, and the answer always carries both `prefixes` and `items`. `maxResults=0` answers production's 400 `Expect maxResults to be a positive number.` under strict; the emulator profile keeps the official emulator's 200 with an empty page. The JSON API list is unchanged.
- Both profiles: the Cloud Storage JSON API answers an absent object's media read with `text/html` (`No such object: <bucket>/<object>`), as production and the official emulator do; it was `text/plain` before, chosen to keep the reflected object name from being run as HTML. Strict writes production's `text/html; charset=UTF-8`.
- Strict profile: Storage JSON answers carry `Content-Type: application/json; charset=UTF-8` on both dialects, the JSON API's error bodies use the Google-fronted pretty layout with a final line feed, and its 204 carries `Content-Type: application/json`, as compared against production (2026-09-30). The emulator profile keeps the official emulator's framing. 
- Both profiles: App Check debug-token exchange accepts the original proto field names `debug_token` and `limited_use` alongside `debugToken` and `limitedUse`, as the pinned Web SDK sends. Conflicting values for two spellings of one field return 400; equal values are accepted. `limited_use: true` keeps the documented 501 replay-protection refusal.
- Both profiles: Storage lists count prefixes and items together toward `maxResults` and cap pages at 1000 entries, as the [Firebase ListOptions reference](https://firebase.google.com/docs/reference/js/storage.listoptions) and [Cloud Storage JSON API reference](https://cloud.google.com/storage/docs/json_api/v1/objects/list) describe. Each prefix appears on one page only; this follows from treating prefixes and items as one ordered sequence, but is not explicitly stated in those references. The official emulator pages items alone and repeats prefixes.
- Strict profile: the Storage JSON API list honours `startOffset` (inclusive), `endOffset` (exclusive) and `matchGlob` (`*`, `**`, `?`, `[...]`, `{a,b}`), applied to object names before they are folded at the delimiter (recorded, lean-v5: offsets `b.txt` and `zz.txt`, glob `dir/*`; the other glob constructs follow the documented syntax and are not recorded; a pattern is compiled once and matched in time linear in the pattern times the name, without recursion, over the names read in batches under short store locks and tested outside them, stopping when the page is complete; a list that carries a `matchGlob` waits for one of two slots of its own before it takes a handler slot), and returns 400 for `includeTrailingDelimiter=true`, which was not recorded. The emulator profile ignores all four, as the official emulator does (measured: the whole listing). Because object versioning is unavailable, `versions=true` returns the same current generations as `versions=false`. An unsatisfiable media range returns 416 with `Content-Range: bytes */N`; a nonzero suffix on an empty object returns its empty body. The emulator profile keeps the official emulator's responses.
- Both profiles: Storage form uploads transfer the file bytes from the request buffer into the object store without a second file-sized allocation.
- Both profiles: the Cloud Storage JSON API resumable session is cancelled by `DELETE` on its URL and answers 499 `clientClosedRequest`, as does a status query after the cancel (recorded 2026-09-30); the official emulator answers 501 to the `DELETE`. The session start has no body and its URL repeats the start query and adds `upload_id`. The JSON API's 401 and parse-error bodies end in a line feed, as production's do.
- Both profiles: Storage success and error bodies follow what production was recorded answering (2026-09-30) where the official emulator differs and no refusal is involved. Object timestamps have three fractional digits. The JSON API object resource carries `timeFinalized`. The Firebase dialect spells `crc32c` in base64, defaults `contentDisposition` to `inline; filename*=utf-8''<file name>` for an upload that names none, omits an empty `metadata` map and an absent `downloadTokens`, and mints a download token on the first metadata read only (a media read no longer does). An absent Firebase object answers the JSON `Not Found.`; a malformed `PATCH` body answers `Parser Error` (Firebase) or the parser's `Parse Error: ...` (JSON API); the resumable start has no body and a cancel after the session finished answers `Upload has already been finalized.`. Each is a documented divergence from the official emulator in the storage probe.
- Both profiles: Storage answers as production does where the official emulator differs and only the status or the method differs (recorded 2026-09-30). An upload over an existing object is evaluated as the rules method `create`, not `update` (the official emulator does the same, so the divergence `overwrite-locked-is-an-update` is retired). A Firebase v0 `PATCH` of an absent object answers 403, not 404. A list under `rules_version = "1"` answers 400 with production's message (`Listing objects in a bucket is disallowed for rules_version = "1".` and the request for version 2), not 403.
- Strict profile: Storage answers a rules refusal, a token of another project and a list under `rules_version = "1"` with production's recorded bytes (two-space pretty JSON, `application/json; charset=UTF-8`, `Permission denied.` without the `No WRITE permission.` suffix). The emulator profile keeps the official emulator's wording and framing.
- Storage credentials on the Firebase dialect (recorded 2026-09-30): under the strict profile `Firebase ` followed by a value without a dot (the recorded `token-malformed` shape, 32 base64url characters) is an anonymous caller, so the rules answer it (403 when they need a user) and a malformed `PATCH` body answers the parser's 400 first; the strict profile used to answer `401 invalid ID token`. Every other value that fails to decode (two or four segments, a `Bearer` value, a three-segment value with a tampered signature, an unknown `kid` or an unsupported algorithm) stays a 401 under strict. An ID token whose refresh tokens were revoked is honoured on Storage in both profiles, as production honours it. The emulator profile maps every decode failure to an anonymous caller and never admits a token that fails verification as its claimed user. Strict answers a bucket with no ruleset with production's 400 "Your bucket has not been set up properly…"; the emulator profile admits every end-user request for a `demo-*` project with no Storage rules, as the official emulator does with its default open rules, and keeps a 403 for any other project.
- Strict profile: a `Bearer` credential that is not the emulator's owner credential on `PATCH /storage/v1/b/<bucket>/o/<object>` is refused with production's recorded 401 `Invalid Credentials`, before the body or the object is read (recorded 2026-09-30; the other JSON API routes were not recorded and keep ignoring the credential). The emulator profile ignores the credential, as the official emulator does.
- Strict profile: a token minted for another project on Storage is refused with production's 403 `Permission denied.`, not `401` with an audience message; an upload that carries no custom metadata evaluates `request.resource.metadata` as `null`, as production does, so a rule that reads the map (`"owner" in request.resource.metadata`) denies it.
- Emulator profile: Storage admits a token minted for another project, as the official emulator does (firebase-tools 15.28.2 never reads `aud`); the audience was refused before, which refused a request the official emulator admits. A signed token must still verify. Firestore keeps its audience refusal. An upload with no custom metadata keeps the official emulator's empty `request.resource.metadata` map, which production does not (strict follows production).
- Functions: a Storage event handler now sees the event the way production delivers it (one onFinalize delivery, 2026-10-01). In both profiles the event's `id` is a decimal string of seventeen digits instead of `<session>-<n>` (derived from the session and the event counter, so a recorded run replays; two events of one session whose counters are fewer than 9·10^16 apart never share an id, while a seed that is not of the `<session>-<n>` form is hashed and may collide), a finalize CloudEvent's `time` is the object's creation instant with its microsecond fraction instead of the instant the runtime admitted it, the object resource's `timeCreated`, `updated` and `timeStorageClassUpdated` print exactly three fraction digits instead of up to nine, and a 1st gen handler's `context.timestamp` is the instant the runtime admitted the event cut to the millisecond (production's was 91 ms after the creation; the delay is not modelled). Only the six-digit fraction of the CloudEvent time was observed; the zero and three digit forms, the time of a deleted or metadata-updated event and other id lengths follow by inference. The `etag` and `generation` of the object and a 2nd gen Storage event's `datacontenttype` still differ from production's.
- Emulator profile: a project id the daemon was not told about can hold tenants, as in the official emulator, which makes any project and tenant on demand. The project is created (and seeded with the declared tenants, whichever request creates it, so a declared tenant a request names first keeps its declared settings) when a request writes a tenant there, or does what already created it (an Admin user create, a provider write, a project setting write): `tenants:create`, or a request that names a tenant that does not exist yet (`GET`, `PATCH`, `DELETE` of a tenant, an account call under it), where it answered `400 INVALID_PROJECT_ID` or `404 TENANT_NOT_FOUND`. A read of the tenant list alone, a refused request (credential, control-token or App Check) and an invalid project id create nothing. Installing the project, seeding it and making the tenant a request names are one admitted step, so a reset that races the request no longer fails half-applied, and a tenant made while a session is being created does not outlive its rollback. A session created for a project id that holds a routed namespace replaces it with its tenants (it answered 500 once tenants were possible there). The strict profile is unchanged, and no strict request takes the session barrier for a seed.
- Emulator profile: the tenant a request names is read as the official emulator reads it (firebase-tools 15.28.2). An empty body `tenantId` is no tenant (`""` is falsy there): a path tenant beside it is the target and none makes a project request, where the emulator profile answered `TENANT_ID_MISMATCH` or looked for the tenant `""`. The query's `tenantId` is read only by `accounts:batchGet` (and only when no other tenant is named) and the action link; every other account route ignores it, so `signUp?tenantId=x` is a project sign-up and a query tenant beside a path or body tenant is neither a mismatch nor a selector. The strict profile is unchanged. The two GET routes that read the query's tenant (`accounts:batchGet`, the action link) read no body, as in the official emulator; `getProjects`, `recaptchaParams`, the config and tenant-management routes ignore the query too, and a malformed query tenant is ignored with it (the API key of such a request is still read, so it is served from the key's project, and a refused key makes no tenant, and neither does a query that does not parse: a repeated, empty, bare or percent-malformed key, or a malformed tenant on a route that reads it, is refused before any tenant is made). On `accounts:batchGet` and the action link an empty or bare `tenantId` is no tenant, where it answered `400 INVALID_ARGUMENT`; a repeated one is still refused. A `null`, boolean, object or array `tenantId`, which the official schema refuses, is read as no tenant.
- Emulator profile: an ID token's tenant is looked for a user only by the operations the official emulator parses the token in (firebase-tools 15.28.2, `parseIdToken`): sign-up upgrade and the Admin create, `lookup`, `update` (the Admin update unless it carries an `oobCode`), `delete`, session cookie, email-link, IdP and phone sign-in, and `sendOobCode` for `VERIFY_EMAIL` and `VERIFY_AND_CHANGE_EMAIL`. `createAuthUri`, `resetPassword`, `signInWithCustomToken` and `sendOobCode` for `PASSWORD_RESET` and `EMAIL_SIGNIN` with a token of a tenant made on the way are now served, where they answered `USER_NOT_FOUND`; a token of another tenant than the request names is still `TENANT_ID_MISMATCH`. The strict profile is unchanged.
- Emulator profile: an Admin account request on a project path (`accounts`, `:lookup`, `:update`, `:delete`, `:batchCreate`, `:batchDelete`, `:query`, `:sendOobCode`, `:createSessionCookie`) with a `tenantId` in its body now runs in that tenant of the path's project, as the official emulator runs it, for the default project and for a compatibility-routed project, where it answered `TENANT_ID_MISMATCH` after making the tenant. Only a request the owner-credential or control-token guard admitted can pick a tenant this way. The strict profile is unchanged.
- Emulator profile: an Admin account operation on a project path whose body names no tenant now runs in the tenant of its ID token, as the official emulator does (`server.js:398-406`), when the token is one of this project with a tenant claim; an Admin delete or update with only such a token answered `USER_NOT_FOUND` from the project's store. An end-user lookup or delete that carries the owner credential is served by the body's selectors or `localId` and reads no ID token, as the official emulator's `Oauth2` branch does, where they answered `USER_NOT_FOUND` for a token of a tenant made on the way. A privileged update (with the owner credential, and the Admin update) asserts its `localId` first and then updates the user of the ID token when it carries one, as the official emulator does (`MISSING_LOCAL_ID` without a `localId`, `USER_NOT_FOUND` for a token of a user the tenant lacks). The strict profile is unchanged.
- Emulator profile: a request that names a tenant the project does not have now makes the tenant on the way, as the official emulator does (firebase-tools 15.28.2, `getProjectStateById` / `getTenantProject`), instead of answering `TENANT_NOT_FOUND`. The target is read as the official emulator reads it: the path, else the body's `tenantId`, else the ID token's tenant, and the query for `accounts:batchGet`; the tenant is made in the request's project with password sign-up, anonymous users and email-link sign-in on, authentication not disabled and multi-factor enabled for `PHONE_SMS`. An account call still finds no user in it, a tenant document read answers the defaults, and a tenant delete removes what it made. The refresh token's tenant is read too (`INVALID_REFRESH_TOKEN` for a token that does not decode and `TENANT_ID_MISMATCH` for one of another tenant, both before a tenant is made), a number in `tenantId` is read as its string, and the action link's query names its tenant. Only a request this daemon serves makes a tenant: one that the owner-credential or control-token guard, App Check or an unknown API key refuses gets that refusal and makes nothing, in any project. A token of another project, or one this daemon cannot verify, is never the target, but its tenant is read as the official emulator reads it and has to agree with the path's or the body's tenant, or the request is `TENANT_ID_MISMATCH` and makes nothing. An empty, boolean, object or array `tenantId`, a name with a slash or a backslash, a path and body tenant that differ, the tenant IdP-config routes and `tenants:create` make nothing. The tenant is published with its multi-factor configuration. The strict profile is unchanged: it refuses and makes no tenant, as production does. This removes the `auth.missingTenantCreation` divergence.
- Emulator profile: `accounts:batchCreate` now follows firebase-tools 15.28.2 when it refuses repeated provider raw IDs under `sanityCheck`, repeated missing or empty local IDs without `allowOverwrite`, and an address held by another current account even with `allowDuplicateEmails`. Request-level refusals happen before row decoding or writes. The strict profile and trusted snapshot imports keep their existing behavior.

### Auth observed through Firestore (AUTH-FS-CROSS)

Behavior below was measured against a real Firestore database with end-user ID tokens, including one of another Firebase project, on 2026-09-27 (AUTH-FS-CROSS stage 1).

- Changed, both profiles: Firestore honours an unexpired ID token of a deleted tenant, as production did about 3 s and 66 s after the deletion, for reads, queries and writes, and so do listeners, which verify their token as other requests do. The token keeps its tenant claim, so Security Rules still tell it apart from the project's user of the same uid. fireemu refused it once the tenant was gone. In a registered (non-default) project of a daemon session the token is checked against the session epoch its tenant had, until the project is reset (it used to be refused there even after this change).

The emulator profile keeps its audience refusal (a token never crosses a project boundary there; the official emulator admits it).

Security Rules (FS-RULES): behavior below was measured against a real Firestore database with end-user ID tokens on 2026-09-24 and 2026-09-25 (FS-RULES). Where a change applies to both profiles, the pinned official emulator was measured on the same cases and answers as production does (`conformance/fs-rules-official.json`), so the emulator profile still follows it.

- Added, both profiles: `existsAfter()` answers whether a document exists once the request's writes are applied. It shares `getAfter()`'s access budget for a path.
- Changed, both profiles: a Security Rules denial answers with production's `PERMISSION_DENIED` and the message `Missing or insufficient permissions.`, on REST and gRPC, unlike the official emulator's evaluation trace. The reason fireemu found stays in the ruleset's request traces (`GET /v1/sessions/{session}/rules/requests` on the control API).
- Changed, both profiles: in Firestore rules, `get()` and `getAfter()` of a missing document answer `null` instead of an error (reading a member of it is still an error). In a read, where no write applies, `getAfter()` and `existsAfter()` read the current state instead of failing. `get()` and `getAfter()` of one path count as one document access. Storage rules keep their answers: `firestore.get()` of a missing document is an error, and `getAfter()`/`existsAfter()` are refused.
- Changed, both profiles: on a delete, `request.resource` is present and `null`.
- Changed, both profiles: Firestore honours an unexpired ID token of an account whose refresh tokens were revoked, that was disabled, or that was deleted, as production does; Identity Toolkit still refuses those tokens.
- Changed, both profiles: an end user's `listCollectionIds` and `partitionQuery` are refused with production's `Missing or insufficient permissions.`
- Changed, strict profile: a credential Firestore cannot use is refused in production's shapes: a token past its allowance is `UNAUTHENTICATED` `Missing or invalid authentication.`, a bearer value that is not a JWT is `UNAUTHENTICATED` with the front end's OAuth text, and every other unusable credential (a JWT that does not verify, an empty bearer, another scheme) is `PERMISSION_DENIED` `Missing or insufficient permissions.`. The emulator profile keeps its own texts.
- Changed, both profiles: rulesets compile as production's compiler compiles them. Expressions up to 99 levels deep compile, where each operator of a chain, `!`, a pair of parentheses, a ternary, a list or map literal and a call's arguments count one level, and 100 levels are refused with `Expression is too complex to evaluate safely.`. The following compile: a call with the wrong number of arguments (false when evaluated), an access method in any letter case, an unknown access method (it grants nothing), a missing semicolon after an allow statement or `rules_version`, 11 `let` bindings in a function, and ten match levels below `/databases/{database}/documents`. A function defined twice in one scope is refused with `Function <name> is already defined.`. These match the official emulator's compiler, which answers as production on every recorded case but one: it compiles a source over 256 KiB, which production and fireemu (as before) refuse. The daemon's runtime threads get an 8 MiB stack, and rulesets are parsed on a thread of their own. Evaluation still stops at 64 nested levels, where the condition is false.
- Changed, both profiles: allow statements are alternatives. One that holds allows the request even if another one raises an error (a document-access budget, an invalid regex, an unsupported feature), in either order; an error decides only when nothing holds. Running out of the 1,000-expression budget still ends the request, as in production, even before an allow with no condition. A request may exhaust fireemu's regex step budget in at most four matches; the fifth ends the request (`FIREEMU-REGEX-EXHAUSTIONS-PER-REQUEST`), so a ruleset of many regex allows cannot multiply the work one request costs.
- Changed, both profiles: a pair of parentheses counts as one expression evaluated toward the 1,000-expression budget. A query's rule may read 20 distinct documents, as a multi-document request may. `request.query.orderBy` is a map in every query, empty when it has no order. `request.query` carries production's nine keys, not only the three documented: `limit`, `offset`, `orderBy`, `allDescendants`, `distinct`, `groupBy`, `kind` (the collection id), `parent` (null for a root query, the parent document's path below one) and `selectOnlyKeys` (false, even when a query selects only `__name__`), so a rule that checks `request.query.keys()` sees what production shows it. `groupBy` is an empty map, and `allDescendants` and `distinct` are false for a collection query.
- Changed, both profiles: an end user's `BatchWrite` is refused with `Missing or insufficient permissions.`, whatever the rules say of its writes. The official emulator refuses it too, with its own text.
- Changed, both profiles: Security Rules judge a write by the method its precondition names: `exists: false` is a create and `exists: true` or `updateTime` an update, whatever the document is now. A write the rules then allow is refused by its failed precondition (`ALREADY_EXISTS`, `NOT_FOUND`), as production answers.
- Changed, strict profile: over REST, the refusal of a bearer value that is not a JWT carries production's `ErrorInfo` (`CREDENTIALS_MISSING`, with the service and the gRPC method the route transcodes to; a document read is `GetOrListDocuments`).
- Changed: callable Functions keep ID-token verification when they decide `context.auth`. Firestore's allowances (30 seconds past `exp`, and the token of a revoked, disabled or deleted account) are not extended to them, because nothing observed a callable honouring such a token.
- Changed: Firestore honours a verified ID token for 30 seconds past its `exp`, as production does: production accepted a token sent at a nominal 29.8 s past `exp` and refused one sent at a nominal 30.3 s past it (dispatch times were not recorded), where fireemu refused it at `exp`. This applies wherever tokens are verified: the strict profile, and the emulator profile with `auth.idTokenSigning: session-rsa` (otherwise that profile admits an unsigned mock token whatever its `exp`, as before). Identity Toolkit keeps its own five-minute allowance.
- Changed, both profiles: a REST `batchGet` error, a malformed body or a Security Rules denial alike, comes inside a one-element JSON array, as production answers a streaming method and fireemu already answered `runQuery`.
- Changed, strict profile: an end user, signed in or not, may not open a read-write transaction, whether by `BeginTransaction` (whose default is read-write) or by the `newTransaction` of `BatchGetDocuments`, `RunQuery` or `RunAggregationQuery`. It is refused with `Missing or insufficient permissions.` whatever the rules say, as production refuses it. A read-only transaction still opens, and the owner credential is unaffected. The emulator profile opens every transaction, as the official emulator does.
- Changed, strict profile (the default): while a database has no ruleset, every client request is refused with `PERMISSION_DENIED`, because production refuses every client request when there is no `cloud.firestore` release. A daemon started without rules therefore refuses SDK requests until rules are loaded (`rules.source`, `firebase.json`, `PUT /v1/rules`); the owner credential is unaffected. The emulator profile still allows everything until rules are loaded, as the official emulator does. The startup banner says which applies.

### Fixed

- Both profiles: Firestore rollback after expiry or an earlier rollback succeeds without reviving the transaction. A committed transaction can seed one retry; rollback of a committed or consumed predecessor remains refused. Read-only retry uses the recorded `Cannot retry a read-only transaction` diagnostic. These outcomes match two sandbox REST recordings; the full FS-TRANSACTION closure remains open.

- A refusal echoes at most 1 KiB of the value, key, path or property path it names, and a transcoder refusal lists at most 16 violations, so a large request cannot grow the response or the daemon's memory many times its size.
- The partition page token is bound to its snapshot version.

### Known issues

- Strict profile only, unobserved in production: managed Admin `bulkDeleteDocuments` and `importDocuments` write through the Commit route, so they apply the data plane's Commit limits. A bulk delete of a collection holding a document inside Commit's delete window is refused with `Transaction too big. Decrease transaction size.`, and an import of an export holding a document strict refuses to write (for example, an export the emulator profile wrote) is refused with that document's error. Both operations commit in chunks of 500 documents and stop at the first refused chunk without undoing the chunks before it, so a larger operation can end partly done. The emulator profile is unaffected.

- Firestore: repeated query executions inside one transaction are isolated, paged transaction observations are aggregated, and read-only results are excluded from conflict accounting.
- Firestore: internal read-only query transactions are owned until stream delivery and rolled back when a handler is cancelled before the first page, so cancelled clients no longer leak transactions.
- Firestore: key query constraints are enforced, and extrema transforms and page counters were corrected.
- Firestore: canonical index keys are separated from structural values, so values that compare equal for indexing but differ structurally no longer collide.
- Firestore: a `__name__` equality or `in` filter looks up its candidates directly instead of scanning the collection or collection-group scope; parent-scoped descending name scans are bounded.
- Firestore: history accounting no longer allocates diagnostics on the hot path.
- gRPC: Nagle delays are disabled on multiplexed connections, removing latency spikes in SDK round trips.
- Pub/Sub: bridge and dead-letter delivery are atomic, dead-letter retries are serialized and resume after bridge recovery, ordered push resumes after dead lettering, push retries resume after logical backoff and are deferred outside worker slots, and unsupported push updates are rejected.
- Functions: a Node executable reached through a symlink (for example the Volta shim) is run by its link name, so discovery no longer fails with exit status 126 and an unavailable Functions runtime.
- Emulator UI: editors stay bound to one target and unsaved drafts are guarded on target switches, route changes, and unloads; stale paged reads no longer overwrite the view; loading, failure, stale, and empty states are distinguished; the log tail stays in view after render; recursive subcollection deletion is paginated; path segments in in-app links are percent-encoded; amber primary buttons meet WCAG AA contrast and focus rings are visible.
- Conformance: the composite-index fixtures record that two equality filters are served by index merging on both sides, and that a REST `runQuery` response omits the `done` flag the official emulator adds, as production does.
- Conformance: production comparisons are bound to the live fireemu output and to the evidence identity, and a missing live comparison is rejected instead of passing vacuously.
