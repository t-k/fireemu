# Functions event observation draft

`corpus.json` prepares the 109 behavioral case-generation obligations in the frozen FUNCTIONS-EVENTS inventory using 25 source scenarios. Several cases inspect different aspects of the same source mutation. Case count is not request count: setup, deployment, controls, retries, capture, cleanup and readbacks still require a concrete bounded execution plan. This draft has no transport, send permission, production evidence or assigned project. The frozen closure remains unchanged.

Each row identifies its source scenario, handler event, generation, observed aspect, routing resource and evidence obligations. Resource names and credentials are symbolic roles, not live resource identifiers or secrets. Handler SDK versions, API request bytes and source budgets remain unprepared. Source-result and delivery values are proposed observation conditions, not recorded Firebase results. `validateCorpus` checks preparation consistency only and cannot decide whether a recording matches production.

For negative delivery, capture must begin before the source operation and retain a baseline cursor. The source result and state readback, matching run/resource correlation, positive controls in the same handler generation before and after the observation, a complete observation window and evidence of no capture loss are all required. An empty event list alone is insufficient. Setup/control events must be identified separately from the tested mutation. A 120-second window is a proposed finite capture bound, not a Firebase delivery SLA or proof that an event will never arrive. Failed capture or unfinished controls yield incomplete evidence.

The retry scenario is a representative v2 Firestore fail-once handler. Capture must preserve the same event identity across a failed and successful attempt. The 600-second window is a proposed bound; expiry before success is incomplete. Exact attempts, retry intervals and ordering between independent events are not deterministic assertions. Handler retry configuration and durable failure-state setup must be read back, and cleanup must stop the owned retry source and remove its state.

Storage archive scenarios require versioning enablement/readback, cleanup of all owned object generations, and restoration/readback of the prior versioning configuration. The control bucket and topic are distinct from their primary resources. Another object prefix in the primary bucket is a positive routing case. Auth uses stable v1 events and disposable same-project users; repeated sign-in and explicit bulk deletion are negative controls. Pub/Sub readback concerns topic configuration and the publish receipt's message ID; it does not assume an API for rereading a published message.

Raw event IDs, times, names and payloads must be retained privately for two recordings. No normalizer is included: volatile-field decisions require those observations. Deployment resources, rules, versioning and capture infrastructure need their own reviewed setup and restoration plan. This source-only draft neither closes any condition nor replaces final-artifact comparison or independent review.

## Delivery evidence consistency

`validateDeliveryEvidence(corpus, closure, binding, record)` is a pure, case-scoped checker for a future capture adapter. It validates the frozen corpus first and binds the record to SHA-256 of `JSON.stringify(corpus)`, a run, a recording and a known case. The caller supplies the independently admitted handler ID, concrete names for all seven resource roles, and distinct subject/before-control/after-control entity names. Neither the binding nor the record establishes ownership or production authorization. This function does not assert that all 109 cases, both recordings, cleanup, or any payload compatibility obligation have completed.

The input schema is `functions-event-delivery-evidence-v1`. Each operation carries a scenario ID, a concrete resource role/name/entity, start/end times, the claimed typed result, a raw receipt and raw blobs for every declared readback and precondition. Blobs use exact `{ base64, sha256 }` fields; decoded bytes must match their hash, use canonical base64 and contain 1 byte to 1 MiB. The record allows at most 10,000 capture frames and 16 MiB of referenced raw bytes. These are local planner limits, not Firebase limits. There is no file, network or credential access. Reusing a blob does not prove separate observations: the future adapter must establish provenance and interpret its native bytes.

All operation, window and capture millisecond values share the capture's monotonic `clockId`; native event times are retained separately as uninterpreted strings. Capture starts before all operations. Its frames must have consecutive cursors after the baseline, nondecreasing capture times, zero initial/final loss counters, intact raw bytes and a final barrier at capture completion. Every event frame must match the expected run, recording, handler, generation, handler event/resource, source family and one declared operation's concrete source resource/entity. Source and handler resource bindings are separate, allowing negative routing through a different bucket, topic or collection. Unknown frames and mismatched bindings are rejected instead of silently filtered.

Positive delivery requires a successful subject event by the proposed window deadline. Negative delivery requires the full proposed duration after the subject operation finishes, no claimed subject events anywhere in the supplied capture, a successful same-handler positive control before the subject starts, and another whose operation starts after the window ends. A late subject event also rejects this evidence package. The caller cannot supply an empty matched-event list to bypass scanning. Retry evidence must retain one source/ID identity and native time across a failed attempt followed by a successful attempt in the window; duplicate attempts are allowed and their exact count/delay is not asserted. Source plus ID is the identity pair in the [CloudEvents specification](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#id).

The result is only `evidence-consistent`. `semanticAdaptersVerified`, `compatibilityEstablished`, `absenceEstablished` and `sendAuthorized` remain false. Source-result/readback semantics, parsing and correlating native events, capture authenticity and loss detection, deployment/configuration readbacks and resource admission are unimplemented trust boundaries. The checker verifies supplied claims and byte integrity; it cannot detect a dishonest adapter that omits an event and renumbers frames. Production capture must provide those guarantees before any negative delivery or compatibility conclusion. No native event ID, time or payload is normalized here.

`validateRecordingSet(corpus, closure, recordings)` checks a supplied pair of declared recordings against the SHA-256 of the exact frozen corpus and closure JSON objects. Their canonical `JSON.stringify` forms must match the pinned digests; changing either frozen input requires a reviewed update to this checker. Each group has a distinct run and recording ID and exactly one case-scoped `{ binding, record }` entry for every frozen case. It rejects missing, duplicate, unknown, mixed and accessor-backed identity entries before returning `declared-evidence-set-consistent`. It uses `validateDeliveryEvidence` for each entry and returns no production authorization or compatibility conclusion. The two IDs and complete declarations do not establish that two production runs occurred, that their raw captures are genuine or independent, or that cleanup and final-artifact comparison are complete.

## Local Firestore v2 native frame check

`verifyNativeFirestoreV2Frame(frame, operation, row)` checks one declared Firestore v2 frame against canonical JSON bytes emitted by a controlled handler capture. It verifies the raw SHA-256 and UTF-8, derives the event ID, time, source, type and document path, and compares those values with the frame claims and owned operation path. A written handler requires the reported written event type; the Auth context variant requires the written suffix and `authtype`. This is a partial local adapter. The existing 109-case recording validator does not invoke it, and no production capture shape or provenance has been verified. The function returns `captureProvenanceVerified: false`, `compatibilityEstablished: false` and `sendAuthorized: false`.

`validateNativeFirestoreV2Evidence(corpus, closure, binding, record)` is an optional one-case composition. It first applies the declared delivery evidence contract, then verifies every Firestore v2 event frame, including before and after controls and repeated retry attempts, against the corresponding owned operation. It rejects other source families and v1. The all-case recording-set validator still does not call this helper. Its result reports local native frame consistency only; semantic source-result checks, capture provenance, compatibility, absence and send authority remain unverified. The synthetic native envelope has not been established as the shape of a production capture.
